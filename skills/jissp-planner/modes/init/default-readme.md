## 1. 아키텍처 원칙

- 과도한 설계(over-engineering)는 지양하되, 적절한 확장성·모듈 응집도·관심사 분리를 고려합니다.
- 검증되지 않은 기술보다 프로젝트에서 이미 사용 중이거나 검증된 기술을 우선합니다.
- 설계 결정에는 항상 "왜 이 선택을 했는가"에 대한 근거를 함께 기록합니다.

## 7. 설계 문서 작성 시 주의사항

- PRD의 모든 요구사항이 설계에 매핑되었는지 확인합니다.
- 결정하지 못한 항목은 억지로 채우지 말고 `(미정)` 으로 남기고, 필요 시 추천안을 제시합니다.
- 사용자 판단이 필요한 트레이드오프(인증 방식, DB 선택 등)는 문서에 명시하고 확인을 요청합니다.
- **계약과 구현을 분리합니다.** 스키마·API·시그니처·타입·페이로드·설정 키 같은 **모듈 간 합의 사항(계약)** 은 Part A에 코드로 명확히 확정하되, 함수 본문·제어 흐름·import·DI 배선 같은 **구현 상세는 문서에 쓰지 않습니다.** 판별 기준: *한 파일 안에서 닫히면 쓰지 않고, 둘 이상이 합의해야 하면 쓴다.*
- 설계 문서는 '복사해서 붙이는 코드 모음'이 아니라 '무엇을 지켜야 하는지 확정하는 문서'입니다.
