# 검토 가이드라인

본 문서는 `jissp-planner` 의 review 모드가 서브에이전트에게 전달하는 **검토 관점**과 **발견 사항 반환 양식**을 정의합니다.

## 검토 관점

검토 대상에 따라 아래 관점 중 해당되는 것을 적용합니다. 관점이 여러 개라는 이유로 서브에이전트를 나누지 마십시오. 레인 분할 기준은 `modes/review/document-review.md` 의 "서브에이전트 구성 기준"을 따릅니다.

### 1. 정합성 (Consistency)

**문서 간 / 문서와 원본 요구사항 간의 일치 여부**

- PRD의 모든 요구사항이 설계 문서에 빠짐없이 매핑되었는가?
- 설계 문서에 PRD에 없는 요구사항이 근거 없이 추가되지 않았는가? (범위 확장)
- 참조한 PRD 문서 경로, 링크, 파일명이 실제로 존재하는가?
- 여러 문서에서 같은 개념을 다른 용어로 부르고 있지 않은가?

### 2. 내부 모순 (Contradiction)

**한 문서 안에서 서로 충돌하는 서술**

- 개요와 세부 요구사항이 서로 다른 방향을 가리키지 않는가?
- 데이터 모델과 API 스펙이 불일치하지 않는가? (필드명·타입·필수 여부)
- 처리 흐름(Flow)과 아키텍처 구조가 일치하는가?
- 첨부된 도식이 본문 서술과 일치하는가?
- 우선순위(P0/P1/P2)가 서로 모순되게 부여되지 않았는가?

### 3. 누락 (Missing)

**있어야 하지만 빠진 정의·작업**

- 요구사항은 정의됐지만 이를 처리하는 설계·인터페이스가 없는 항목
- 정의된 상태·이벤트 중 전이(transition)나 처리 주체가 없는 항목
- 에러/예외 처리, 경계 조건(빈 값, 최대치, 동시성) 정의 누락
- 비기능적 요구사항(보안·성능·로깅·권한) 정의 누락
- 마이그레이션, 롤백, 하위 호환성 고려 누락

### 4. 잘못된 정의 (Incorrect Definition)

**정의는 있지만 틀렸거나 부적절한 항목**

- 기술적으로 실현 불가능하거나 선택한 스택으로 구현할 수 없는 설계
- 전달받은 프로젝트 Rule 문서(설계 Rule·추가 Rule·리뷰 설정의 추가 기준 문서)의 규칙(스택·컨벤션·의존성 방향)을 위반한 설계
- 실제 코드베이스의 구조·네이밍과 어긋나는 정의 (코드 확인이 가능한 경우)
- 근거 없이 사실처럼 단정된 서술 (`(미정)` 으로 표기해야 할 내용)

### 5. 모호함 (Ambiguity)

**구현자가 여러 갈래로 해석할 수 있는 서술**

- "적절히", "필요 시", "빠르게" 등 측정 불가능한 기준
- 주체가 생략되어 누가 수행하는지 불명확한 작업
- 입력/출력 형식이 특정되지 않은 인터페이스

### 6. 양식 준수 (Format)

- PRD: `~/jissp-agent-kit/skills/jissp-planner/modes/draft/output-guideline.md` 양식과 초안 수준의 간결함
- 구조 문서(`*-structure.md`): `~/jissp-agent-kit/skills/jissp-planner/modes/structure/output-guideline.md` 양식
  - 문서 최상단 `문서 성격 배너`(상태 표기 포함) 포함 여부
  - ⚠️ **검토의 무게중심은 §2 디렉토리 구조(역할·테스트 분류)·§3 의존 방향과 흐름·§4 테스트 seam**다. 판단 기준은 `~/jissp-agent-kit/skills/jissp-planner/modes/structure/structure-principles.md` 를 따른다.
  - 역할이 한 줄이 아닌 모듈, 순환·금지 방향 의존, seam이 없는 외부 의존, `Integration`·`조립` 모듈에 들어간 로직, 과잉 분리(pass-through 레이어·단일 구현 인터페이스 남용)를 지적한다.
  - 반대로 **구조 문서에 시그니처·타입 필드·스키마·함수 본문, 메서드 호출 수준의 처리 흐름·동작 규칙이 들어가 있으면 범위 초과로 지적한다.** 계약·세부 동작은 설계 문서의 몫이므로, 구조 문서에 이것들이나 요구사항 매핑표·테스트 검증 포인트·컨벤션 대조표가 없는 것은 누락이 아니다.
- 설계 문서: `~/jissp-agent-kit/skills/jissp-planner/modes/architecture/output-guideline.md` 양식
  - **Part A(§1~§9) = 설계 결정(확정 대상), Part B(§11~§12) = 구현 지시(실행 참고)** 구조 준수 여부
  - ⚠️ **검토의 무게중심은 Part A**다. 특히 §4(데이터 모델)·§5(인터페이스 계약)이 모호함 없이 확정되었는지 본다.
  - §3의 『모듈 단위와 테스트 경계』 표는 **구조 문서와 같은 기준**(위 항목)으로 본다. 표가 통째로 없으면 누락으로 지적한다.
  - 구조 문서가 함께 전달되면 구조 제약 준수를 본다: §3이 구조 문서의 구조를 재설계하지 않았는지, 『모듈 단위와 테스트 경계』 표가 구조 문서 §2(역할·테스트 분류)·§4(seam)와 일치하는지, §11이 구조 문서 §2 트리와 일치하는지, 구조 문서 §1 `합의 사항` 이 §4·§5 계약에 반영되었는지. 구조 변경이 §9에 기록되지 않고 본문에 바로 반영되었으면 지적한다.
  - Part B는 파일 목록의 방향 일치만 확인하고, 상세도 부족을 지적사항으로 올리지 않는다. 반대로 **Part B에 함수 본문·import·DI 배선 등 구현 코드가 들어가 있으면 지적한다.**
  - §12에 병렬 그룹(`2-A`, `2-B`)이 있으면 **같은 그룹 단계끼리 §11 `단계` 파일이 겹치는지, 한 단계가 다른 단계의 구현체를 직접 호출하는 숨은 의존이 있는지, 공용 파일(DI 등록·배럴·공용 타입·마이그레이션)이 그룹 단계에 들어가 있는지** 지적한다. 병렬 실행 시 충돌·중단으로 이어지므로 Major로 본다. 그룹이 없는 것은 누락이 아니다.
  - 문서 최상단 `문서 계약 배너` 포함 여부
- 파일명 규칙 준수 여부 (기본 규칙: `YYYYMMDD_HHmmss_[feature]-[prd|structure|architecture].md`. 프로젝트 설정으로 바뀌었을 수 있으므로, 전달받은 문서들 사이에서 형식이 어긋나는 경우만 Minor로 지적)

### 7. 프로젝트 리뷰 설정 (전달된 경우)

`reference_docs` 에 jissp-planner 리뷰 설정 문서(`review-config.md`)가 포함되어 있으면 아래처럼 적용합니다.

- **1. 추가 검토 관점**: 위 1~6 관점에 **더해서** 점검합니다. 검토 대상의 문서 유형(PRD·구조 문서·설계 문서)에 해당하는 항목과 `공통` 항목만 적용하고, 프롬프트 검토는 `공통` 항목만 적용합니다. 항목에 `[심각도]` 가 붙어 있으면 위반 시 그 심각도로 보고합니다. 근거 필드에는 `review-config.md §1` 처럼 위치를 적습니다.
- **2. 제외 항목**: 해당하는 지적은 보고하지 않습니다. (1~6 관점보다 우선)
- **3. 심각도 조정**: 해당하는 지적은 아래 "심각도 기준" 대신 지정된 심각도로 보고합니다.
- **4. 추가 기준 문서 · 5. 실행 옵션**: 호출 측이 처리합니다. 검토자는 적용하지 않습니다.
- 리뷰 설정은 검토 **기준**만 바꿉니다. 아래 반환 양식·분량 제한·보고 대상 판단 규칙은 설정과 무관하게 그대로 따릅니다.

## 심각도 기준

| 심각도 | 기준 |
|---|---|
| **Critical** | 이대로 구현하면 동작하지 않거나, 요구사항을 충족할 수 없는 문제 |
| **Major** | 구현자가 잘못 해석할 가능성이 높거나, 주요 요구사항이 누락된 문제 |
| **Minor** | 오타, 용어 불일치, 양식 위반 등 해석에 영향이 적은 문제 |

## 분류 기준

| 분류 | 기준 |
|---|---|
| **자체 수정 가능** | 정답이 하나로 특정되는 문제 (오타, 누락된 매핑, 잘못된 참조 경로, 양식 위반, 명백한 내부 모순) |
| **사용자 결정 필요** | 트레이드오프가 있거나 의도를 확인해야 하는 문제 (설계 방향 충돌, 요구사항 자체의 모순, 범위 판단) |

## 발견 사항 반환 양식

서브에이전트는 문서를 **직접 수정하지 않고**, 아래 양식으로 발견 사항만 반환합니다.

```markdown
## 검토 관점: [담당 관점명]
## 검토 대상: [문서 경로]

### [심각도] 한 줄 요약
- **위치**: [문서 경로]:[줄 번호 또는 절 제목]
- **문제**: (무엇이 왜 잘못되었는지 — 한 줄)
- **근거**: (다른 문서/절/Rule/코드의 위치만 — 예: `rules/.../README.md:12`, `§5.1`. 인용·해설 금지)
- **제안**: (어떻게 고쳐야 하는지 — 한 줄)
- **분류**: 자체 수정 가능 | 사용자 결정 필요
```

**분량 제한 (필수 준수)**

- 각 필드는 **한 줄**. 줄바꿈·하위 불릿·강조 남발 금지.
- **근거**는 위치만 적습니다. 원문을 인용하거나 왜 그것이 근거인지 설명하지 마십시오.
- 발견 사항 하나는 **6줄을 넘기지 않습니다.**
- 발견 사항은 **심각도 순으로 최대 15건**까지만 반환합니다. 초과분은 `그 외 Minor N건` 으로 집계합니다.
- 반환 결과에 서론·총평·결론 문단을 붙이지 마십시오. 양식 그대로만 반환합니다.

**보고 대상 판단**

- 발견 사항이 없으면 `발견 사항 없음` 과 함께 점검한 항목을 나열합니다.
- **추측 금지**: 근거를 문서/코드에서 특정할 수 없는 지적은 반환하지 않습니다.
- 문서에 명시적으로 `(미정)` 으로 표기된 항목은 "누락"으로 보고하지 않습니다. 단, 미정 상태로 남기면 구현이 막히는 경우에는 `사용자 결정 필요` 로 보고합니다.
- 스타일·취향 수준의 지적(문장 다듬기 등)은 제외합니다.
- **이전 검토 회차의 판단을 번복하는 지적**은 현재 문서 서술만을 근거로 판단합니다. "N차에서는 이랬다" 는 식의 이력 비교를 반환하지 마십시오.
