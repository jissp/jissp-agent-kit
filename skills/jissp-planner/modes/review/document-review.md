# [작업 A] 문서 검토

작성 완료된 PRD/설계 문서를 대상으로 모순·누락·잘못 정의된 부분을 찾아내고 보완합니다.

경로 표기(`[Jissp 문서]/[PRD 문서]`, `[Jissp 문서]/[설계 문서]` 등)의 해석 기준과 공통 원칙은 스킬 루트의 SKILL.md와 `modes/review/guide.md` 를 따릅니다.

## A-1. 검토 대상 수집

1. 전달된 경로의 문서를 확인합니다. 파일이 존재하지 않으면 `[Jissp 문서]/[PRD 문서]`, `[Jissp 문서]/[설계 문서]` 에서 유사 파일을 탐색하여 사용자에게 확인합니다.
2. 대상 문서가 설계 문서 또는 구조 문서(`*-structure.md`)인 경우, **연관된 PRD 문서**(문서 내 "참조한 PRD 문서 경로" 등)를 함께 검토 대상에 포함합니다. 대상이 설계 문서이고 §1에 구조 문서 경로가 있으면(인계받은 경우) **그 구조 문서**도 포함합니다. (문서 전문을 읽지 말고 `Grep` 으로 경로만 확인) 상위 문서와 함께 검토해야 문서 간 정합성(요구사항 매핑·구조 제약 준수)을 확인할 수 있습니다.
3. `[설계 Rule 문서]` 와 `[추가 Rule 문서]` 중 존재하는 문서를 검토 기준으로 함께 전달합니다. 리뷰 설정의 `추가 기준 문서` 도 같은 방식으로 전달합니다.
4. `[리뷰 설정 문서]` 가 있으면 모든 레인에 함께 전달합니다. (`modes/review/guide.md` 의 "프로젝트 리뷰 설정")

### 코드 대조 범위 사전 산출 (필수)

코드 대조 레인에 "프로젝트 코드베이스"를 통째로 넘기면 서브에이전트가 자유 탐색에 시간을 다 씁니다. **메인 컨텍스트에서 확인할 파일 목록을 먼저 뽑아 넘깁니다.**

- `Grep` 으로 검토 대상 문서에서 **경로처럼 보이는 토큰만** 추출합니다. (예: 확장자·디렉토리 구분자를 포함한 패턴을 `output_mode: "content"` 로 조회)
- 문서 전문을 `Read` 하지 마십시오. Grep 은 매칭된 줄만 반환하므로 컨텍스트 분리 원칙을 깨지 않습니다.
- 추출된 경로에서 중복을 제거해 목록으로 만들고, 서브에이전트에 `code_scope` 로 전달합니다.
- **존재 여부는 메인에서 확인하지 않습니다.** 없는 경로는 서브에이전트가 "잘못된 참조"로 보고하도록 그대로 넘깁니다.
- 문서에 경로가 하나도 등장하지 않으면 코드 대조 레인 자체가 불필요합니다. A-2의 1개 레인 처리로 넘어갑니다.
- 리뷰 설정의 **코드 대조**가 `off` 이면 이 산출을 생략하고 1개 레인으로 처리합니다.

## A-2. 분리된 컨텍스트에서 분석 (필수)

메인 컨텍스트 윈도우를 오염시키지 않기 위해, **문서 분석은 반드시 `Agent` 툴로 서브에이전트를 띄워 수행**합니다. 메인 컨텍스트에서 문서 전문을 직접 읽어 분석하지 마십시오.

> **Gemini(agy) 환경**: `Agent` 툴 대신 `invoke_subagent` 를 사용합니다. 레인마다 `Subagents` 배열 항목 하나(`TypeName: "jissp-doc-reviewer"`, `Prompt`: 아래 "서브에이전트 전달 사항")를 넣어 **한 번의 호출로 병렬 실행**합니다. agy 는 호출 시 모델을 고를 수 없으므로 아래 `모델` 열과 `model` 지정은 생략합니다. 그 외 규칙(에이전트 타입·레인 구성·전달 사항)은 동일합니다.

### 서브에이전트 구성 기준 (필수 준수)

서브에이전트는 **입력(읽어야 하는 자료)이 다를 때만 나눕니다.** 관점이 다르다는 이유만으로 레인을 늘리지 마십시오. 같은 문서를 여러 레인이 각각 통째로 다시 읽는 것은 중복 비용입니다.

**기본 구성은 2개 레인입니다.**

| 레인 | 담당 | 읽는 자료 | 에이전트 타입 | 모델 |
|---|---|---|---|---|
| 문서 내부 검토 | 정합성·완결성·모순·일관성·비기능·양식을 **한 레인에서 모두** | 검토 대상 문서 + guideline | `jissp-doc-reviewer` | `sonnet` |
| 코드/외부 대조 | 문서의 사실 주장을 실제 코드·Rule 문서와 대조 | `code_scope` 목록 + Rule 문서 | `jissp-doc-reviewer` | `opus` |

- **두 레인은 반드시 한 메시지에서 동시에 띄웁니다 (필수).** 하나의 응답 안에 `Agent` 툴 호출 2개를 넣어 병렬 실행시킵니다. 레인 1의 결과를 받은 뒤 레인 2를 띄우면 소요 시간이 그대로 2배가 됩니다. 두 레인은 서로의 결과에 의존하지 않으므로 순차 실행할 이유가 없습니다.
- **에이전트 타입 (필수 준수)**: 두 레인 모두 반드시 **`jissp-doc-reviewer`** 로 띄웁니다 (`Agent` 툴의 `subagent_type: "jissp-doc-reviewer"`). 이 에이전트는 `tools: Read, Glob, Grep` 으로 **쓰기 수단이 전혀 없어**(Edit/Write뿐 아니라 `Bash` 도 없음), 검토 에이전트가 문서·코드를 임의로 수정하는 사고를 구조적으로 막습니다. 반환 규격도 `review-guideline.md` 하나만 따르도록 되어 있어 불필요한 리포트 작성·정상 항목 나열이 발생하지 않습니다.
  - **`general-purpose`(또는 `subagent_type` 미지정)로 띄우지 마십시오.** 그 타입은 도구가 `*`(전체)라 "문서를 수정하지 말 것"이라는 프롬프트 지시만으로는 쓰기를 막지 못하며, 검토 요청을 구현으로 확장해 승인 없는 코드 변경을 남기는 사고가 실제로 발생했습니다. 권한은 프롬프트가 아니라 **에이전트 타입으로** 강제합니다.
  - **`jissp-gap-validator` 를 쓰지 마십시오.** 그쪽은 `Write` 를 가진 **산출물 갭 검증용**(`jissp-task-manager` 등)으로, 갭 리포트를 파일로 남깁니다. review 모드는 A-4 승인 게이트를 거친 뒤 **메인 컨텍스트가** 문서를 수정하는 구조이므로, 검토자가 쓰기 권한을 가지면 그 게이트가 무너집니다.
- **모델**: 기본 `sonnet`. `opus` 는 **코드/외부 대조 레인에만** `Agent` 툴의 `model: "opus"` 로 오버라이드합니다. 문서를 읽고 모순을 찾는 작업은 `sonnet` 으로 충분합니다.
- **코드 대조가 불필요한 경우**(순수 기획 PRD 등)에는 **1개 레인**으로 끝냅니다.
- **레인을 3개 이상으로 늘리는 것은 아래 조건에서만** 허용합니다. 늘릴 때는 **그 이유를 사용자에게 먼저 알립니다.**
  - 검토 대상 문서가 3개 이상이고 서로 독립적으로 읽어야 하는 경우 → **문서 단위로** 분할 (관점 단위 아님)
  - 대상 문서 하나가 과도하게 커서(대략 100KB 초과) 한 레인이 감당하기 어려운 경우 → 장(章) 단위로 분할
  - 사용자가 명시적으로 심층·다각도 검토를 요청한 경우
- 레인을 나눌 때는 **각 레인의 입력이 겹치지 않도록** 범위를 지정합니다.

### 서브에이전트 전달 사항

`jissp-doc-reviewer` 의 입력 계약에 맞춰 아래 필드를 전달합니다.

| 필드 | 레인 1 (문서 내부) | 레인 2 (코드 대조) |
|---|---|---|
| `review_target` | 검토 대상 문서의 **절대 경로** | 검토 대상 문서의 **절대 경로** |
| `reference_docs` | 관련 PRD 문서 경로 + 관련 구조 문서 경로(설계 문서 검토 시) + `[리뷰 설정 문서]` | Rule 문서·추가 기준 문서 경로 + `[리뷰 설정 문서]` |
| `guideline_path` | `~/jissp-agent-kit/skills/jissp-planner/modes/review/review-guideline.md` (**절대 경로**) | 동일 |
| `focus` | 정합성·모순·누락·모호함·양식 (+ 리뷰 설정의 추가 검토 관점) | 문서의 사실 주장 ↔ 실제 코드 대조 (+ 리뷰 설정의 추가 검토 관점 중 코드 확인이 필요한 항목) |
| `code_scope` | (전달하지 않음) | A-1에서 산출한 **파일 경로 목록** |

- **1개 레인으로 끝나는 경우**(코드 대조 불필요·`off`) Rule 문서·추가 기준 문서를 레인 1의 `reference_docs` 에 함께 넣어, Rule 위반 점검이 빠지지 않게 합니다.
- 문서 본문을 프롬프트에 복사하지 말고 **경로만** 전달하여 서브에이전트가 직접 읽게 합니다.
- 레인 2에 `code_scope` 를 반드시 전달합니다. 목록 없이 띄우면 에이전트가 코드베이스를 자유 탐색하여 시간이 급증합니다.
- 반환 양식·분량 제한은 `jissp-doc-reviewer` 가 `guideline_path` 를 읽어 스스로 준수하므로, 프롬프트에 양식을 다시 풀어 쓰지 마십시오.

## A-3. 발견 사항 정리 및 분류

서브에이전트가 반환한 발견 사항을 종합하여 중복을 제거하고, 심각도(Critical/Major/Minor) 순으로 정렬한 뒤 **두 가지로 분류**합니다.

- **자체 수정 가능**: 사용자 판단이 불필요한 명백한 문제 (오타, 문서 내 모순, 누락된 요구사항 매핑, 양식 위반, 잘못된 참조 경로 등)
- **사용자 결정 필요**: 트레이드오프가 있거나 의도를 확인해야 하는 문제 (설계 방향 충돌, 요구사항 자체의 모순, 범위 판단 등)

분류 결과를 **수정 전에 사용자에게 먼저 보고**합니다. 발견 사항이 하나도 없으면 점검한 관점을 요약하여 알리고 종료합니다.

## A-4. 사용자 확인

- **사용자 결정 필요** 항목이 있으면 `AskUserQuestion` 으로 해결 방향을 질문합니다. 각 항목마다 근거와 함께 **권장안을 첫 번째 선택지**로 제시합니다.
- 질문 없이 임의로 판단하여 문서를 확정하지 마십시오.

## A-5. 문서 수정

확정된 방향에 따라 문서를 수정합니다.

- **자체 수정 가능** 항목은 즉시 수정합니다. 단, 리뷰 설정의 **자체 수정 가능 항목 처리**가 `confirm` 이면 A-4에서 수정 여부를 함께 확인받고, 승인된 항목만 수정합니다.
- **사용자 결정 필요** 항목은 A-4에서 확정된 방향으로 수정합니다.
- 수정은 `Edit` 로 **해당 부분만 최소 범위로** 반영합니다. 문서 전체를 재작성하지 마십시오.
- 원본 문서의 양식과 문체를 그대로 유지합니다. (PRD는 `modes/draft/output-guideline.md`, 구조 문서는 `modes/structure/output-guideline.md`, 설계 문서는 `modes/architecture/output-guideline.md` 양식 준수)
- 사용자가 "수정하지 않아도 된다"는 의사를 표현한 항목은 수정하지 않습니다.

### 검토 흔적 삽입 금지 (최우선 규칙)

**문서는 "최종 확정된 내용"만 서술합니다. 검토 과정·근거·이력은 문서에 남기지 않고 채팅 응답(A-7)으로만 보고합니다.**

문서에 **절대 추가하지 않는 것**:

| 금지 | 예시 |
|---|---|
| 검토 회차 표기 | `(4차 발견)`, `✅ 확정 (4차)`, `3차 정정`, `2차의 근거는 오류였다` |
| 판단 근거 각주 | `> **⚠️ C2/C3 는 Rule 과 상충한다 (4차 발견 — 코드 대조)**` 로 시작하는 blockquote 해설 블록 |
| 본문 → 각주 포인터 | `— 아래 주석`, `아래 주석 참조`, `§5.1 주석` |
| 변경 설명 주석 | `<!-- 수정: ... -->`, `※ 4차 보충: ...`, `⚠️ 범위가 3차 서술보다 넓다` |
| 이력 보존 취소선 | `- [x] ~~기존 서술~~ — ✅ 확정: ...` |

- 잘못된 서술은 **주석을 달아 반박하지 말고, 올바른 내용으로 교체**합니다. 틀린 원문은 지웁니다.
- 결정된 사항은 **결정 결과만** 적습니다. 검토 과정에서의 판단 경위·이전 서술은 적지 않습니다. (단, 설계 문서 §3·구조 문서 §7의 `채택안 / 버린 대안 / 이유` 처럼 원본 양식이 요구하는 설계 근거는 그 양식대로 작성합니다)
- 이미 문서에 위와 같은 흔적이 쌓여 있다면, 이번 수정 범위 안에서 **함께 제거**합니다.
- 유일한 예외: 기존 문서가 원래 채택한 표기(`(미정)` 등)는 그대로 사용합니다.

### 미결정 항목 기록

수정하지 않기로 한 항목은 원본 문서 양식의 미결정 절에 **항목당 한 행**으로 기록합니다.

- 설계 문서: §9 표(`ID | 항목 | 권장안 / 대안 | 확인 필요 사유`)에 한 행 추가
- 구조 문서: §10 표(같은 컬럼)에 한 행 추가
- PRD: 미결정 절이 없으므로 해당 항목 자리에 `(미정)` 으로 표기
- 각 칸은 한 줄로 씁니다. 배경 설명·발견 경위는 덧붙이지 않고, 대안 간 비교 설명은 채팅으로 보고합니다.

## A-6. 재검증 (조건부)

수정 범위가 넓거나(3개 이상의 절을 수정) 구조적 변경이 있었던 경우, A-2를 한 번 더 수행하여 수정으로 인한 **새로운 모순이 발생하지 않았는지** 확인합니다.

- 리뷰 설정의 **재검증**이 `always` 면 문서를 수정한 경우 항상 1회, `off` 면 수행하지 않습니다.
- **재검증은 최대 1회**만 수행합니다. (무한 반복 금지)

## A-7. 결과 요약 응답

작업이 완료되면 사용자에게 아래를 **간략하게** 정리하여 응답합니다.

- 검토한 문서 경로
- 발견한 문제와 **어떤 부분이 어떻게 변경되었는지** (심각도 순, 항목별 한 줄)
- 사용자 결정에 따라 반영한 사항 (있는 경우)
- 수정하지 않고 남긴 사항 및 그 이유 (있는 경우)
- 리뷰 설정에서 적용하지 못한 항목 및 그 이유 (있는 경우 — 잘못된 실행 옵션 값, 없는 추가 기준 문서 경로, 공통 원칙과 충돌하는 설정)

**응답 분량 제한**: 전체 **30줄 이내**. 항목당 **한 줄**(줄바꿈·하위 불릿 없이)로 쓰고, 판단 근거를 재서술하지 않습니다. 항목이 10개를 넘으면 Critical/Major 만 나열하고 Minor 는 `그 외 Minor N건 (오타·용어 통일 등)` 한 줄로 묶습니다.

## A-8. 다음 작업 안내 (조건부)

검토 대상 문서의 종류에 따라 아래와 같이 다음 작업을 물어봅니다.

**검토 대상이 PRD 문서뿐이고 연관된 구조·설계 문서가 아직 없는 경우** — 아래 선택지를 제시합니다.

1. **`/jissp-planner structure`**: 신규 모듈 설계, 새 파일·디렉토리가 여럿 생기는 신규 기능 개발, 모듈 경계가 바뀌는 큰 리팩토링처럼 **구조부터 잡아야 하는 경우** 권장합니다.
   - 사용자가 선택하면 검토·수정이 완료된 PRD 문서 경로를 모드 args로 하여 structure 모드로 전환합니다.
2. **`/jissp-planner architecture`**: 기존 구조 안에서 닫히는 변경이라 구조 설계가 필요 없는 경우입니다.
   - 사용자가 선택하면 검토·수정이 완료된 PRD 문서 경로를 모드 args로 하여 architecture 모드로 전환합니다.
3. **종료**: 사용자가 원하지 않으면 여기서 작업을 종료합니다.

**검토 대상이 구조 문서(`*-structure.md`)이고 연관된 설계 문서가 아직 없는 경우** — 구조 문서 배너의 상태를 확인합니다.

- `상태: 확정` 이면 **architecture 모드(`/jissp-planner architecture`)로 설계 문서 작성을 진행할지** 물어봅니다. 사용자가 동의하면 `modes/structure/guide.md` 의 **S-7 인계 args** 형식으로 모드 args를 구성하여 architecture 모드로 전환합니다. (구조 문서 경로가 빠지면 안 됩니다. 구조 제약은 architecture 가이드 B-2가 적용합니다.)
- `상태: 초안` 이면 구조가 아직 확정되지 않았음을 알리고, `/jissp-planner structure revise [구조 문서 경로] [변경 요청]` 또는 사용자 확정을 먼저 거치도록 안내합니다.

> 설계 문서가 이미 검토 대상에 포함되어 있었다면 본 단계를 생략하고 A-7에서 종료합니다.
