# 요구사항 순차 입력 개요

1. 사용자의 "모호한 제안"을 기술적 맥락으로 해석하고, 확장된 인사이트를 더해 정리합니다.
2. 사용자로부터 **개요 → 요구사항 → 성공 조건(Goal)** 순서로 입력을 순차적으로 받습니다.
3. 요구사항은 종료 표현이 나올 때까지 반복적으로 수집합니다.
4. 성공 조건(Goal)은 **선택 입력**이며, 입력하지 않으면 해당 절차를 건너뜁니다.

# 입력 방식 (필수)

- 개요·요구사항·성공 조건·확인 질문은 **일반 텍스트 메시지로 묻고, 사용자가 자유롭게 입력한 답을 기다립니다.**
- 이 단계들에서 `AskUserQuestion` 등 **선택지 UI를 사용하지 않습니다.** 예상 요구사항·개요를 선택지로 만들어 고르게 하지 않습니다. (사용자가 요구사항을 직접 입력할 수 없게 되기 때문)
- 보완 제안이 필요하면 텍스트로 "추천안"이라고 밝혀 적고, 채택 여부는 사용자가 자유 입력으로 답하게 합니다.
- 선택지 UI는 요구사항 수집이 끝난 뒤의 분기(작성 승인, 다음 작업 안내, 파일 덮어쓰기 여부)에서만 사용합니다.

# Interaction Protocol (프로세스)

## Step 1: 개요 입력받기

- 사용자에게 프로젝트/아이디어의 **개요**를 먼저 요청합니다.
- 입력받은 개요를 분석하여 핵심 목적과 대상 사용자를 파악합니다.
- 개요가 지나치게 모호하면 1~2가지 핵심 질문으로 명확히 한 뒤 다음 단계로 넘어갑니다.

## Step 2: 요구사항 반복 입력받기

- 개요 입력이 끝나면 **요구사항**을 하나씩 입력받습니다.
- 매 입력마다:
  1. 사용자가 입력한 요구사항을 기술적 맥락으로 해석하여 짧게 정리합니다. **표현은 PRD답게 다듬되(정제 권장), 요구사항의 내용·의도는 빠짐없이 보존**합니다. (거칠게 적힌 원문을 정돈·정교화하는 것은 좋으나, 그 과정에서 항목을 빼거나 의미를 축소·왜곡해서는 안 됩니다.)
  2. 지금까지 수집된 요구사항 목록(번호 매김)을 **하나도 빠짐없이** 보여줍니다. (표시를 간결히 하되, 목록에서 항목을 생략·병합·삭제하지 않습니다.)
  3. "다음 요구사항을 입력하시거나, 완료되었다면 `끝` 또는 `여기까지`를 입력해주세요."라고 안내합니다.
- **종료 조건**: 사용자가 `여기까지`, `끝`, 공백(빈 입력) 등 더 이상 입력하지 않음을 표현하면 즉시 수집을 중단합니다.

> **내용 보존 원칙**: 위의 "짧게/간단히"는 **대화 중 표시 방식**에 대한 지침일 뿐입니다. PRD 문서를 작성할 때는 사용자가 입력한 요구사항의 **표현은 PRD답게 정제·정교화하되, 내용·의도는 하나도 잃지 않아야** 합니다. 다듬는 것(권장)과 빼먹는 것(금지)은 다릅니다 — 어떤 요구사항도 생략·누락해서는 안 됩니다.

## Step 3: 성공 조건(Goal) 입력받기 — 선택

요구사항 수집이 종료되면, **마지막으로 한 번** 성공 조건(Goal)을 입력받습니다.

- 다음과 같이 안내합니다: "이 작업이 **어떤 상태가 되면 성공(완료)인지** 판단할 성공 조건(Goal)이 있다면 입력해주세요. 없다면 `없음` 또는 공백을 입력하시면 건너뜁니다."
- **입력한 경우**:
  1. 요구사항과 **동일한 방식**으로 처리합니다. 즉, 사용자가 입력한 성공 조건을 기술적 맥락으로 해석하고, 필요하면 실제 프로젝트(코드베이스·기술 스택·기존 구조)를 분석하여 이 프로젝트에서 **검증 가능한 형태**의 성공 조건으로 정제합니다.
     - 예: "로그인이 잘 되면 됨" → "기존 인증 모듈(`auth`) 기준으로 정상 계정 로그인 시 세션이 발급되고, 잘못된 비밀번호는 401을 반환한다."
  2. 정제한 성공 조건 목록(번호 매김)을 사용자에게 보여주고, 추가 입력이 있는지 확인합니다.
  3. **정제는 하되 사용자가 말한 조건을 생략·축소·왜곡하지 않습니다.** 사용자가 입력하지 않은 성공 조건을 임의로 사실처럼 추가하지 않으며, 프로젝트 분석으로 도출한 보완 조건은 **추천안임을 명시**합니다.
- **입력하지 않은 경우 (`없음`·공백·별도 언급 없음)**:
  - 성공 조건 절차를 **건너뛰고 기존과 동일하게** 다음 단계로 진행합니다.
  - 성공 조건을 임의로 만들어내지 않으며, PRD 문서에도 해당 항목을 추가하지 않습니다.

## Step 4: 중간 정리 및 승인

- 수집한 개요와 요구사항 **전체**를 정리하여 보여줍니다. (요구사항은 개수·내용을 빠짐없이 나열하며, "요약"을 이유로 항목을 줄이지 않습니다.)
- 성공 조건(Goal)을 입력받았다면 함께 정리하여 보여줍니다. (입력받지 않았다면 표시하지 않습니다.)
- 누락되었거나 불분명한 요구사항(기능적/비기능적)이 있으면 최대 3가지 이내로 확인 질문을 합니다.
- 사용자에게 "이 내용을 기반으로 PRD 문서 초안을 작성해도 될까요?"라고 확인받습니다.

## Step 5: PRD 문서 초안 작성으로 전달

- 사용자의 승인이 떨어지면 수집된 개요·요구사항(및 입력받은 경우 성공 조건)을 종합하여 다음 단계(PRD 초안 작성)로 넘어갑니다.
