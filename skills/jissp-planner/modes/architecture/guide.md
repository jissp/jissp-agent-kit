# 이 설계 문서의 목적과 성격 (⚠️ 가장 중요 — 반드시 먼저 이해할 것)

architecture 모드가 작성하는 문서는 **"코드를 미리 써두는 문서"가 아니라 "무엇을 지켜야 하는지 확정하는 문서"** 입니다.

## 계약과 구현의 분리

문서는 성격이 다른 두 부분으로 나뉩니다.

| | **Part A — 설계 결정** (§1~§9) | **Part B — 구현 지시** (§11~§12) |
| --- | --- | --- |
| 성격 | 합의·확정의 대상 (계약) | 착수 시점의 실행 참고 자료 |
| 수명 | 코드보다 오래 산다 | 구현 착수 순간 코드가 진실이 된다 |
| 변경 시 | **재검토 필요** | 재검토 불필요 |
| 갱신 의무 | 있음 (문서가 진실) | **없음** (코드가 진실) |

1. **사전 조사 기반의 결정 기록**: 요구사항을 어떤 구조·계약으로 실현할지, 실제 코드를 조사한 근거 위에서 결정하여 기록합니다.
2. **계약의 확정(Part A의 핵심)**: 데이터 모델(스키마·DDL)과 인터페이스(API·시그니처·타입·페이로드·설정 키)를 명확히 고정합니다. **이것이 구현이 반드시 지켜야 하는 고정점**입니다.
3. **구조와 트레이드오프 기록**: 모듈 경계, 의존 방향, 채택한 방식과 버린 대안, 그 이유를 남깁니다.
4. **영향 범위 명시**: 결정이 파급되는 범위(호출부·의존 모듈·공용 타입·설정·DB 마이그레이션 등)와 side effect를 기록합니다.
5. **실행 가능한 상태**: "문서를 그대로 복사하면 구현이 끝난다"가 아니라, **"계약을 어기지 않고 구현에 착수할 수 있다"** 를 목표로 합니다.

## 코드를 문서에 쓸 것인가 — 판별 기준 단 하나

> **한 파일 안에서 닫히는 것은 쓰지 않는다. 둘 이상의 파일·모듈·시스템·사람이 합의해야 하는 것만 쓴다.**

- **✅ 코드로 쓴다 (계약)**: 함수·메서드 **시그니처**(본문 없이), 타입·인터페이스·DTO 정의, DB DDL·마이그레이션 SQL, API 요청/응답 스키마·상태 코드, 이벤트·큐 페이로드 스키마, 설정·환경변수의 키·타입·기본값, 외부에 노출되거나 저장되는 enum **값**.
- **❌ 코드로 쓰지 않는다 (구현)**: 함수 **본문**(제어 흐름·분기 조건·변수 매핑), 에러 핸들링·Fallback 세부 구현, `import` 구문, DI 배선, ORM·쿼리 구현체, 로깅 문장.

> **왜 빼는가**: 구현 착수 시점에 실행자는 어차피 실제 코드를 다시 읽습니다. 그때 문서의 본문 스니펫은 이미 낡아 있을 가능성이 높고, **낡은 스니펫은 없는 것보다 나쁩니다**(잘못된 확신을 줍니다). 계약만 고정하면 실행자는 계약을 지키면서 현재 코드에 맞는 구현을 합니다.

**예외**: 순서가 깨지기 쉬운 처리, 트랜잭션 경계, 동시성·멱등성처럼 **구현자 재량에 맡기면 설계 의도가 깨지는 흐름**은 실제 코드가 아니라 §6에 **3~5줄 의사코드**로 서술합니다.

## 절대 하지 말 것

- ❌ 파일 하나를 통째로 재현하는 스니펫을 쓰지 마십시오. (구현자가 복사하도록 유도합니다.)
- ❌ **"추가 조사 없이 그대로 구현 가능한 완전한 코드"를 목표로 삼지 마십시오.** 이 목표가 문서를 코드 저장소로 변질시키고, 이후 수정 비용을 폭증시킵니다.
- ❌ 스니펫 안에 설계 근거를 주석으로 넣지 마십시오. "왜 이렇게 바꾸는가"는 스니펫 **바깥 본문**에 서술합니다. 주석으로 넣으면 구현자가 최종 코드의 일부로 오해해 그대로 옮기고, 기획·트레이드오프 설명이 코드에 눌러앉아 낡은 주석으로 남습니다.
- ❌ 스니펫의 클래스·인터페이스 선언에 역할 요약 주석(`/** 공용 공휴일 조회 코어 서비스 ... */`)을 붙이지 마십시오. 역할·구조 설명은 스니펫 바깥 본문에 쓰고, 코드에서는 모듈 `README.md` 가 담당합니다.

# 실행 분기: 모드 args 판별

모드 args에 따라 아래 작업 중 하나로 동작합니다. (작업 A였던 Rule 문서 초기화는 init 모드로 옮겨졌습니다.)

- 모드 args가 `init` 인 경우 → 이전 호출 방식과의 호환용입니다. init 모드(`modes/init/guide.md`)로 전환합니다.
- 모드 args의 첫 단어가 `revise` 인 경우 → **[작업 C] 기존 설계 문서 수정** (`revise [설계 문서 경로] [변경 요청]`)
- 모드 args가 PRD 문서 경로 **또는 작업 내용을 기술한 프롬프트**인 경우 → **[작업 B] 설계 문서 작성**
- 모드 args가 비어 있는 경우 → 직전 대화에서 생성된 PRD 문서 또는 확정된 구조 문서가 있으면 그 문서를 대상으로 확인을 구한 뒤 [작업 B]로 진행합니다. 대상을 특정할 수 없으면 사용자에게 `revise` / PRD 문서 경로 / 작업 프롬프트 중 무엇을 전달할지 안내하고 종료합니다.

> 입력이 **이미 존재하는 설계 문서 경로 + 변경 요청**으로 보이면, `revise` 키워드가 없어도 작업 C를 제안한 뒤 확인을 받고 진행합니다. (전체 재작성을 기본값으로 삼지 마십시오.)

# [작업 B] 설계 문서 작성 (모드 args: PRD 문서 경로 또는 작업 프롬프트)

전달받은 PRD 문서 또는 작업 프롬프트를 기반으로, 사전 조사(실제 코드 분석)를 거쳐 설계 문서를 작성합니다.

## B-0. 실행 방식 판정 (메인 / 위임)

코드 분석과 문서 작성을 서브에이전트에 맡길지(`agent`) 메인이 직접 할지(`inline`) 정합니다. 플래그·호출·반환 처리 규약은 `modes/delegation.md` 를 따르며, `agent` 로 정해지면 그 문서를 읽습니다.

- B-1 2번에서 요구사항을 파악한 뒤, 아래 기준으로 판정합니다.
  - **`inline`**: 요구사항이 기존 모듈 1~2개 안에서 끝나고, 모듈 경계를 넘는 계약(DB 스키마·API·공용 타입·이벤트·큐 페이로드·설정 키)을 새로 만들거나 바꾸지 않는 변경
  - **`agent`**: 그 외 전부. 구조 문서가 함께 전달된 경우도 `agent` 입니다.
- **단계 배정** (`agent` 일 때)

| 단계 | 담당 |
| --- | --- |
| B-1 1번 Rule 문서 | 메인은 **존재 여부만** 확인 (없을 때의 질문 포함). 내용은 서브에이전트가 읽음 |
| B-1 2번 요구사항 파악·질문 | 메인 |
| B-2 ~ B-4 | 서브에이전트 (B-4의 자동 수정까지) |
| B-5 ~ B-7 | 메인 |

- `inline` 이면 모든 단계를 메인이 수행합니다.

## B-1. Rule 문서 및 요구사항(PRD/프롬프트) 로드

1. `[설계 Rule 문서]` 파일을 읽어 프로젝트에 맞는 설계 Rule/GuideLine을 파악합니다. (이 시점에는 존재 여부만 확인하고, 내용은 B-0에서 `inline` 으로 정해진 뒤 읽습니다. `agent` 면 서브에이전트가 읽습니다)
   - **Rule 문서가 존재하지 않는 경우**: 사용자에게 "먼저 `/jissp-planner init` 으로 Rule 문서를 초기화하는 것을 권장합니다."라고 안내한 뒤, 기본 가이드라인(`modes/init/default-readme.md`)을 준용하여 계속 진행할지 확인합니다.
   - `[추가 Rule 문서]` 가 지정되어 있으면 함께 읽습니다. 설계 Rule 문서와 같은 무게로 준수합니다.
2. 요구사항 원문을 파악합니다.
   - **입력이 PRD 문서 경로인 경우**: 해당 문서를 읽어 개요·요구사항·제약사항을 파악합니다. PRD 문서를 찾을 수 없는 경우, `[Jissp 문서]/[PRD 문서]` 디렉토리에서 유사 파일을 탐색하여 사용자에게 확인합니다.
   - **입력이 작업 프롬프트인 경우**: 프롬프트 내용을 요구사항으로 삼아 목표·범위·제약을 정리합니다. 요구사항이 불명확하거나 범위가 모호한 부분은 임의로 가정하지 말고 사용자에게 확인한 뒤 진행합니다.

## B-2. 작업 대상 및 연관 코드 분석 (⚠️ 필수 — 생략 금지)

**문서 작성 전 반드시 작업 대상과 연관 레퍼런스 모듈 및 로직의 실제 코드를 분석해야 합니다.** PRD와 Rule 문서만 읽고 곧바로 설계 문서를 작성하지 마십시오. 실제 코드 근거 없이 추측만으로 작성된 설계 문서는 잘못된 산출물로 간주합니다.

- **모듈 문서 확인**: `[모듈 문서]` 가 지정되어 있으면, 작업 대상·연관 모듈의 문서를 먼저 읽어 흐름과 불변식을 파악합니다. 사용 규칙은 SKILL.md의 `모듈 문서 사용 원칙` 을 따릅니다.
- **작업 대상 코드**: 요구사항이 구현되거나 변경될 실제 파일·모듈·클래스·함수를 `Grep`/`Glob`/`Read` 로 탐색하여 현재 구조와 동작을 파악합니다.
- **연관 레퍼런스 모듈·로직**: 작업 대상이 의존하거나 영향을 주고받는 주변 모듈(호출부·피호출부, 공용 유틸, 데이터 모델, 인터페이스 등)의 실제 코드를 확인하여 통합 지점과 제약을 파악합니다.
- **기존 패턴·컨벤션**: 유사 기능의 기존 구현을 표본으로 확인하여, 설계가 프로젝트의 실제 코드 패턴과 일관되도록 근거를 확보합니다.
- **⭐ 계약 도출 (Part A의 핵심 산출물)**: 위 분석을 토대로, **모듈 경계를 넘나드는 것**을 식별합니다 — 변경/신설될 DB 스키마, API 엔드포인트, 공개 함수 시그니처, 공용 타입·DTO, 큐·이벤트 페이로드, 설정 키. 이것이 §4·§5가 됩니다. **기존 계약과의 차이(변경 전/후)** 를 함께 확인하십시오.
- **⭐ 모듈 단위와 테스트 경계 도출 (Part A의 산출물)**: 신설·변경되는 각 모듈의 **책임(한 문장)·테스트 분류·seam** 을 정합니다. 이것이 §3의 『모듈 단위와 테스트 경계』 절이 되며, 분류와 작성 규칙은 `modes/architecture/output-guideline.md` 를 따릅니다. 구조 문서(`*-structure.md`)가 함께 전달된 경우 **그 문서의 §4·§6을 그대로 옮기고 새로 설계하지 않습니다.**
- **구조 문서가 함께 전달된 경우의 제약**: 전달 경로(structure 모드 인계 args, args 없이 호출, 태스크 모드의 `module-structure.md`, review 모드 경유)와 무관하게 `상태: 확정` 인 구조 문서를 확정된 제약으로 따릅니다.
  - 구조 문서의 §3 디렉토리 구조, §4 모듈 책임, §5 의존 방향, §6 테스트 경계를 따릅니다. 설계 문서 §3(시스템 아키텍처)은 구조 문서를 참조해 작성하고 구조를 재설계하지 않습니다.
  - §11(변경 대상 파일)은 구조 문서 §3의 트리와 일치시킵니다.
  - 구조 문서 §9의 인계 사항을 §4·§5 계약으로 확정합니다.
  - 구조 변경이 필요하다고 판단되면 임의로 바꾸지 말고 설계 문서 §9(미결정 사항)에 기록합니다.
- **변경 대상 파일 식별 (Part B의 산출물)**: 신규 생성/수정/삭제 대상 파일 목록과 각 파일의 **변경 요지**(1~2문장)를 도출합니다. 이 단계에서 함수 본문을 미리 설계하려 하지 마십시오.
- **영향 범위 도출**: 계약 변경이 파급되는 범위(호출부·의존 모듈·공용 타입·설정·DB 마이그레이션·외부 연동 등)를 도출합니다. 이것이 §7이 됩니다.
- 설계 문서에는 위 분석에서 확인한 **실제 코드상의 근거(파일 경로·모듈명 등)** 를 명시하여, 추측이 아닌 코드 기반 설계임이 드러나도록 합니다.
- 분석 결과 요구사항과 실제 코드가 충돌하거나 정보가 부족한 경우, 임의로 가정하지 말고 사용자에게 확인합니다. (서브에이전트는 `modes/delegation.md` 5장대로 처리합니다)

## B-3. 설계 문서 작성

`modes/architecture/output-guideline.md` 파일의 양식과 절차를 따라 설계 문서를 작성합니다. Rule 문서의 규칙이 본 템플릿과 충돌하면 **Rule 문서를 우선**합니다.

- 저장 위치·파일명 규칙은 `modes/architecture/output-guideline.md` 의 `파일명 규칙` 을 따릅니다.
- **문서 최상단에 `문서 계약 배너`를 반드시 포함**합니다. (Part A/Part B의 갱신 정책 명시)
- **Part A(§1~§9)와 Part B(§11~§12)를 물리적으로 분리**하여 작성합니다. 절 번호와 Part 헤더를 임의로 바꾸지 마십시오.
- **§4(데이터 모델)·§5(인터페이스 계약)을 가장 정밀하게 작성합니다.** 이 두 절이 구현의 고정점이며, 여기가 모호하면 문서가 실패합니다. 구현자(Sonnet)가 추측하지 않도록 타입·시그니처·제약조건 수준까지 모호함 없이 확정하며, 시그니처·스키마는 코드 블록으로 명확히 쓰되 **본문은 쓰지 않습니다.**
- **§6(처리 흐름)에서 틀리면 안 되는 핵심 흐름은 의사코드로 고정합니다.** 트랜잭션 경계, 동시성/분산 락, 처리 순서 강제, 장애 복구 흐름은 3~5줄 의사코드로 반드시 명시합니다.
- **§3에 『모듈 단위와 테스트 경계』 하위 절을 반드시 둡니다.** 하위 절 번호는 문서 구성에 맞게 부여합니다(예: `3.5`).
- **§11(변경 대상 파일)은 표의 요지 수준으로만 작성합니다.** 완성 코드를 붙이지 말고, 각 행의 `준수할 계약` 컬럼으로 §4·§5를 참조시킵니다.
- **§12(작업 순서)는 §3 테스트 분류 기준의 `하위 단위 → 조립` 방향으로 작성하고, 수용 기준 및 실행 모델(난이도)을 명시합니다.**
  - 각 단계별로 완료를 판정할 **수용 기준(검증 조건)** 을 1문장으로 기술합니다.
  - 기본 실행 모델은 `Sonnet` 으로 지정하되, 복잡한 트랜잭션·동시성·레이스 컨디션·레거시 결합 제어가 필요한 고난도 단계는 `Opus (opus-required)` 로 명시합니다. 구현 시 `/planner-execute` 가 이 표를 기준으로 실행 모델 가드레일을 적용합니다.
  - 서로 의존하지 않는 모듈이 여럿이면 계약과 조립 사이를 **병렬 그룹**(`2-A`, `2-B`)으로 나눕니다. 그룹은 모듈 체인 단위로 나누고, 같은 그룹 단계끼리 §11 `단계` 컬럼의 파일이 겹치지 않게 하며, 공용 파일(DI 등록·배럴·공용 타입·마이그레이션)은 계약·조립 단계에 둡니다. 세부 규칙은 `output-guideline.md` §12 「병렬 그룹」 을 따릅니다.
- 요구사항이 설계에 빠짐없이 반영되도록 §2 매핑 표를 채웁니다.
- 명확한 흐름(처리 프로세스, 아키텍처 구조 등)이 도식화에 도움이 되는 경우, 도식화할 흐름과 첨부할 절만 정해 둡니다. 도식은 §9 확정 후 B-5에서 그립니다. (먼저 그리면 §9 결정에 따라 흐름이 바뀔 때 다시 그려야 합니다)

### 태스크 등록 인계 args (`/jissp-task-manager add` 호출 시 그대로 사용)

task-manager 가 관련 문서를 다시 추측하지 않도록, 이번 작업에서 **실제로 사용한 문서 경로**를 명시해 전달합니다. `[ ]` 부분만 실제 값으로 치환하고, 해당 문서가 없는 줄은 삭제합니다. (입력이 작업 프롬프트였다면 PRD 줄 대신 `작업 프롬프트` 줄을 남깁니다.)

# [작업 C] 기존 설계 문서 수정 (모드 args: `revise [설계 문서 경로] [변경 요청]`)

이미 작성된 설계 문서에 변경 요청을 반영합니다. **이 작업의 목적은 문서 전체 재작성을 피하는 것**입니다.

> ⚠️ **문서를 처음부터 다시 쓰지 마십시오.** 변경 요청이 닿는 절만 국소적으로 수정합니다. 전체 재작성은 수정 비용 폭증의 주범이며, 확정된 결정을 흔들어 재검토를 불필요하게 유발합니다.

## C-1. 입력 확인

- 설계 문서 경로가 없으면 사용자에게 요청합니다. (경로가 불명확하면 `[Jissp 문서]/[설계 문서]` 에서 후보를 탐색해 확인합니다.)
- 변경 요청 내용이 없으면 무엇을 바꿔야 하는지 사용자에게 확인합니다.
- 대상 문서를 읽어 **Part A/Part B 구조를 갖춘 v2 문서인지** 확인합니다.
  - **구 양식(Part 구분이 없는 문서)인 경우**: 사용자에게 알리고 두 선택지를 제시합니다 — ① 해당 절만 국소 수정(구조 유지), ② v2 양식으로 재구성(§11의 코드 스니펫을 계약과 요지로 분리). 사용자 선택 없이 임의로 재구성하지 마십시오.

## C-2. 변경 요청의 영향 판정 (⚠️ 핵심 단계)

변경 요청이 어디에 닿는지 먼저 판정합니다.

| 판정 | 해당하는 변경 | 처리 |
| --- | --- | --- |
| **Part A 영향** | 스키마·API·시그니처·타입·페이로드·설정 키 변경, 모듈 경계·의존 방향 변경, 아키텍처 결정 번복, 요구사항 추가/삭제 | C-3 |
| **Part B 영향** | 파일 분할/이동, 파일명·클래스명 조정, 작업 순서 변경 등 **계약이 그대로인 변경** | C-4 |
| **둘 다** | 계약이 바뀌면서 파일 구성도 달라짐 | C-3 → C-4 |

- 판정이 모호하면 **"이 변경이 다른 모듈·시스템과의 합의를 바꾸는가?"** 로 판별합니다. 바꾼다면 Part A, 아니면 Part B입니다.
- 판정 결과를 사용자에게 한 줄로 알린 뒤 진행합니다.

## C-3. Part A 수정

- **변경 요청이 닿는 절만** 수정합니다. 관련 없는 절은 손대지 않습니다.
- 계약(§4·§5)이 바뀌면 그 파급을 함께 갱신합니다: §2 요구사항 매핑, §6 처리 흐름, §7 영향 범위 중 **실제로 영향받는 항목만**.
- 결정이 번복된 경우 §3의 결정을 **새 결정으로 교체**합니다. 이전 안은 설계 근거로 의미가 있을 때만 `버린 대안` 과 그 이유로 남기고, "사용자 요청으로 변경" 같은 경위는 본문에 쓰지 않습니다. 변경 경위는 C-5의 `개정 이력` 에만 기록합니다. (태스크 모드면 태스크 README "작업 이력"에도 남습니다)
- **§11(Part B)은 이 단계에서 갱신하지 않습니다.** 대신 영향받는 행의 `변경 요지` 앞에 `[재작성 필요]` 를 표기만 합니다. 실제 갱신은 구현 착수 시점에 실행자가 실제 코드를 보고 판단합니다.
- 새로 생긴 판단 필요 사항은 §9에 추가합니다.
- **수정 후 B-4의 Part A 체크리스트(1~8)를 수정된 절에 한해 재적용**합니다. (문서 전체를 재검토하지 않습니다.)

## C-4. Part B 수정

- 해당 표의 **행 단위로만** 수정합니다.
- **재검토를 수행하지 않습니다.** Part B는 확정 대상이 아니므로 검토 사이클을 돌리지 않습니다.
- Part B만 바뀐 경우 `/jissp-planner review`·`/jissp-architecture-preview` 재호출을 권하지 않습니다.
