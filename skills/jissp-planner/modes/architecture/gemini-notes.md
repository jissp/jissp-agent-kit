# Gemini 모델 전용 주의사항 — architecture 모드

`modes/architecture/guide.md` 와 함께 반드시 숙지하고 적용합니다.

- 사용자가 참조하라고 전달한 문서(가이드라인, README 등)가 있다면, 결과를 요약할 때 해당 문서의 '출처 경로(링크)'를 임의로 생략하지 말고 최종 문서에 반드시 명시적으로 기록할 것.
- **[B-2] 단계를 절대 생략하지 말 것.** PRD·가이드라인 문서만 읽고 실제 코드 분석 없이 설계 문서를 작성하면 안 됩니다. 반드시 작업 대상과 연관 레퍼런스 모듈·로직의 실제 코드를 `Grep`/`Glob`/`Read` 로 확인한 뒤, 그 근거를 바탕으로 설계 문서를 작성하십시오.
- **Rule/GuideLine 문서의 모든 규칙 항목을 하나씩 대조하며 반드시 설계에 반영할 것.** 추론 특성상 규칙을 누락하거나 임의로 요약·생략하기 쉬우므로, 각 규칙 항목을 명시적으로 점검하고 설계 문서에 그 적용 근거를 남길 것.
- 🚨 **상세화의 대상은 '계약'이지 '구현'이 아닙니다.** §4·§5(데이터 모델·인터페이스 계약)는 `(미정)`·`// TODO`·`// 알아서 매핑` 같은 Placeholder 없이 **타입·필드·시그니처 수준까지 완전하게** 확정하십시오. 계약을 모호하게 남기고 판단을 구현자에게 떠넘기는 것은 실패한 설계입니다.
  - 🚨 **반대로 §11(변경 대상 파일)에는 함수 본문·제어 흐름·import·DI 배선·쿼리 구현체를 절대 쓰지 마십시오.** 각 파일은 "무엇을 하는지" 1~2문장 요지와 `준수할 계약` 참조로만 기술합니다. 완전한 코드를 적어 넣는 것은 v2에서 **명시적으로 금지**된 행위입니다.
  - 두 지시는 충돌하지 않습니다: **계약은 100% 확정, 구현은 0% 작성**입니다.
- **계약 우선 순차 분석**: 여러 파일을 뭉뚱그려 설명하지 말고, 계약이 정해지는 순서대로(예: 1. DB 스키마 → 2. 공용 타입/DTO → 3. 모듈 공개 인터페이스 → 4. API 엔드포인트) 짚어가며 §4·§5를 확정한 뒤, 그 계약을 소비하는 파일들을 §11에 나열하십시오.
