# Output Format: 설계 문서 템플릿

## 0. 근본 원칙 — 계약(Contract)과 구현(Implementation)의 분리

설계 문서에는 성격이 완전히 다른 두 가지가 들어간다. 이 둘을 섞으면 문서가 "복붙용 코드 저장소"로 변질되고, 코드 한 줄이 바뀔 때마다 문서 전체 정합성을 맞추는 비용이 폭증한다. **v2는 이 둘을 물리적으로 분리한다.**

| | **Part A — 설계 결정** (§1~§9) | **Part B — 구현 지시** (§11~§12) |
| --- | --- | --- |
| 성격 | 합의·확정의 대상 (계약) | 실행 참고 자료 |
| 수명 | 코드보다 오래 산다 | 구현 착수 순간 코드가 진실이 된다 |
| 변경 시 | **재검토 필요** (`/jissp-planner review`·`jissp-architecture-preview` 대상) | 재검토 불필요 |
| 갱신 의무 | 있음 (문서가 진실) | **없음** (코드가 진실) |

> ⚠️ **Part B는 갱신하지 않아도 된다.** 구현 과정에서 파일이 갈라지거나 함수명이 바뀌어도 Part B를 따라가며 고칠 필요가 없다. 지켜야 하는 것은 Part A의 계약뿐이다. 이 정책을 문서 상단 배너에 반드시 명시한다.

### 코드를 문서에 쓸 것인가 — 판별 기준 단 하나

> **한 파일 안에서 닫히는 것은 쓰지 않는다. 둘 이상의 파일·모듈·시스템·사람이 합의해야 하는 것만 쓴다.**

**✅ 코드로 쓴다 (계약 — Part A에 배치)**

- 함수·메서드 **시그니처** (이름, 파라미터 타입, 반환 타입 — **본문 없이**)
- 타입·인터페이스·DTO·엔티티 정의
- DB DDL, 마이그레이션 SQL, 인덱스 정의
- API 엔드포인트, 요청/응답 스키마, 상태 코드, 에러 코드
- 이벤트·큐·잡(Job) 페이로드 스키마
- 설정 키·환경변수의 이름·타입·기본값
- 외부에 노출되거나 저장소에 남는 enum **값** (큐 이름, 상태 문자열 등)

**❌ 코드로 쓰지 않는다 (구현 — 문서에서 제외)**

- 함수 **본문** — 제어 흐름(`if`/`for`/`try`), 분기 조건, 변수 매핑
- 에러 핸들링·Fallback 세부 구현
- `import` 구문, DI 배선 코드, 모듈 등록 보일러플레이트
- ORM·쿼리 구현체 (Prisma/TypeORM 호출 등)
- 로깅 문장, 방어 코드

> **왜 빼는가**: 구현 착수 시점에 실행자는 어차피 실제 코드를 다시 읽는다. 그때 문서의 본문 스니펫은 이미 낡아 있을 가능성이 높고, **낡은 스니펫은 없는 것보다 나쁘다**(잘못된 확신을 준다). 계약만 고정하면 실행자는 계약을 지키면서 현재 코드에 맞는 구현을 한다.

**예외 — 틀리면 설계가 틀리는 흐름**

순서가 깨지기 쉬운 처리, 트랜잭션 경계, 동시성·멱등성 처리처럼 **구현자의 재량에 맡기면 설계 의도가 깨지는 것**은 실제 코드가 아니라 **§6 처리 흐름에 3~5줄 의사코드(pseudo-code)** 로 서술한다. 언어 문법에 얽매인 코드로 쓰지 않는다.

### 금지 사항

- ❌ 파일 하나를 통째로 재현하는 스니펫 (구현자가 복사하도록 유도한다)
- ❌ 스니펫 안의 설계 근거 주석 — "왜 이렇게 바꾸는가"는 스니펫 **바깥 본문**에 쓴다. 주석으로 넣으면 구현자가 최종 코드의 일부로 오해해 그대로 옮기고, 기획·트레이드오프 설명이 코드에 눌러앉아 낡은 주석으로 남는다.
- ❌ 스니펫의 클래스·인터페이스 선언에 붙인 역할 요약 주석 (`/** 공용 공휴일 조회 코어 서비스 ... */`) — 역할·구조 설명은 문서 본문에 쓰고, 코드에서는 모듈 `README.md` 가 담당한다.
- ❌ "추가 조사 없이 그대로 구현 가능한 완전한 코드"를 목표로 삼는 것. 이 목표가 문서를 코드 저장소로 만든다. **목표는 "계약을 어기지 않고 구현할 수 있는 상태"**다.

## 파일명 규칙

- 저장 위치: `[Jissp 문서]/[설계 문서]`
  - 태스크 모드(`--task`)면 이 규칙 대신 SKILL.md "태스크 모드"의 저장 위치·파일명(`[태스크 디렉토리]/architecture.md`)을 따릅니다.
- 파일명: `[파일명 규칙]` 을 따르며, 문서 유형은 `architecture` 입니다.
  - `[feature]` 는 PRD 문서명이나 핵심 기능명에서 도출합니다.
  - 예) `20260923_150312_export-csv-architecture.md` (기본 파일명 규칙 기준)

## 문서 양식

문서 최상단에는 반드시 아래 **문서 계약 배너**를 그대로 포함합니다.

```markdown
> **문서 계약**
> - **§1~§9 (Part A) = 확정 대상.** 이 절들이 이 문서의 본체이며, 변경 시 재검토가 필요합니다.
> - **§11~§12 (Part B) = 실행 참고.** 구현 착수 이후에는 코드가 진실이며, 이 절들을 코드에 맞춰 갱신할 의무는 없습니다.
> - 구현이 지켜야 하는 것은 Part A의 계약(§4·§5)이며, Part B의 파일 목록이 아닙니다.
```

# Part A — 설계 결정 (확정 대상)

### 1. 개요
- 목적, 해결하려는 문제, 핵심 가치 제안
- 참조한 PRD 문서 경로, 구조 문서 경로(인계받은 경우) 및 참조한 Rule/GuideLine 문서 경로 명시
- **설계 범위(In Scope) / 범위 밖(Out of Scope)** 을 명시하여 경계를 확정

### 2. 요구사항 매핑
- PRD의 기능적/비기능적 요구사항을 우선순위(P0/P1/P2)별로 정리
- 각 요구사항이 아래 설계의 어느 절에서 충족되는지 매핑 (요구사항 누락 방지)

| ID | 우선순위 | 요구사항 | 충족 위치 |
| --- | --- | --- | --- |
| R1 | P0 | ... | §3.2, §5.1 |

### 3. 시스템 아키텍처
- 전체 구조 (레이어/모듈/컴포넌트 구성 및 **경계**)
- **의존 방향**: 어떤 모듈이 어떤 모듈을 참조해도 되는지/안 되는지
- 기술 스택 선정 및 그 근거 (Rule 문서의 스택 우선)
- **주요 아키텍처 결정과 트레이드오프**: 채택안 / 검토 후 버린 대안 / 버린 이유. 이 절이 Part A에서 가장 오래 살아남는 내용이다.
- 구조가 복잡하면 `/flow-diagram` 스킬로 도식화하여 첨부
- **마지막 하위 절로 `모듈 단위와 테스트 경계` 를 반드시 둔다.** (하위 절 번호는 문서에 맞게 부여 — 예: `3.5`)

#### §3 필수 하위 절 — 모듈 단위와 테스트 경계

> **계약(§4·§5)이 "무엇을 지킬지"를 고정한다면, 이 절은 "무엇을 어떤 단위로 떼어 둘지"를 고정한다.** 이 절이 비면 구현이 조회·판단·저장을 한 덩어리로 작성해도 설계 위반으로 판정할 근거가 없다.

이번 설계가 신설·변경하는 모듈마다 한 행을 채운다.

| 모듈 | 책임 (한 문장) | 테스트 분류 | 대체 지점(seam) |
| --- | --- | --- | --- |
| `domain/xxx-policy` | ...를 판단한다 | `Unit-순수` | — |
| `application/xxx-service` | ...흐름을 조립한다 | `Unit-주입` | `XxxRepository`, `Clock` |
| `infra/xxx.repository` | DB 접근만 담당한다 | `Integration` | — |
| `api/xxx.controller` | 요청을 서비스에 위임한다 | `조립` | — |

**테스트 분류**

| 분류 | 의미 |
| --- | --- |
| `Unit-순수` | I/O 없는 계산·판단·변환 로직. 입력/출력만으로 검증 가능 |
| `Unit-주입` | 협력 객체를 주입받아 동작. fake·stub으로 대체해 검증 |
| `Integration` | DB·외부 API 등과 맞닿는 adapter. 로직 없이 **얇게** 유지 |
| `조립` | 진입점·DI 등록·라우팅. 로직이 없어야 함 |

작성 규칙:

- **책임이 한 문장으로 안 써지면**("그리고", "및", "~도 한다"가 들어가면) 모듈을 나눈다.
- **`Integration`·`조립` 행에 분기·계산 로직을 두지 않는다.** 그 로직은 `Unit-*` 모듈로 내린다.
- **seam**: 부수효과(DB·캐시·큐, 외부 API, 파일 시스템, 현재 시각·랜덤, 환경변수)를 주입받는 지점을 적는다. 외부 의존과 맞닿는 곳에만 둔다.
- ⚠️ **과잉 분리 금지**: pass-through 레이어, 파일당 함수 1개, 구현이 하나뿐인데 두는 인터페이스는 만들지 않는다. 판단 기준은 **"독립적으로 테스트할 가치가 있는가 / 독립적으로 바뀔 이유가 있는가"** 이며, 둘 다 아니면 합친다.
- 여기서 정하는 것은 **단위와 경계까지**다. 시그니처는 §5에서 확정한다.
- 구조 문서(`*-structure.md`)가 함께 전달된 경우, **그 문서의 §4(모듈 책임)·§6(테스트 경계)을 이 표로 옮기고 새로 설계하지 않는다.**

### 4. 데이터 모델 (계약)
- 핵심 엔티티 정의: 필드, 타입, PK/FK, 인덱스, 제약조건
- 엔티티 간 관계 (1:N, N:M)
- **DDL·마이그레이션 SQL은 여기에 코드로 명시한다** — 스키마는 여러 코드가 합의하는 계약이므로 문서에 남을 가치가 있다.
- **모호함 없는 제약 확정**: Null 허용 여부, 기본값, 유니크 제약, 외래키 동작 등 데이터 제약을 생략 없이 구체적으로 기재합니다.

### 5. 인터페이스 계약
> **이 절과 §4가 구현이 반드시 지켜야 하는 고정점이다.** Part B의 파일 목록이 낡아도 이 절은 유효해야 한다.

각 항목을 코드 블록으로 명시하되 **시그니처·스키마까지만** 쓰고 본문은 쓰지 않는다.
**구현자가 추측하지 않도록 타입·시그니처 수준까지 모호함 없이 확정**합니다. (`any`, `object`, 생략 표기 `...` 지양)

- **5.1 API 엔드포인트**: 메서드, 경로, 요청/응답 스키마, 상태 코드, 에러 규약
- **5.2 모듈 공개 인터페이스**: 다른 모듈이 호출하는 클래스·함수의 완전한 시그니처 (파라미터 타입, 반환 타입, 커스텀 예외)
- **5.3 타입·DTO 정의**: 모듈 경계를 넘나드는 타입 및 필드별 구체적 타입/선택적(Optional) 여부
- **5.4 이벤트·큐 페이로드**: 잡 이름(문자열 값 포함), 페이로드 스키마
- **5.5 설정·환경변수**: 키 이름, 타입, 기본값, 필수 여부

```ts
// 시그니처만. 본문(구현)은 쓰지 않는다.
class CapturePlaceInfoQueueService {
  enqueue(payload: CapturePlaceInfoJobPayload): Promise<void>;
}
```

### 6. 처리 흐름 (Flow)
- 주요 시나리오별 단계적 처리 흐름 (자연어 서술 우선)
- 복잡한 흐름은 `/flow-diagram` 스킬로 도식화하여 첨부
- **틀리면 설계가 틀리는 흐름**(트랜잭션 경계, 처리 순서 의존, 동시성·멱등성, 실패 시 복구)은 **반드시 3~5줄 의사코드(pseudo-code)** 로 명시합니다. 실제 언어 코드로 쓰지 않습니다.
  - 트랜잭션의 시작·커밋·롤백 범위와 외부 I/O 분리 경계
  - 동시 요청 방지를 위한 락(분산/DB 락) 획득·해제 순서 및 멱등키 검증 지점
  - 여러 작업의 실행 순서가 강제되는 지점 (예: 외부 결제 승인 후 DB 최종 커밋)

### 7. 영향 범위 및 마이그레이션
- §3~§6의 결정이 파급되는 범위: 호출부/피호출부, 의존 모듈, 공용 타입·인터페이스, 설정/환경변수, DB 스키마, 테스트
- 하위호환/breaking change 여부와 대응 방안
- 배포 시 주의점: 데이터 마이그레이션 순서, 롤백 전략, 무중단 배포 시 구/신 버전 공존 구간
- 함께 수정해야 하는 외부 연동(다른 서비스·확장 프로그램·클라이언트 등)

### 8. 비기능 설계
- 보안(인증/인가, 민감정보), 성능, 확장성, 로깅/모니터링, 장애 대응
- Rule 문서의 비기능 기준을 충족하는 방식으로 기술

### 9. 미결정 / 확인 필요 사항
- `(미정)` 항목 및 **사용자 판단이 필요한 결정 사항** 목록
- 각 항목에 권장안과 그 근거, 선택 시 파급 효과를 함께 기재

| ID | 항목 | 권장안 / 대안 | 확인 필요 사유 |
| --- | --- | --- | --- |
| D1 | ... | ... | ... |

> §10 은 비워 둡니다. (이전 양식의 성공 조건 절 — 기존 설계 문서와 §11·§12 번호를 맞추기 위해 번호를 당기지 않습니다)

# Part B — 구현 지시 (실행 참고 / 비확정)

> 아래 절들은 **착수 시점의 스냅샷**입니다. 구현 과정에서 실제 파일 구성이 달라져도 갱신하지 않아도 되며, 실행자가 반드시 지켜야 하는 것은 Part A의 계약입니다.

### 11. 변경 대상 파일
- B-2 코드 분석에서 식별한 신규(New)/수정(Modify)/삭제(Delete) 대상 파일 목록
- **각 행은 "무엇을 하는지" 한두 문장으로 요지만 적는다.** 함수 본문이나 완성된 코드를 붙이지 않는다.
- **`준수할 계약` 컬럼이 이 표의 핵심**이다. 이 컬럼이 Part B를 Part A에 묶어, 파일 목록이 낡아도 지켜야 할 것은 남는다.

| 구분 | 파일 경로 | 변경 요지 | 준수할 계약 | 테스트 분류 | 단계 | 요구사항 |
| --- | --- | --- | --- | --- | --- | --- |
| New | `path/to/new.ts` | 추가할 클래스와 그 책임 (1~2문장) | §5.2 `XxxService` | `Unit-주입` | 2-A | R2 |
| Modify | `path/to/existing.ts` | 바꿀 지점과 방향 (1~2문장) | §4 `xxx` 테이블 | `Integration` | 2-B | R3 |
| Delete | `path/to/legacy.ts` | 제거 사유와 대체 지점 | §5.2 | — | 3 | R4 |

- **`테스트 분류` 컬럼은 §3 『모듈 단위와 테스트 경계』 표의 분류를 그대로 옮겨 적는다.** 그 표에 없는 모듈이 여기 등장하면, 파일 목록을 늘리지 말고 **§3부터 채운다.** (삭제 대상·타입 정의 전용 파일은 `—`)
- **`단계` 컬럼은 이 파일을 작성하는 §12 단계의 `순서` 값이다.** (위 예시 값은 §12 「병렬 그룹」 예시 기준) 파일 하나는 단계 하나에만 속하며, 병렬 그룹을 동시에 실행할 때의 파일 소유권은 이 컬럼으로 정해진다.
- 리네이밍이 다수 발생하면 AS-IS / TO-BE 대응표를 별도로 둔다.

### 12. 작업 순서
- **기본 방향은 하위 단위 → 조립**이다. §3 『모듈 단위와 테스트 경계』 표의 테스트 분류 순서대로 단계를 나누고, 각 단계에 해당 모듈을 배치한다.

| 순서 | 단계 | 대상 | 선행 | 수용 기준 (완료 판정 검증) | 실행 모델 (난이도) |
| --- | --- | --- | --- | --- | --- |
| 1 | 계약 | §4 스키마·마이그레이션, §5 타입·DTO·시그니처 | — | 컴파일 및 타입 검사 통과, 마이그레이션 정상 실행 | `Sonnet` |
| 2 | `Unit-순수` | I/O 없는 판단·계산·변환 로직 | 1 | 엣지 케이스 포함 단위 계산 검증 통과 | `Sonnet` |
| 3 | `Unit-주입` | 비즈니스 흐름 서비스. seam은 계약(인터페이스)만 있으면 fake로 대체되므로 `Integration` 보다 먼저 착수한다 | 2 | 목/스텁 기반 비즈니스 시나리오 정상 흐름 검증 | `Sonnet` |
| 4 | `Integration` | DB·외부 API adapter | 3 | 실제 DB 쿼리/외부 호출 연결 동작 검증 | `Sonnet` |
| 5 | `조립` | 진입점·DI 등록·라우팅 | 4 | 엔드포인트 호출 및 라우팅/조립 정상 동작 | `Sonnet` |

- **`선행` 컬럼**: 이 단계를 착수하기 전에 끝나 있어야 하는 단계의 `순서` 값을 적는다. (없으면 `—`)

- **`수용 기준 (완료 판정 검증)` 작성 규칙**:
  - 각 단계가 끝났을 때 구현자가 무엇으로 완료를 검증할지(타입 체크 통과, 특정 시나리오 단위 검증, 빌드 통과 등) 명확한 기준 1문장을 기술합니다.
- **`실행 모델 (난이도)` 작성 규칙**:
  - **기본값은 `Sonnet`** 입니다. 명확한 계약과 단위 규약이 있으므로 대부분의 단계는 Sonnet으로 충분합니다.
  - **`Opus (opus-required)` 지정 기준**: 아래 항목 중 하나라도 해당하여 고도의 추론과 복잡한 상황 판단이 필수적인 경우에만 지정합니다.
    1. 복잡한 트랜잭션 롤백 및 보상 트랜잭션, 분산 락, 동시성/레이스 컨디션 제어가 핵심인 단위
    2. 기존 레거시 코드베이스의 암묵적 불변식이나 강한 결합을 깨뜨리지 않고 조심스럽게 리팩토링/배선해야 하는 단위
    3. 장애 시나리오별 복잡한 Fallback 및 정밀한 예외 복구 분기
- 해당 모듈이 없는 단계는 생략한다.
- 이 방향을 벗어나야 하면(예: 기존 adapter 시그니처 변경이 선행되어야 하는 경우) 해당 단계에 이유를 한 줄 병기한다.
- 순서를 지켜야 하는 이유(컴파일 의존, 데이터 정합성 등)를 한 줄로 병기
- 중간 검증 가능 지점(여기까지 하면 무엇이 동작하는가)이 있으면 표시

#### 병렬 그룹 (선택)

서로 의존하지 않는 모듈이 여럿이면, 계약과 조립 사이의 단계를 **병렬 그룹**으로 묶어 동시에 착수할 수 있게 한다. `순서` 의 숫자가 같고 접미사만 다른 단계(`2-A`, `2-B`)가 한 그룹이다.

| 순서 | 단계 | 대상 | 선행 | 수용 기준 (완료 판정 검증) | 실행 모델 (난이도) |
| --- | --- | --- | --- | --- | --- |
| 1 | 계약 | §4 스키마, §5 타입·시그니처, 공용 타입·DI 토큰 | — | 컴파일 및 타입 검사 통과 | `Sonnet` |
| 2-A | 모듈 X | `Unit-순수` → `Unit-주입` (`XxxCalculator`, `XxxService`) | 1 | 목/스텁 기반 X 시나리오 검증 | `Sonnet` |
| 2-B | 모듈 Y | `Integration` (`YyyRepository`) | 1 | 실제 DB 쿼리 동작 검증 | `Sonnet` |
| 3 | 조립 | 진입점·DI 등록·라우팅 | 2-A, 2-B | 엔드포인트 호출 및 조립 정상 동작 | `Sonnet` |

- **그룹은 모듈 체인 단위로 나눈다.** 테스트 분류(계층)로 나누지 않는다. 각 그룹 단계 안에서는 위 기본 방향(`Unit-순수` → `Unit-주입` → `Integration`)을 그대로 따른다.
- **같은 그룹의 단계끼리는 서로를 `선행` 으로 두지 않고, §11 `단계` 컬럼의 파일이 겹치지 않아야 한다.** 한 단계가 다른 단계의 구현체를 직접 호출해야 하면 같은 그룹에 둘 수 없다. (계약(인터페이스)만 쓰는 것은 의존이 아니다.)
- **여러 모듈이 함께 건드리는 공용 파일**(DI 등록, 배럴(index) 파일, 공용 타입·상수, 마이그레이션)은 그룹 단계에 넣지 않고 계약 단계나 조립 단계에 둔다.
- **그룹을 나누는 조건**: 독립 모듈이 2개 이상이고 각 단계에 실질적인 구현 분량이 있을 때만 나눈다. 한쪽이 파일 1~2개 수준이면 나누지 않고 기본 순서로 쓴다.
- 그룹을 나눴으면 표 아래에 **나눈 근거**(무엇이 왜 독립인지)를 한 줄 병기한다.
