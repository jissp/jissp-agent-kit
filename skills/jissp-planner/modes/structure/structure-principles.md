# 구조 설계 원칙: 테스트하기 쉬운 구조

본 문서는 `jissp-planner` structure 모드가 디렉토리·모듈 구조를 설계할 때 적용하는 **판단 기준**입니다.

## 0. 이 원칙의 관점

- 목표는 **테스트를 먼저 작성하는 것(Test-First)이 아닙니다.** **unit 단위로 떼어 테스트할 수 있는 구조**를 먼저 잡는 것입니다.
- "테스트하기 쉽다"는 곧 **책임이 작고 분명하며, 의존이 적고 교체 가능하다**는 뜻입니다. 이는 재사용성·가독성·변경 용이성과 같은 방향을 가리킵니다.
- 모든 판단의 최종 질문은 하나입니다.

> **이 단위를 다른 모듈을 띄우지 않고, 입력만 주어 검증할 수 있는가?**

---

## 1. 단일 책임과 응집도

- 각 모듈(디렉토리·파일)은 **책임을 한 문장으로 설명할 수 있어야** 합니다. 설명에 "그리고", "및", "~도 한다"가 들어가면 분리 후보입니다.
- **함께 바뀌는 것은 함께 둡니다.** 같은 이유로 수정되는 코드가 여러 디렉토리에 흩어져 있다면 응집도가 낮은 구조입니다.
- 기술 계층(controller/service/repository)만으로 나누기보다, 규모가 있는 기능은 **기능(도메인) 단위로 먼저 묶고 그 안에서 계층을 나누는 것**을 우선 검토합니다. (단, 프로젝트 컨벤션이 계층 우선이면 아래 「기존 코드베이스 컨벤션과의 관계」에 따라 수용을 검토)

## 2. 순수 로직과 부수효과의 분리 (⭐ 핵심)

- **계산·판단·변환·검증 로직**은 I/O 없이 "입력 → 출력"으로 실행되는 단위로 분리합니다. 이 단위가 unit 테스트의 주 대상입니다.
- 아래 **부수효과**는 경계 모듈(adapter)로 격리하고, 핵심 로직이 직접 호출하지 않게 합니다.
  - DB·캐시·큐 접근
  - 외부 API·SDK 호출
  - 파일 시스템
  - 현재 시각·랜덤·UUID 생성
  - 환경변수·전역 설정 직접 참조
- 격리의 판단 기준: **핵심 로직을 테스트할 때 DB/네트워크/시계를 준비해야 한다면 분리가 덜 된 것**입니다.

## 3. 교체 가능한 경계 (Seam)

- 부수효과 모듈은 **호출하는 쪽에서 주입받을 수 있는 형태**로 둡니다. 테스트에서 fake·stub·in-memory 구현으로 대체할 수 있는 지점이 곧 seam입니다.
- 구조 문서에는 **"무엇을 어디서 대체할 수 있는가"** 만 적습니다. 인터페이스 시그니처는 architecture 모드에서 확정합니다.
- ⚠️ **과잉 추상화 금지**: 구현이 하나뿐이고 테스트에서 대체할 필요도 없는 대상에 인터페이스 계층을 추가하지 않습니다. seam은 **외부 의존과 맞닿는 곳**에만 둡니다.

## 4. 오케스트레이션과 로직의 분리 (스파게티 방지)

- 진입점(controller·handler·job·CLI command·페이지 컴포넌트 등)은 **흐름을 조립만** 합니다. 분기·계산·변환은 하위 단위로 내립니다.
- 하나의 단위가 **"조회 → 판단 → 변환 → 저장 → 알림"** 을 모두 수행하면 분리 대상입니다. 조립하는 단위와 판단하는 단위를 나눕니다.
- 조립 단위는 로직이 없으므로 테스트 비용이 작고, 판단 단위는 I/O가 없으므로 unit 테스트가 쉬워집니다.

## 5. 낮은 결합도와 의존 방향

- 의존은 **변경이 잦은 쪽 → 안정적인 쪽**으로 흐릅니다. 일반적으로 `진입점 → 조립(application) → 도메인 로직` 방향이며, `adapter(I/O)` 는 도메인 로직이 요구하는 역할을 구현하는 쪽에 둡니다.
- 아래 의존은 **금지**합니다.
  - 순환 의존 (A → B → A, 디렉토리 단위 포함)
  - 하위 모듈이 상위 진입점을 참조
  - 공용(shared·common) 모듈이 특정 기능 모듈을 참조
  - 도메인 로직이 특정 프레임워크·SDK 타입에 직접 의존 (프로젝트 컨벤션상 불가피한 경우는 구조 문서 §6 미결정 사항에 올려 확정)
- 모듈 간 참조는 **각 모듈이 외부에 노출하는 단위**를 통해서만 합니다. 다른 모듈의 내부 파일을 직접 참조하는 구조를 만들지 않습니다.

## 6. 재사용 — 필요할 때만 공용화

- **2곳 이상에서 실제로 쓰이는 로직만** 공용 모듈로 승격합니다. "나중에 쓸 것 같아서" 만드는 추측성 공용화는 하지 않습니다.
- 기존 코드베이스에 이미 같은 역할의 유틸·모듈이 있으면 **새로 만들지 않고 재사용**합니다. (코드 분석 단계에서 반드시 확인)

## 7. 과잉 분리 금지

아래는 테스트 용이성을 명분으로 흔히 발생하는 과잉 설계입니다. 발견하면 합칩니다.

- 파일 하나에 함수 하나씩 기계적으로 쪼개기
- 한 곳에서만 쓰이는 몇 줄짜리 로직을 별도 모듈로 분리
- 아무 일도 하지 않고 호출만 전달하는 레이어(pass-through)
- 구현이 하나뿐인데 인터페이스·팩토리·추상 클래스를 겹겹이 두는 구조
- 디렉토리 깊이만 늘리는 중첩 (내용물이 파일 1개인 디렉토리가 연쇄되는 경우)

판단 기준: **분리한 단위가 독립적으로 테스트할 가치가 있는가? 독립적으로 바뀔 이유가 있는가?** 둘 다 아니면 분리하지 않습니다.

## 테스트 분류

구조 문서의 각 모듈에는 아래 분류 중 하나를 부여합니다. (상수·타입 정의 전용 파일은 제외) 분류가 곧 **그 모듈을 어떻게 테스트할지**를 결정합니다.

| 분류 | 의미 | 테스트 방식 |
| --- | --- | --- |
| `Unit-순수` | I/O 없는 계산·판단·변환 로직 | mock 없이 입력/출력으로 검증 |
| `Unit-주입` | 협력 객체(주로 adapter)를 주입받아 동작 | 협력 객체를 fake·stub으로 대체해 검증 |
| `Integration` | DB·외부 API 등과 맞닿는 adapter | unit 대상이 아님. 로직 없이 **얇게** 유지하고 통합 테스트로 검증 |
| `조립` | 진입점·DI 등록·라우팅 | 로직이 없어야 함. 테스트 최소화 (E2E·통합에서 간접 검증) |

- `Integration` · `조립` 모듈에 분기·계산 로직이 들어가 있다면 구조가 잘못된 것입니다. 해당 로직을 `Unit-*` 모듈로 내립니다.
- 핵심 요구사항을 담당하는 로직은 가능한 한 `Unit-순수` 로 두는 것을 우선합니다.

## 기존 코드베이스 컨벤션과의 관계

- **기본 구조는 본 문서의 원칙을 기준으로 설계**합니다.
- 단, 기존 코드베이스 컨벤션(Rule 문서·실제 코드의 디렉토리 구성·네이밍·계층 방식)이 있으면 **최대한 수용**합니다. 원칙을 만족하는 방법이 여럿이면 컨벤션에 맞는 쪽을 고릅니다.
- 컨벤션과 원칙이 정면으로 충돌하면 조용히 한쪽을 고르지 않습니다. **원칙을 우선한 항목**은 근거 위치·사유와 함께 구조 문서의 `미결정 / 확인 필요 사항` 에 올려 사용자 확정을 받습니다. 수용한 컨벤션은 따로 기록하지 않습니다.
