# Output Format: 구조 문서 템플릿

## 0. 구조 문서가 다루는 범위

구조 문서는 **"무엇을 어디에 두고, 누가 누구를 참조하며, 각 단위를 어떻게 떼어 테스트하는가"** 를 **대략적으로** 확정합니다. 디렉토리 구조와 흐름을 한눈에 파악하는 것이 목적이며, 세부 동작과 계약(시그니처·스키마)은 이후 architecture 모드의 설계 문서에서 이 구조를 제약으로 삼아 확정합니다.

| | structure 모드 (구조 문서) | architecture 모드 (설계 문서) |
| --- | --- | --- |
| 확정 대상 | 디렉토리 트리, 모듈 역할, 의존 방향, 대략적 흐름, seam | 데이터 모델, 인터페이스 계약, 처리 흐름, 영향 범위 |
| 이름 수준 | 모듈·노출 단위의 **이름과 역할 한 줄** | 시그니처·타입 필드·스키마 |
| 흐름 수준 | 모듈 단위 화살표 (`handler → queue → processor`) | 단계별 처리 순서·분기·실패 처리 |

**✅ 쓴다**

- 디렉토리·파일 트리 (신규/수정/이동/삭제 표시, 역할 한 줄, 테스트 분류)
- 의존 방향과 금지 의존
- 모듈 단위의 대략적 흐름 (몇 줄)
- seam (외부 의존을 어디서 대체하는가)
- 주요 구조 결정과 버린 대안

**❌ 쓰지 않는다**

- 함수·메서드 시그니처, 파라미터·반환 타입
- 타입·DTO 필드, DB DDL, API 요청/응답 스키마, 설정 키
- 함수 본문, 의사코드, **라이브러리·메서드 호출 수준의 처리 순서**, 단계별 분기·실패 처리 흐름
- 동작 규칙 (에러 문구 책임, 실패 전파 방식, 값 전달 방식 등 — architecture 모드의 몫)
- 요구사항 → 모듈 매핑표, 테스트 검증 포인트·테스트 케이스, 컨벤션 대조표
- 구현 작업 순서

> **왜 빼는가**: 계약과 동작은 구조가 확정된 뒤에야 흔들림 없이 정할 수 있습니다. 구조 문서에 세부를 쓰기 시작하면 구조 합의와 계약 합의가 뒤섞이고, 구조를 바꿀 때마다 세부까지 다시 쓰게 됩니다. 확정 과정에서 동작에 관한 합의가 나오면 본문에 풀어 쓰지 말고 §1 `합의 사항` 에 한 줄로만 남겨 architecture 모드로 넘깁니다.

---

## 파일명 규칙

- 저장 위치: `[Jissp 문서]/[설계 문서]`
  - 태스크 모드(`--task`)면 이 규칙 대신 SKILL.md "태스크 모드"의 저장 위치·파일명(`[태스크 디렉토리]/module-structure.md`)을 따릅니다.
- 파일명: `[파일명 규칙]` 을 따르며, 문서 유형은 `structure` 입니다.
  - `[feature]` 는 PRD 문서명이나 핵심 기능명에서 도출합니다.
  - 예) `20260923_143000_export-csv-structure.md` (기본 파일명 규칙 기준)

## 문서 양식

문서 최상단에는 반드시 아래 **문서 성격 배너**를 그대로 포함합니다. `상태` 값은 사용자 확정 전에는 `초안`, 확정 후에는 `확정` 으로 둡니다.

```markdown
> **문서 성격: 구조 확정 문서**
> - 디렉토리·모듈 역할·의존 방향·대략적 흐름·테스트 seam을 확정합니다.
> - 계약(시그니처·스키마)과 세부 동작은 다루지 않으며, architecture 모드의 설계 문서가 이 구조를 제약으로 삼아 확정합니다.
> - **상태: 초안**
```

---

### 1. 개요
- 목적 (2~3줄)
- 입력: 참조한 PRD 문서 경로 또는 작업 프롬프트 요지, 참조한 Rule 문서 경로 (없으면 `없음`) — 한 줄씩
- 적용 유형: `신규 모듈` / `신규 기능` / `구조 변경 리팩토링` 중 해당 항목
- **범위(In Scope) / 범위 밖(Out of Scope)** — 항목당 한 줄. 선행 태스크·다른 작업에 맡기는 부분은 범위 밖에 한 번만 적습니다.
- **합의 사항** *(있는 경우에만)*: 요구사항 확인·확정 과정에서 사용자가 정한 동작·계약 관련 결정을 항목당 한 줄로 적습니다. 구조 문서는 이를 설계하지 않고 기록만 하며, architecture 모드가 계약으로 확정합니다. 작성자가 스스로 도출한 항목은 적지 않습니다.

### 2. 디렉토리 구조
- 코드 블록에 트리로 작성하고, 각 항목 끝에 **표시 + 역할 한 줄 + 테스트 분류**를 붙입니다.
- 표시: `[New]` 신규 / `[Modify]` 수정 / `[Move]` 이동(원래 경로 병기) / `[Delete]` 삭제 / 표시 없음 = 변경 없음(맥락 파악용)
- 역할은 **무엇을 맡는지 한 줄**입니다. 처리 순서(`A → B → C`)나 "그리고"가 들어가면 줄이거나 모듈 분리를 다시 검토합니다.
- 테스트 분류는 `modes/structure/structure-principles.md` 의 분류(`Unit-순수` / `Unit-주입` / `Integration` / `조립`)를 괄호로 붙입니다. 변경 없는 항목, 테스트 파일, 상수·타입 정의 전용 파일에는 붙이지 않습니다.
- 파일 단위까지 내려가되, 변경 없는 영역은 `...` 으로 생략합니다. 테스트 파일은 `tests/` 등 위치만 보이면 되며 개별 파일을 모두 나열하지 않아도 됩니다.
- **구조 변경 리팩토링**인 경우 `2.1 AS-IS` / `2.2 TO-BE` 두 트리로 나누고, 이동이 많으면 AS-IS → TO-BE 대응표를 추가합니다.

```text
src/
└── feature/pricing/
    ├── domain/
    │   ├── price-calculator.ts        [New]    할인 적용 후 최종 금액 계산 (Unit-순수)
    │   └── discount-policy.ts         [New]    할인 규칙 판정 (Unit-순수)
    ├── adapter/
    │   └── coupon-repository.ts       [New]    쿠폰 조회 (Integration)
    ├── pricing.service.ts             [New]    조회와 계산 조립 (Unit-주입)
    └── pricing.controller.ts          [Modify] 진입점, 서비스 호출로 교체 (조립)
```

### 3. 의존 방향과 흐름
- 모듈 간 의존을 ASCII 도식으로 표현합니다. 도식은 **모듈 단위**까지만 그리고, 메서드 호출·라이브러리 API는 적지 않습니다.
- 도식 아래에 **허용 규칙**과 **금지 규칙**을 목록으로 명시하고, 순환 의존이 없음을 한 줄로 기재합니다.
- 흐름이 의존 도식만으로 안 보이면(비동기 단계, 큐 등) **대략적 흐름**을 3~5줄로 덧붙입니다. 분기·실패 처리 흐름은 쓰지 않습니다.

```text
pricing.controller ──▶ pricing.service ──▶ domain/*
                               │
                               └──▶ adapter/coupon-repository
```

- 허용: `service → domain`, `service → adapter`
- 금지: `domain → adapter`, `domain → service`, `adapter → service`
- 순환 의존: 없음

### 4. 테스트 seam
- 외부 의존마다 **격리 지점과 대체 방법**을 한 줄씩 적습니다. 외부 의존이 없으면 `없음` 한 줄로 대체합니다.
- 테스트 파일 위치가 기존 컨벤션과 다르면 그 규칙을 한 줄 덧붙입니다. (같으면 쓰지 않습니다)

```text
- DB (쿠폰): adapter/coupon-repository.ts → in-memory fake, PricingService 생성 시 주입
- 현재 시각: shared/clock.ts → 고정 시각 stub, DiscountPolicy 생성 시 주입
```

### 5. 주요 구조 결정
- 파일·모듈의 **배치·분리·병합 결정**만 기록합니다. 과잉 분리를 피하려고 **일부러 합친 결정**도 여기에 남깁니다.
- 동작·계약에 관한 결정(실패 처리 방식, 값 전달 방식, 응답 문구 등)은 기록하지 않습니다.
- **5개 이내**로 유지합니다. 넘으면 트리만 봐도 자명한 결정부터 뺍니다.

| # | 결정 | 채택안 | 버린 대안 | 이유 |
| --- | --- | --- | --- | --- |
| S1 | 할인 규칙 위치 | `domain/discount-policy.ts` 로 분리 | 서비스 내부 private 메서드 | 규칙 조합이 많아 독립 unit 테스트 필요 |

### 6. 미결정 / 확인 필요 사항
- 사용자 판단이 필요한 구조 결정, 기존 컨벤션과 정면으로 충돌해 원칙을 우선한 항목(근거 위치 포함)을 기록합니다.
- 각 항목에 권장안과 그 근거를 함께 기재합니다.
- 해소된 항목은 결정 결과를 본문(§2~§5)에 반영하고 이 절에서 제거합니다. (결정 과정은 남기지 않습니다.)
- `상태: 확정` 으로 바꾸기 전에 이 절의 항목은 모두 해소되어야 합니다. 항목이 남아 있으면 확정하지 않습니다.

| ID | 항목 | 권장안 / 대안 | 확인 필요 사유 |
| --- | --- | --- | --- |
| D1 | ... | ... | ... |
