# Output Format: 구조 문서 템플릿

## 0. 구조 문서가 다루는 범위

구조 문서는 **"무엇을 어디에 두고, 누가 누구를 참조하며, 각 단위를 어떻게 떼어 테스트하는가"** 를 확정합니다. 계약의 세부(시그니처·스키마)는 이후 architecture 모드의 설계 문서에서 이 구조를 제약으로 삼아 확정합니다.

| | structure 모드 (구조 문서) | architecture 모드 (설계 문서) |
| --- | --- | --- |
| 확정 대상 | 디렉토리 트리, 모듈 경계·책임, 의존 방향, 테스트 경계 | 데이터 모델, 인터페이스 계약, 처리 흐름, 영향 범위 |
| 이름 수준 | 모듈·노출 단위의 **이름과 역할 한 줄** | 시그니처·타입 필드·스키마 |

**✅ 쓴다**

- 디렉토리·파일 트리 (신규/수정/이동/삭제 표시)
- 모듈별 책임 (한 문장)
- 모듈이 외부에 노출하는 단위의 **이름과 역할 한 줄** (예: `PriceCalculator` — 할인 적용 후 최종 금액 계산)
- 의존 방향과 금지 의존
- 테스트 분류와 seam (무엇을 어디서 대체하는가)
- 구조 결정과 버린 대안

**❌ 쓰지 않는다**

- 함수·메서드 시그니처, 파라미터·반환 타입
- 타입·DTO 필드, DB DDL, API 요청/응답 스키마, 설정 키
- 함수 본문, 제어 흐름, 의사코드
- 테스트 코드, 테스트 케이스 상세 (검증 포인트 한 줄까지만)
- 구현 작업 순서

> **왜 빼는가**: 계약은 구조가 확정된 뒤에야 흔들림 없이 정할 수 있습니다. 구조 문서에 시그니처를 쓰기 시작하면 구조 합의와 계약 합의가 뒤섞여, 구조를 바꿀 때마다 계약까지 다시 쓰게 됩니다.

---

## 파일명 규칙

- 저장 위치: `[Jissp 문서]/[설계 문서]`
  - 태스크 모드(`--task`)면 이 규칙 대신 SKILL.md "태스크 모드"의 저장 위치·파일명(`[태스크 디렉토리]/module-structure.md`)을 따릅니다.
- 파일명: `[파일명 규칙]` 을 따르며, 문서 유형은 `structure` 입니다.
  - `[feature]` 는 PRD 문서명이나 핵심 기능명에서 도출합니다.
  - 예) `20260923_143000_export-csv-structure.md` (기본 파일명 규칙 기준)

## 문서 양식

문서 최상단에는 반드시 아래 **문서 성격 배너**를 그대로 포함합니다. `상태` 값은 사용자 확정 전에는 `초안`, 확정 후에는 `확정` 으로 둡니다.

```markdown
> **문서 성격: 구조 확정 문서**
> - 디렉토리·모듈 경계·책임·의존 방향·테스트 경계를 확정합니다.
> - 계약(시그니처·스키마)은 다루지 않으며, architecture 모드의 설계 문서가 이 구조를 제약으로 삼아 확정합니다.
> - **상태: 초안**
```

---

### 1. 개요
- 목적과 해결하려는 문제 (2~3줄)
- 입력: 참조한 PRD 문서 경로 또는 작업 프롬프트 요지
- 참조한 Rule 문서 경로 (없으면 `없음`)
- 적용 유형: `신규 모듈` / `신규 기능` / `구조 변경 리팩토링` 중 해당 항목
- **범위(In Scope) / 범위 밖(Out of Scope)**

### 2. 요구사항 → 모듈 매핑
- 모든 요구사항이 어느 모듈에서 충족되는지 매핑합니다. (요구사항 누락 방지)
- 한 요구사항이 여러 모듈에 걸치면 모두 적되, **주 담당 모듈**을 첫 번째에 둡니다.

| ID | 요구사항 | 담당 모듈 |
| --- | --- | --- |
| R1 | ... | `feature/pricing/domain` (주), `feature/pricing/adapter` |

### 3. 디렉토리 구조
- 코드 블록에 트리로 작성하고, 각 항목 끝에 **표시 + 역할 한 줄**을 붙입니다.
- 표시: `[New]` 신규 / `[Modify]` 수정 / `[Move]` 이동(원래 경로 병기) / `[Delete]` 삭제 / 표시 없음 = 변경 없음(맥락 파악용)
- 파일 단위까지 내려가되, 변경 없는 영역은 `...` 으로 생략합니다.
- **구조 변경 리팩토링**인 경우 `3.1 AS-IS` / `3.2 TO-BE` 두 트리로 나누고, 이동이 많으면 AS-IS → TO-BE 대응표를 추가합니다.

```text
src/
└── feature/pricing/
    ├── domain/
    │   ├── price-calculator.ts        [New]    할인 적용 후 최종 금액 계산 (순수 로직)
    │   └── discount-policy.ts         [New]    할인 규칙 판정
    ├── adapter/
    │   └── coupon-repository.ts       [New]    쿠폰 조회 (DB 접근)
    ├── pricing.service.ts             [New]    조회 → 계산 흐름 조립
    └── pricing.controller.ts          [Modify] 진입점, 서비스 호출로 교체
```

### 4. 모듈 책임 정의
- §3의 신규·수정 모듈마다 한 행씩 작성합니다.
- `책임`은 **한 문장**입니다. "그리고"가 들어가면 분리를 다시 검토합니다.
- `노출 단위`는 이름과 역할만 적고 시그니처는 쓰지 않습니다.
- `테스트 분류`는 `modes/structure/structure-principles.md` 의 분류(`Unit-순수` / `Unit-주입` / `Integration` / `조립`)를 사용합니다.

| 모듈 | 책임 | 노출 단위 | 테스트 분류 |
| --- | --- | --- | --- |
| `feature/pricing/domain/price-calculator.ts` | 할인 규칙을 적용해 최종 금액을 계산한다 | `PriceCalculator` | Unit-순수 |
| `feature/pricing/pricing.service.ts` | 쿠폰 조회와 금액 계산을 조립한다 | `PricingService` | Unit-주입 |

### 5. 의존 방향
- 모듈 간 의존을 ASCII 도식으로 표현합니다. 복잡하면 `/flow-diagram` 스킬로 도식을 생성해 첨부합니다.
- 도식 아래에 **허용 규칙**과 **금지 규칙**을 목록으로 명시합니다.
- 순환 의존이 없음을 확인한 결과를 한 줄로 기재합니다.

```text
pricing.controller ──▶ pricing.service ──▶ domain/*
                               │
                               └──▶ adapter/coupon-repository
```

- 허용: `service → domain`, `service → adapter`
- 금지: `domain → adapter`, `domain → service`, `adapter → service`
- 순환 의존: 없음

### 6. 테스트 경계
- **6.1 Seam 목록**: 외부 의존마다 격리한 모듈과 테스트 시 대체 방법을 적습니다.

| 외부 의존 | 격리 모듈 | 테스트 시 대체 방법 | 대체 지점 |
| --- | --- | --- | --- |
| DB (쿠폰) | `adapter/coupon-repository.ts` | in-memory fake | `PricingService` 생성 시 주입 |
| 현재 시각 | `shared/clock.ts` | 고정 시각 stub | `DiscountPolicy` 생성 시 주입 |

- **6.2 Unit 테스트 대상**: `Unit-순수` · `Unit-주입` 모듈별 **핵심 검증 포인트**를 한 줄씩 적습니다. (테스트 케이스 상세·테스트 코드는 쓰지 않습니다.)
- **6.3 테스트 배치**: 테스트 파일 위치 규칙 한 줄 (프로젝트 컨벤션을 따르며, 컨벤션이 없으면 제안하고 §10에 기록)

### 7. 구조 결정과 트레이드오프
- 분리·병합·배치에 관한 주요 결정마다 채택안과 버린 대안, 그 이유를 기록합니다. 과잉 분리를 피하려고 **일부러 합친 결정**도 여기에 남깁니다.

| # | 결정 | 채택안 | 버린 대안 | 이유 |
| --- | --- | --- | --- | --- |
| S1 | 할인 규칙 위치 | `domain/discount-policy.ts` 로 분리 | 서비스 내부 private 메서드 | 규칙 조합이 많아 독립 unit 테스트 필요 |

### 8. 컨벤션 대조
- 기존 코드베이스 컨벤션(Rule 문서·실제 코드 패턴)과 본 구조를 대조합니다.
- 컨벤션이 없거나 신규 프로젝트면 `대조할 기존 컨벤션 없음` 한 줄로 대체합니다.

| 기존 컨벤션 | 근거 위치 | 처리 | 사유 |
| --- | --- | --- | --- |
| 기능별 `*.service.ts` 단일 파일에 로직 집중 | `src/feature/order/order.service.ts` | 원칙 우선 | 계산 로직을 `domain/` 로 분리해야 unit 테스트 가능 |
| 파일명 kebab-case | Rule 문서 §2 | 수용 | - |

- `원칙 우선` 으로 처리한 항목은 §10에도 올려 사용자 확정을 받습니다.

### 9. 설계 문서 인계 사항
architecture 모드가 이 구조 위에서 **계약으로 확정해야 할 경계**를 목록으로 넘깁니다. 이름과 합의 대상만 적고 내용은 정하지 않습니다.

- `PricingService` ↔ `CouponRepository`: 쿠폰 조회 결과의 형태
- `PriceCalculator`: 계산 입력·결과 타입
- (DB 스키마·API 변경이 예상되면 그 대상만 명시)

### 10. 미결정 / 확인 필요 사항
- 사용자 판단이 필요한 구조 결정, `원칙 우선` 으로 처리한 컨벤션 충돌 항목을 기록합니다.
- 각 항목에 권장안과 그 근거를 함께 기재합니다.
- 해소된 항목은 결정 결과를 본문(§3~§8)에 반영하고 이 절에서 제거합니다. (결정 과정은 남기지 않습니다.)
- `상태: 확정` 으로 바꾸기 전에 이 절의 항목은 모두 해소되어야 합니다. 항목이 남아 있으면 확정하지 않습니다.

| ID | 항목 | 권장안 / 대안 | 확인 필요 사유 |
| --- | --- | --- | --- |
| D1 | ... | ... | ... |
