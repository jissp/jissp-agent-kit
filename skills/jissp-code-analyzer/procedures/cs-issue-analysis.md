# [분석 절차] 버그/이슈 제보 — 코드 분석·판정

버그/이슈 제보 요구사항 문서의 **분석 요구사항(확정본)** 을 코드에서 추적해 판정하고, 분석 결과 문서 본문을 만듭니다.
이 절차는 **읽기 전용**입니다. 소스 코드를 수정하지 않습니다.

## 1. 코드 분석
**확정된 요구사항**을 코드에서 추적합니다.
1. 요구사항과 관련된 **진입점**을 찾습니다. (에러 문구·엔드포인트·함수/컴포넌트명·기능 키워드로 grep/검색)
2. 진입점부터 관련 로직을 따라가며, 요구사항의 질문에 답할 수 있는 코드 경로를 확보합니다.
3. 다음 관점으로 교차 검증합니다.
   - 조건 분기·예외 처리·경계값(널/빈값/타입/범위) 처리 여부
   - 제보자가 말한 입력·환경 조건이 그 코드 경로를 실제로 타는지
   - 최근 관련 변경 이력(가능하면 `git log`/`git blame`)으로 이미 수정/회귀되었는지
4. 확신이 서지 않으면 억지로 결론 내지 말고 **'판단 불가'**로 두고, 무엇을 더 확인하면 되는지 적습니다.
5. 탐색 범위가 넓으면 `Explore` 에이전트로 병렬 탐색해도 됩니다.

**검증 방식 — 정적 분석 우선 [필수]**
- 재현·원인 검증은 **코드 경로를 읽고 로직 흐름을 따라가는 정적 분석**으로만 수행합니다.
- **테스트 코드를 새로 작성하거나, 테스트 스위트를 실행하지 않습니다.** 작성·실행 비용이 분석 목적 대비 과도합니다. (이 스킬의 산출물은 분석 결과 문서이며, 실제 검증 코드는 후속 작업의 몫)
- 정적 분석만으로 확신이 부족하면 아래 순서로 **최소한의 확인**만 합니다.
  1. 기존 테스트 코드가 해당 경로를 이미 다루는지 **읽기만으로** 확인
  2. 그래도 필요하면 스크래치 디렉토리에서 **일회성 스니펫**(예: `node -e`, 단일 함수 호출 10줄 이내)으로 핵심 로직만 확인 — 프로젝트에 파일을 남기지 않습니다
- 이것으로도 확인이 안 되면 **'판단 불가'** + 필요한 확인 항목을 남기고 넘어갑니다. 검증을 위해 테스트 환경을 구성하지 않습니다.

## 2. 판정
각 요구사항마다 아래 중 하나로 결론짓고 **신뢰도(높음/중간/낮음)** 를 함께 제시합니다.

**버그 제보 유형**
- **재현됨**: 코드상 해당 조건에서 문제가 발생하는 경로가 명확함
- **조건부 재현**: 특정 조건/입력/환경에서만 발생 (조건을 명시)
- **재현 안 됨**: 코드상 해당 문제가 발생할 수 없음 (근거 제시. 다른 원인 가능성도 언급)
- **판단 불가**: 정보/코드 접근이 부족 (무엇이 더 필요한지 명시)

**확인 요청 / 조회 / 개선 요청 유형**
- **의도된 동작**: 코드상 명시적으로 그렇게 설계됨 (근거 제시)
- **의도치 않은 동작**: 설계 의도와 다른 결과 (근거 제시)
- **판단 불가**: 정보/코드 접근이 부족 (무엇이 더 필요한지 명시)

**반대 가능성 점검**: '재현됨'으로 기울 때도 발생하지 않을 조건을, '재현 안 됨'으로 기울 때도 다른 원인 가능성을 한 번 검토합니다.

## 3. 분석 결과 문서 본문 가공
판정 결과와 개선 방향을 이 스킬 디렉토리의 `templates/cs-issue-analysis.md` 양식으로 가공합니다.
- 요구사항 문서의 `원문에서 파악한 내용`·`분석 요구사항(확정본)`은 그대로 옮깁니다.
- 요구사항 문서의 `확인 필요 사항`은 분석으로 해소된 항목을 빼고 `확인 필요 사항`에 이어 씁니다.

## 4. 요약 작성
본문과 함께 반환할 요약을 **핵심만 간결하고 명료하게** 작성합니다.
- 첫 문장에 **결론(판정)** 을 먼저 씁니다.
- 판정·신뢰도 / 핵심 근거 코드 1~3개 / 발생 조건 / 추정 원인 / 개선 방향만 담습니다.
- 요약에 본문 전문을 넣지 않습니다.
