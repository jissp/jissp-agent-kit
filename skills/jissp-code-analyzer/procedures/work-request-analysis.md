# [분석 절차] 업무 요청 — 현행 동작·영향 범위 분석

업무 요청 요구사항 문서의 **요청 내용·범위**를 기준으로, 현재 코드가 어떻게 동작하는지와 요청을 반영하려면 무엇이 영향을 받는지 분석합니다.
이 절차는 **읽기 전용**입니다. 소스 코드를 수정하지 않으며, 구현은 후속 작업의 몫입니다.

## 1. 현행 동작 파악
1. 요청과 관련된 **진입점**을 찾습니다. (화면·엔드포인트·함수/컴포넌트명·기능 키워드로 grep/검색)
2. 진입점부터 관련 로직을 따라가며 **지금 어떻게 동작하는지**를 코드 경로로 확보합니다.
3. 탐색 범위가 넓으면 `Explore` 에이전트로 병렬 탐색해도 됩니다.

## 2. 요청과의 차이
- 요구사항 항목별로 **이미 되는 것 / 일부만 되는 것 / 없는 것**을 구분하고 근거 코드를 붙입니다.

## 3. 영향 범위·기술 스택
- `영향 범위` : 수정될 것으로 보이는 파일·모듈·API·DB (실제 코드 확인 후 기재)
- `기술 스택` : 현재 프로젝트 스택으로 가능한지, 신규 도입이 필요한지

## 4. 구현 가능성 판정
요구사항 전체에 대해 아래 중 하나로 결론짓고 **신뢰도(높음/중간/낮음)** 를 함께 제시합니다.
- **가능**: 현재 구조에서 영향 범위 안의 변경으로 충족 가능
- **조건부 가능**: 선행 작업·외부 결정·구조 변경이 필요 (조건을 명시)
- **판단 불가**: 정보/코드 접근이 부족 (무엇이 더 필요한지 명시)

## 5. 분석 결과 문서 본문 가공
이 스킬 디렉토리의 `templates/work-request-analysis.md` 양식으로 가공합니다.
- 요구사항 문서의 `요청 내용`·`범위`·`기대 결과`는 그대로 옮깁니다.
- 요구사항 문서의 `확인 필요 사항`은 분석으로 해소된 항목을 빼고 `확인 필요 사항`에 이어 씁니다.
- `구현 방향`은 방향과 영향 범위 수준까지만 씁니다. 코드 diff·구현 코드는 쓰지 않습니다.

## 6. 요약 작성
- 첫 문장에 **결론(구현 가능성)** 을 먼저 씁니다.
- 판정·신뢰도 / 이미 되는 것과 없는 것 / 주요 영향 범위 / 확인 필요 사항만 담습니다.
- 요약에 본문 전문을 넣지 않습니다.
