변경된 코드의 품질·보안·유지보수성을 리뷰합니다.
호출 방식 판별·사전 확인·다음 단계 안내는 이 SKILL 이 수행하고, 실제 리뷰(변경분 수집·컨텍스트 로딩·분석·리뷰 문서 기록)는 [docs/worker.md](docs/worker.md) 작업 계약을 따릅니다.

## 호출 방식 판별 (가장 먼저 수행)

호출 방식에 따라 변경분 수집 범위가 달라집니다. 다른 작업 전에 A/B/C를 먼저 판별합니다. 방식별 수집 범위의 세부는 `docs/worker.md` 「변경분 수집」에 있습니다.

| 방식 | 조건 | 리뷰 대상 |
|---|---|---|
| **A** | 인자 없이 호출 | 스테이지된 변경분 (`git diff --cached`) |
| **B** | 인자로 파일(경로/`@`참조) 전달 | 해당 파일의 변경분 + 연관 파일 정합성 반영 |
| **C** | 호출 측 스킬(`jissp-task-manager` 등)이 "이번 작업의 변경 파일 목록"을 전달 | 스테이지와 무관하게 해당 파일의 로컬 변경분 |

## 사전 확인

사용자에게 물어야 하는 경우만 여기서 확인합니다.

- **A**: `git diff --cached --name-only` 결과가 비어 있으면 스테이지된 변경이 없음을 알리고 종료합니다.
- **B**: 파일마다 `git status --short -- [파일]` 로 변경 여부를 확인합니다. 변경분이 없는 파일이 있으면 사용자에게 알리고 "파일 전체를 리뷰할지" 확인합니다. 승인한 파일은 `whole_file_targets` 로 다룹니다.
- **C**: 확인 없이 진행합니다. (변경분이 없는 파일은 작업 절차에서 제외하고 보고합니다)

## 실행 순서

1. 「호출 방식 판별」과 「사전 확인」을 수행합니다.
2. `docs/worker.md` 를 읽고 「입력」의 항목을 위에서 판별한 값으로 채워 그 절차를 직접 수행합니다.
3. 「결과 양식」의 리뷰 문서 경로·「채팅 요약」·「정합성 반영」·「종합」을 사용자에게 전달하고 「리뷰 완료 후」로 넘어갑니다. `상태: 중단` 이면 사유를 알리고 종료합니다.

## 리뷰 완료 후

리뷰 문서를 기록한 뒤에는 **지적사항을 임의로 코드에 반영하지 말고** 기록한 파일 경로와 함께 다음 단계를 사용자에게 물어 선택하게 합니다.

- **선택지 1) 설계 문서 작성** — 지적사항이 여러 파일에 걸치거나 구조적 변경이 필요한 경우 권장. 방금 기록한 리뷰 파일을 입력으로 `/jissp-planner architecture` 를 호출한다.
- **선택지 2) 바로 수정 진행** — 지적사항이 국소적이고 명확한 경우. 리뷰 문서에서 반영할 항목의 AS-IS/TO-BE 를 읽어 코드에 직접 반영한다.
- **선택지 3) 여기서 종료** — 리뷰 문서 확인만 필요한 경우.

「종합」의 권장 다음 단계를 권장안으로 함께 제안하되, 최종 결정은 사용자가 하도록 합니다.
