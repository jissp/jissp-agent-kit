# 모드 B — 리팩토링 계획 Preview (승인 게이트)

`jissp-code-refactoring`이 도출한 개선 후보를 검증하고, 항목별 Before/After로 제시하여 사용자가 적용할 항목을 고르게 합니다.

진행 순서는 `B-1 → P-1B → P-2B → P-3 → P-4 → P-5` 입니다.

> **P-1B에 들어가기 전에 이 문서 뒷부분의 「출력 형식」을 먼저 훑어보십시오.** 항목별로 무엇을 어떤 순서로 적어야 하는지가 거기에 정해져 있습니다.

---

## B-1. 입력 판별

`jissp-code-refactoring`이 승인 게이트를 위해 `args: refactoring-preview`로 호출하는 모드입니다.

이 모드는 **설계 문서가 아니라 직전 대화 컨텍스트를 입력으로 삼습니다.** 아래가 컨텍스트에 존재해야 합니다.

1. **작업 범위** — 아래 둘 중 하나. 호출 스킬의 입력 모드에 따라 갈립니다.
   - **스니펫 대상**: 사용자가 대화창에 첨부한 원본 코드
   - **파일 대상**: 리팩토링 대상 파일 경로 목록 (스테이지된 변경 파일 또는 사용자가 지정한 파일)
2. **개선 후보 목록** — 호출 스킬이 도출한 항목들 (대상 파일 / 카테고리 / 변경 전 / 변경 후 / 근거)
3. **전파 파일 목록** — 식별자명·파일명 변경으로 참조만 갱신될 파일들 (없을 수 있음)
4. **적용하지 않은 후보 목록** — 도출했으나 제외한 항목과 그 이유 (없을 수 있음)

1·2 중 하나라도 없으면 아래를 안내하고 **종료**합니다. (직접 후보를 만들어내지 마십시오.)

> 모드 B는 리팩토링 후보 목록이 컨텍스트에 있어야 동작합니다. `jissp-code-refactoring`으로 후보를 먼저 도출해 주세요.

모드 B에서는 `[Jissp 문서]` 경로 확인과 설계 문서 탐색이 **불필요합니다.** 건너뜁니다.

## P-1B. 후보 인벤토리 정리

컨텍스트에 있는 개선 후보를 **하나도 빠뜨리지 않고** 인벤토리로 옮깁니다. 요약하거나 병합하지 마십시오. 사용자가 항목 단위로 고를 것이므로, **후보 1건 = Preview 항목 1건**이 원칙입니다.

각 후보에서 아래를 추출합니다.

- **번호** — 1부터 연속. 이 번호가 사용자의 선택 단위이자 호출 스킬과의 계약입니다.
- **대상** — 파일 대상이면 파일 경로. 스니펫 대상이면 생략합니다.
- **카테고리** — 네이밍 / 흐름 / 효율 / 관용구 / 죽은코드 / 주석
- **변경 전 / 변경 후** — 원본(스니펫 또는 파일)에서 발췌한 실제 코드
- **근거** — 왜 개선인지 한 줄
- **파급 범위** — 작업 범위 안에서 끝나는지, 밖으로 노출되는 식별자·파일명을 건드리는지. 후자라면 **참조를 갱신할 전파 파일 목록**까지 함께 옮깁니다.
- **적용하지 않은 후보** — 항목과 제외 사유 (P-3에서 별도 절로 제시)

### 후보를 새로 만들지 않습니다

모드 B의 역할은 **이미 도출된 후보를 검증하고 대조 형식으로 보여주는 것**입니다.
Preview 과정에서 "이것도 고치면 좋겠다"는 항목이 눈에 띄어도 후보에 추가하지 마십시오. P-4의 관찰 항목으로만 적습니다.

## P-2B. 후보 검증 (⚠️ 필수 — 생략 금지)

**호출 스킬이 도출한 후보를 그대로 신뢰하지 않습니다.** 이 검증이 모드 B의 존재 이유이자, 무분별한 리팩토링을 걸러내는 지점입니다.

각 후보에 대해 아래를 확인하고, 하나라도 걸리면 **"⚠️ 검증 필요"로 표시**해 사용자가 알고 고르게 합니다. (후보를 임의로 삭제하지는 않습니다.)

1. **원본 대조** — 후보의 `변경 전` 코드가 원본에 **실제로 존재하는지** 확인합니다. 파일 대상이면 해당 파일을 Read로 열어 확인합니다. 없거나 다르면 그 사실을 적습니다. 후보가 원본을 잘못 읽은 채 만들어졌을 수 있습니다.
2. **동작 보존** — 이 변경으로 반환값·예외·부수효과 순서·경계값(`null`/`0`/`''`/빈 배열) 거동이 달라지는 입력이 있는지 확인합니다. 특히 `||`↔`??`, `==`↔`===`, truthy 검사 치환을 의심합니다.
3. **파급 범위** — 변경 대상이 export된 심볼·public 메서드·인터페이스 필드·파일명처럼 **작업 범위 밖에서 참조될 수 있는 것**인지 확인합니다.
   - **스니펫 대상**: 확인할 수단이 없으므로 "작업 범위 밖 영향 가능"으로 표시합니다.
   - **파일 대상**: 호출 스킬이 넘긴 전파 파일 목록을 **Grep으로 직접 재확인**합니다. 목록에 없는 참조처가 나오면 그 사실을 적고 "⚠️ 검증 필요"로 표시합니다. 목록이 옳으면 영향 파일 수를 그대로 노출합니다.
4. **실익** — 이 변경으로 실제로 나아지는지 확인합니다. 취향 차이, 이름만 바꾸는 변경, 이득이 불확실한 효율 개선은 그 사실을 적습니다.
5. **과도함** — 원본 대비 후보 건수가 과한지 봅니다. 원본의 골격(함수 구성, 흐름의 큰 순서)이 알아볼 수 없게 바뀌는 규모라면 P-4에 적습니다.

### 탐색 범위

Before의 출처는 작업 범위입니다. 그 밖으로 나가는 탐색은 **파급 확인 용도로만** 허용됩니다.

- **스니펫 대상**: Before는 **사용자가 첨부한 스니펫 그 자체**입니다. 스니펫에 등장하는 심볼을 추적하려고 코드베이스를 `Grep`·`Glob`으로 탐색하지 마십시오. 스니펫만으로 판단이 서지 않는 항목은 `(작업 범위 밖 — 확인 불가)`를 병기합니다.
- **파일 대상**: 대상 파일은 `Read`로 열어 Before를 확인하고, `Grep`은 **3번(파급 범위) 재확인에만** 씁니다. "더 고칠 것 없나" 하고 코드베이스를 둘러보지 마십시오. 새 후보를 만드는 것은 모드 B의 역할이 아닙니다.

어느 경우에도 **파일을 수정하지 않습니다.** 모드 B는 응답 전용입니다.

## P-3. Preview 조립

아래 「출력 형식」의 섹션 구성에 따라 조립합니다.

- **번호를 절대 재배열·재사용하지 않습니다.** P-1B에서 매긴 번호가 그대로 사용자의 선택 단위이자, 호출 스킬이 "3번 적용"을 해석하는 키입니다.
- **최종 리팩토링 코드 전체를 여기서 출력하지 않습니다.** Preview는 항목별 발췌까지입니다. 전체 코드는 승인 후 호출 스킬이 만듭니다. (여기서 코드를 다 내주면 승인 게이트가 무의미해집니다.)
- 항목이 많아도 **묶거나 생략하지 않습니다.** 고를 수 없는 항목은 없는 항목과 같습니다. 다만 항목 하나의 서술은 3~5줄로 압축합니다.
- P-2B에서 표시한 `⚠️ 검증 필요`를 해당 항목 옆에 그대로 노출합니다.

## P-4. 검증 결과 정리

P-2B의 검증 과정에서 드러난 것들 중, **사용자가 적용할 항목을 고르기 전에 알아야 할 것**을 1~3개로 압축하여 Preview 마지막에 붙입니다.

우선순위가 높은 것부터 고릅니다.

1. **동작 변화 가능 지점** — P-2B 2번에서 걸린 항목
2. **작업 범위 밖 파급** — P-2B 3번에서 걸린 항목. 참조 갱신이 스테이지되지 않은 파일까지 미치는 경우를 특히 앞에 둡니다.
3. **원본과 어긋난 후보** — P-2B 1번에서 걸린 항목
4. **과도한 리팩토링 신호** — 후보 총량이 원본 골격을 바꿀 규모인 경우
5. **수정하지 않고 남기는 버그 의심 지점** — 리팩토링 범위 밖이므로 관찰로만

각 항목은 `문제 → 근거(파일:라인) → 영향` 순으로 씁니다. 걸리는 것이 없으면 억지로 만들지 말고 "특별히 걸리는 지점은 없습니다"로 마무리합니다.

> 이 단계는 **모드 B 전용**입니다. 모드 A는 수행하지 않습니다. 설계 문서의 전제 검증과 착수 전 리스크 도출은 `jissp-planner` review 모드의 역할입니다.

## P-5. 후속 안내 — 승인 게이트

Preview 마지막에 **선택지를 제시하고 응답을 기다립니다.** 이 지점이 승인 게이트입니다.

```
적용할 항목을 골라주세요. (예: "1,3번만", "전부", "취소")
```

- **여기서 반드시 멈춥니다.** 사용자가 고르기 전에 리팩토링 결과 코드를 만들지 않습니다.
- **본 SKILL은 승인 결과를 실행하지 않습니다.** 선택을 받으면 제어는 호출한 `jissp-code-refactoring`으로 돌아가며, 적용은 그쪽 책임입니다.
- 사용자가 "전부"를 골라도 P-2B에서 `⚠️ 검증 필요`로 표시한 항목이 있으면, 해당 번호를 한 줄로 다시 짚어주고 그래도 포함할지 확인합니다.
- 🔗 전파 항목도 마찬가지로 한 번 더 짚습니다. 특히 **스테이지되지 않은 파일**을 함께 고치는 항목은 반드시 별도로 확인합니다.
- 사용자가 "취소"를 고르면 그대로 종료합니다. 설득하거나 대안을 나열하지 않습니다.

## 모드 B 전용 제약

- **후보를 추가·삭제하지 마세요.** 검증하고 표시할 뿐, 목록 자체는 호출 스킬이 정한 것을 유지합니다.
- **최종 코드를 출력하지 마세요.** 승인 전에 결과 코드를 내놓으면 게이트가 무의미해집니다.
- **다른 SKILL을 호출하지 마세요.** 승인을 받은 뒤 제어를 호출자에게 돌려주는 것으로 역할이 끝납니다.
- **문서 저장 대상이 아닙니다.** 모드 B Preview는 대화창 응답으로만 전달합니다.

# 출력 형식

리팩토링 후보를 적용하기 **전에**, 무엇이 어떻게 바뀌는지를 항목 단위로 보여주고 사용자가 고를 수 있게 하는 응답 양식입니다.

## 대원칙

1. **선택 가능해야 합니다.** 모든 후보에 연속 번호를 매기고, 항목 하나만 봐도 적용 여부를 판단할 수 있게 씁니다. 묶거나 생략한 항목은 사용자가 고를 수 없으므로 없는 것과 같습니다.
2. **최종 코드를 내주지 않습니다.** 항목별 발췌 diff까지가 Preview의 범위입니다. 전체 결과 코드를 여기서 출력하면 승인 게이트가 무의미해집니다.
3. **Before는 원본에서 그대로 가져옵니다.** 후보 목록에 적힌 "변경 전"을 그대로 믿지 말고, 원본(첨부 스니펫 또는 대상 파일)에 실제로 그 코드가 있는지 확인한 뒤 옮깁니다.
4. **응답 전용입니다.** 파일을 만들거나 코드를 수정하지 않습니다.
5. **분량은 스크롤 2~3회 이내.** 항목당 3~5줄로 압축합니다. 항목 수가 많으면 각 항목을 더 짧게 쓰되, 항목을 없애지는 않습니다.

## 섹션 구성

각 섹션은 `---`로 구분합니다.

### (도입부) 한 줄 안내

무엇을 대상으로 몇 건의 후보를 검토했는지, 아직 적용하지 않았음을 한 줄로 밝힙니다.

> 첨부하신 스니펫(42줄)에서 개선 후보 4건을 도출했습니다. 아직 적용하지 않았습니다.

파일 대상이면 대상 파일 수와 출처를 함께 밝힙니다.

> 스테이지된 파일 3개에서 개선 후보 6건을 도출했습니다. 아직 적용하지 않았습니다.

### 1. 한눈에 보기

전체 후보를 표로 먼저 보여줍니다. 사용자가 이 표만 보고도 고를 수 있어야 합니다.

**스니펫 대상**

| # | 카테고리 | 무엇을 | 파급 |
| --- | --- | --- | --- |
| 1 | 네이밍 | `data` → `pendingOrders` (L4, L9, L17) | 작업 범위 내부 |
| 2 | 흐름 | 중첩 if 3단 → 가드 절 (L12-28) | 작업 범위 내부 |
| 3 | 효율 | `targetIds.includes` → `Set.has` (L31) | 작업 범위 내부 |
| 4 | 관용구 | `x !== undefined ? x : 0` → `x ?? 0` (L36) | ⚠️ 검증 필요 |

**파일 대상** — `대상` 칸을 추가합니다.

| # | 대상 | 카테고리 | 무엇을 | 파급 |
| --- | --- | --- | --- | --- |
| 1 | `order.service.ts` | 네이밍 | `data` → `pendingOrders` (L4, L9) | 파일 내부 |
| 2 | `order.service.ts` | 네이밍 | `fetchAll` → `fetchPendingOrders` (L11) | 🔗 2개 파일 |
| 3 | `sync.ts` | 효율 | `targetIds.includes` → `Set.has` (L31) | 파일 내부 |

- `파급` 칸에는 `작업 범위 내부`(스니펫) / `파일 내부`(파일) / `🔗 N개 파일` / `⚠️ 작업 범위 밖 영향 가능` / `⚠️ 검증 필요` 중 하나를 씁니다.
- 위치는 `L12-28` 형식으로 적어 원본에서 바로 찾을 수 있게 합니다.

### 2. 항목별 상세

번호 순서대로, 항목마다 아래 4줄 구조로 씁니다.

````
#### 1. `data` → `pendingOrders` (네이밍)

```diff
- const data = orders.filter(o => o.status === 'PENDING')
- return data.map(...)
+ const pendingOrders = orders.filter(o => o.status === 'PENDING')
+ return pendingOrders.map(...)
```

- 근거: `data`는 무엇이 담겼는지 숨기고, 3곳에서 재사용되어 매번 위로 거슬러 읽어야 합니다.
- 파급: 작업 범위 내부 지역 변수 3곳. 밖으로 노출되지 않습니다.
````

파일 대상이면 소제목에 파일 경로를 붙이고, 전파가 있으면 `파급` 줄에 **파일별 참조 개수**를 적습니다.

````
#### 2. 🔗 `fetchAll` → `fetchPendingOrders` (네이밍) — `src/order/order.service.ts`

```diff
- async fetchAll(siteId: string) {
````

### 3. 적용하지 않은 후보 *(있는 경우)*

호출 스킬이 도출했다가 제외한 항목을 **이유와 함께** 밝힙니다. 사용자가 "그건 왜 안 해?"라고 묻지 않아도 되게 만드는 절입니다.

- `parseRow()` 함수 추출 — 한 곳에서만 호출되는 4줄 로직이라 추출 시 호출부와 정의부를 오가야 합니다.
- `filter().map()` → `reduce()` 통합 — 순회는 1회 줄지만 읽는 난이도가 올라갑니다.

사용자가 이 중 하나를 되살려달라고 할 수 있으므로, 번호는 붙이지 않되 항목명은 명확히 적습니다.

### 4. 그대로 두는 것

변하지 않는 부분을 밝혀 "어디까지 손대나"에 대한 불안을 없앱니다.

- 함수 시그니처, 반환 타입 (호출부 0줄 변경)
- 예외 처리 흐름 `try/catch` (L20-26)
- 외부 호출 순서·횟수

### 5. 짚고 넘어갈 것 *(발견된 경우에만)*

리팩토링 범위 밖이지만 사용자가 알아야 할 것을 **1~3개**로 압축합니다. 없으면 절을 생략합니다.

각 항목은 `문제 → 근거(위치) → 영향` 순으로 씁니다.

> - ⚠️ L18의 `if (count = 0)`은 비교가 아니라 대입으로 보입니다. 리팩토링 범위 밖이라 그대로 두었으며, 의도한 것이 아니라면 별도로 확인이 필요합니다.
> - 🔧 L31-40 전체가 O(n²)입니다. 3번 항목으로 일부 완화되지만 근본 해결은 알고리즘 교체라 범위 밖입니다.
