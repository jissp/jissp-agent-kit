# 모드 A — 설계 문서 Preview

작성된 설계 문서를 기준으로, 그것을 적용하면 기존 대비 무엇이 어떻게 달라지는지를 **실제 코드와 대조하여** 정리합니다.

진행 순서는 `A-0 → A-1 → P-1A → P-2A → P-3 → P-5` 입니다.

> **P-1A에 들어가기 전에 이 문서 뒷부분의 「출력 형식」을 먼저 훑어보십시오.** 무엇을 얼마나 보여줄지가 거기에 정해져 있습니다. 그것을 모른 채 조사하면 쓰지도 않을 파일까지 읽게 됩니다.

## A-0. 사전 준비: 디렉토리 정의 확인

작업 시작 전 반드시 `~/jissp-agent-kit/jissp-document.md` 파일을 읽어 **Jissp 문서 경로**와 **세부 디렉토리명**을 확인하십시오.

- **Jissp 문서**: `[프로젝트 경로]/0-jissp-docs`
- **설계 문서**: `[Jissp 문서]/plans`
- **분석 문서**: `[Jissp 문서]/analysis`

> 사용자가 명시적으로 경로를 지정하는 경우, 지정된 경로를 우선시합니다.

## A-1. 입력 판별

첫 번째 args로 **Preview 대상 설계 문서 경로**를 받습니다.

- **설계 문서 경로가 전달된 경우** → P-1A로 진행합니다.
- **args가 비어 있는 경우** → `[Jissp 문서]/plans` 디렉토리에서 최근 수정된 설계 문서를 탐색하여 후보를 제시하고, 어떤 문서를 대상으로 할지 사용자에게 확인한 뒤 진행합니다. 후보가 없으면 설계 문서 경로를 전달해달라고 안내하고 종료합니다.
- **다른 스킬(예: `jissp-planner` architecture 모드)이 호출한 경우** → 전달받은 설계 문서 경로를 그대로 사용하며, 별도 확인 없이 P-1A로 진행합니다.

## P-1A. 설계 문서 통독 및 변경 인벤토리 추출

전달받은 설계 문서를 **처음부터 끝까지** 읽습니다. 발췌·부분 읽기로 대체하지 마십시오.

읽으면서 아래 항목을 인벤토리로 뽑아냅니다.

| 인벤토리 항목 | v2 양식 출처 |
| --- | --- |
| **계약 변화** — API 엔드포인트, 공개 시그니처, 타입/DTO, 큐 페이로드, 응답 스키마 | §5 (Part A) |
| **데이터 변화** — DB 스키마·DDL·마이그레이션, 저장 불변식 | §4 (Part A) |
| **구조 변화** — 모듈 경계, 의존 방향, 채택/폐기된 대안 | §3 (Part A) |
| **흐름 변화** — 요청·데이터·제어 흐름의 순서·참여자·책임 | §6 (Part A) |
| **환경 변화** — 환경변수·설정, 외부 연동, 하위호환·롤백 | §5.5, §7 (Part A) |
| **변경 대상 파일** — 신규/수정/삭제 목록 | §11 (Part B) |
| **사용자 체감 변화** — 화면·응답 형태·에러 표시 등 외부 관측 가능한 변화 | §1, §5.1, §6 |

### ⚠️ Part A와 Part B는 다르게 취급합니다

v2 설계 문서는 **Part A(§1~§9, 확정된 계약)** 와 **Part B(§11~§12, 실행 참고)** 로 나뉩니다. 문서 최상단의 `문서 계약 배너`로 확인할 수 있습니다.

- **Preview의 대조 대상은 Part A입니다.** 사용자가 이 Preview를 보고 판단하는 것은 "이 계약·구조로 가도 되는가"이지 "파일을 몇 개 만드는가"가 아닙니다.
- **Part B(§11 파일 목록)는 조사의 착수점으로만 씁니다.** 어느 파일을 열어볼지 정하는 데 쓰고, 목록 자체를 Preview 내용으로 나열하지 마십시오. §5(추가/삭제되는 것)에 역할 단위로 압축해 넣습니다.
- **§11이 실제 코드와 어긋나는 것은 지적 대상이 아닙니다.** Part B는 갱신 의무가 없는 스냅샷입니다. 단, **§4·§5 계약이 실제 코드와 모순되면 반드시 지적**합니다 — 그것은 설계 오류입니다.
- §11의 행에 `[재작성 필요]` 표기가 있으면 그 행은 무시하고, 해당 계약(§4·§5)을 기준으로 영향을 판단합니다.

### 구 양식 문서인 경우

Part 구분이 없는 문서라면 "변경 대상 파일 및 변경점" 절을 Part B로, 나머지를 Part A로 간주하여 위 원칙을 동일하게 적용합니다. 그 절의 코드 스니펫은 **의도를 보여주는 예시**이므로 Preview에 그대로 옮기지 말고, 실제 코드와 대조한 결과만 씁니다.

### 대상 문서가 설계 문서가 아닌 경우

전달받은 문서가 PRD·분석 문서 등 **구현 계획이 없는 문서**라면, 변경 대상 파일을 특정할 수 없어 Preview의 정확도가 떨어집니다. 이 사실을 사용자에게 알리고, `/jissp-planner architecture`로 설계 문서를 먼저 작성할지 확인한 뒤 진행 여부를 결정합니다.

## P-2A. 현재 코드 대조 검증 (⚠️ 필수 — 생략 금지)

**P-1A에서 뽑은 인벤토리의 각 항목을 실제 코드로 확인합니다.** 이 단계를 건너뛰고 설계 문서만으로 Preview를 쓰면, 문서의 오류를 그대로 증폭시키는 잘못된 산출물이 됩니다.

- **수정·삭제 대상 파일은 직접 읽습니다.** 현재 그 파일이 무엇을 하고 있는지, 몇 줄인지, 어떤 함수·시그니처를 갖고 있는지 확인합니다. → Before 칸과 diff의 `-` 쪽 재료입니다.
- **삭제 대상은 참조처를 `Grep`으로 전수 확인합니다.** 설계 문서가 "여기서만 쓰인다"고 주장해도 직접 확인합니다. 확인 결과가 문서와 다르면 그 사실을 Preview에 적습니다.
- **신규 파일은 경로 충돌만 확인합니다.** 이미 같은 경로에 파일이 있는지, 같은 역할의 모듈이 이미 존재하는지 `Glob`으로 한 번에 봅니다. 신규 파일은 **Before가 존재하지 않으므로 대조 대상이 아닙니다.** 설계 문서에 적힌 구현 내용을 코드 블록으로 옮기지 말고, **역할 한 줄로 요약**해 §5(추가/삭제되는 것)에 넣습니다.
- **환경변수·설정은 실제 파일에서 현재 값의 유무를 확인합니다.** (예: `.env`, `configuration.ts`) 없으면 부팅·런타임에 어떤 영향이 있는지까지 코드로 확인합니다.
- **계약 변화는 호출부를 확인합니다.** 엔드포인트·시그니처가 바뀔 때 그것을 호출하는 코드가 어디에 몇 개나 있는지 파악해야 "클라이언트 0줄 변경" 같은 결론을 낼 수 있습니다.
- **계약 자체의 실현 가능성을 확인합니다(⚠️ 이 스킬의 최대 가치).** §4·§5의 스키마·시그니처·타입이 현재 코드와 충돌하지 않는지 대조합니다. 타입 불일치, 이미 점유된 엔드포인트, 기존 시그니처와의 비호환, 저장된 enum 값 변경처럼 **계약 수준의 오류는 구현 전에 잡아야 비용이 가장 적습니다.** 발견하면 §7(주의 지점)에 명시합니다.

### 문서와 코드가 다른 경우

설계 문서의 서술과 실제 코드가 다르면 **문서 쪽에 맞추지 말고 코드를 사실로 채택**합니다. Before는 언제나 코드가 기준입니다. 이때 설계 문서를 임의로 수정하지 마십시오.

## P-3. Preview 조립

아래 「출력 형식」의 섹션 구성과 표기 규칙에 따라 Preview를 조립합니다.

- 섹션은 대상 설계의 성격에 맞게 **가감**합니다. UI 변화가 없으면 화면 절을 통째로 뺍니다.
- **분량은 스크롤 2~3회 이내.** 모든 변경을 나열하지 말고, 사용자가 "달라졌다"고 체감할 항목 위주로 압축합니다. 사소한 변경은 표의 한 줄로 흡수시킵니다.
- 표·ASCII 도식·diff 스니펫을 섞어 쓰되, 같은 정보를 두 형식으로 중복 표현하지 않습니다.
- 흐름 변화 도식은 mermaid가 아닌 **코드블록 내 ASCII**로 그립니다. 도식이 복잡하면 `/flow-diagram` 스킬의 표기 규칙을 참고하되, **Preview는 문서를 생성하지 않습니다.**
- 각 절의 끝에는 가능하면 **한 문장짜리 결론**을 답니다. (예: "경로가 유지되므로 클라이언트 코드는 0줄 변경입니다.")

Preview 응답이 끝나면, 이 설계로 작업에 착수할지(`/planner-execute`) **한 줄로만** 물어봅니다. (장황한 안내 금지)

# 출력 형식

설계 문서를 적용했을 때 **기존 대비 무엇이 어떻게 달라지는지**를 사용자가 한 번에 파악할 수 있도록 정리하는 응답 양식입니다.

## 대원칙

1. **Before / After 대조가 전부입니다.** "무엇을 만든다"가 아니라 "지금은 이런데, 적용하면 이렇게 된다"로 씁니다. 대조 없이 설계 문서를 요약만 하는 응답은 실패입니다.
   - 뒤집어 말하면, **대조할 Before가 없는 것은 코드로 보여줄 대상이 아닙니다.** 신규 파일은 §4가 아니라 §5에 역할 한 줄로 넣습니다.
2. **설계 문서를 재서술하지 않습니다.** 설계 문서는 이미 사용자가 갖고 있습니다. Preview는 "차이"만 뽑아냅니다.
3. **Before는 반드시 실제 코드에서 확인한 사실**이어야 합니다. 설계 문서에 적힌 "현재 이렇습니다"를 그대로 옮기지 말고, 해당 파일을 직접 열어 확인한 내용을 씁니다.
4. **응답 전용입니다.** 파일을 생성하거나 소스 코드를 수정하지 않습니다.
5. **분량은 스크롤 2~3회 이내.** 모든 변경을 나열하지 말고, 사용자가 "달라졌다"고 체감할 항목 위주로 압축합니다.

## 섹션 구성

아래는 기본 골격입니다. **대상 설계의 성격에 맞게 가감**하되, `흐름 변화`·`계약 변화`·`추가/삭제되는 것`·`그대로인 것`은 가급적 유지합니다. `주의 지점`은 발견한 문제가 있을 때만 붙입니다.

각 섹션은 `---` 로 구분하고, 번호를 붙인 제목을 답니다.

### (도입부) 한 줄 안내

무엇을 무엇과 대조했는지, 그리고 코드를 수정하지 않았음을 한 줄로 밝힙니다.

> 설계 문서대로 적용했을 때 무엇이 어떻게 달라지는지 실제 코드와 대조해 정리했습니다. (코드는 수정하지 않았습니다.)

### 1. 사용자가 보는 화면 / 체감 변화 *(UI·UX·외부 동작 변화가 있을 때만)*

최종 사용자나 API 소비자 입장에서 달라지는 것을 표로 대조합니다. 내부 리팩토링처럼 겉보기 변화가 없으면 **이 절을 생략**하고, 대신 "사용자 체감 변화 없음"을 §6(그대로인 것)에 적습니다.

| | Before (현재) | After (적용 후) |
| --- | --- | --- |
| 로그인 화면 | MCP가 그린 폼 (`hp-login.view.ts:8-105`) | 즉시 302 → 외부 로그인 화면 |
| 실패 표시 | 폼 아래 인라인 메시지 | 실패 페이지 (사유 비노출) |

- Before 칸에는 **근거 파일 경로:라인**을 함께 적습니다.

### 2. 흐름 변화 (Before / After)

요청·데이터·제어 흐름이 어떻게 바뀌는지 ASCII 도식으로 대조합니다.

````
[Before]
브라우저 ─GET /auth/login?key─► 서버   200 HTML(폼)
브라우저 ─POST /auth/login {id,pw}─► 서버 ─POST /sign-in─► 외부
                                      └─ 토큰 저장 → 세션 completed

[After]
브라우저 ─GET /auth/login?key─► 서버   302 (state·PKCE 생성)
        ─────────────────────► 외부 /authorize → 로그인 → 동의
        ◄──── 302 /callback?code&state ────
브라우저 ─GET /callback ─► 서버 ─POST /token─► 외부
                            └─ 토큰 저장 → 세션 completed → 200 HTML
````

- `[Before]` / `[After]` 를 **하나의 코드블록 안에** 위아래로 배치하면 눈으로 대조하기 쉽습니다.
- 도식 아래에는 **이 변화의 본질을 한 문장**으로 덧붙입니다.
  > 비밀번호가 서버를 통과하지 않게 되는 것이 이 전환의 실질입니다.
- mermaid·PlantUML 금지. 코드블록 내 ASCII만 사용합니다.
- 도식이 복잡해지면 `/flow-diagram` 스킬의 표기 규칙을 참고하되, **Preview는 문서를 만들지 않습니다.**

### 3. 계약 변화 (엔드포인트 / 인터페이스 / 시그니처)

외부에 노출되는 계약이 어떻게 바뀌는지 표로 정리합니다. **변하지 않는 항목도 "동일"로 함께 적어야** 영향 범위가 드러납니다.

| 경로 / 시그니처 | Before | After |
| --- | --- | --- |
| `POST /auth/sessions` | `{sessionKey, authUrl}` | 동일 |
| `GET /auth/login` | 200 text/html (폼) | 302 Location: `.../authorize` |
| `POST /auth/login` | 200 `{ok, member}` | 삭제 (404) |
| `GET /auth/callback` | — | 신설 (200/400 HTML) |

- 표 아래에 **호출자 관점의 결론**을 한 줄로 답니다.
  > 경로가 유지되므로 클라이언트 코드는 0줄 변경입니다.

### 4. 코드 변화 미리보기

**AS-IS / TO-BE가 명확히 대조되는 수정만** 골라 `diff` 코드블록으로 보여줍니다. 핵심 2~4개면 충분하며, 전체를 나열하지 않습니다.

이 절에 넣을 것과 넣지 않을 것을 먼저 가릅니다.

| | 대상 |
| --- | --- |
| **넣는다** | 기존 코드가 다른 코드로 **교체**되는 수정 — 시그니처 변경, 로직 대체, 흐름 전환, 삭제 |
| **넣지 않는다** | **신규 파일** — Before가 없어 대조가 성립하지 않습니다. §5에 역할 한 줄로 요약합니다 |
| | **단순 포매팅** — import 순서, 공백·들여쓰기, 세미콜론, 따옴표 스타일. 읽는 사람의 판단에 영향이 없습니다 |
| | **기계적 반복 변경** — 같은 치환이 여러 파일에 동일하게 적용되는 경우. 대표 1건만 보이고 나머지는 "동일 패턴 N곳"으로 적습니다 |

> Before 칸에 쓸 것이 없다면 그 항목은 이 절에 들어올 자리가 아닙니다.

파일마다 `경로 — 한 줄 설명` 형태로 소제목을 답니다.

````
auth-session.controller.ts — 폼 서빙(34-50줄) + 자격증명 수신(52-62줄)이 리다이렉트 + 콜백으로 교체

```diff
- public async loginForm(@Query('sessionKey') k, @Res() res) {
-     res.type('html').send(renderLoginPage(k));
- }
+ public async startLogin(@Query('sessionKey') k, @Res() res) {
+     const url = await this.service.startOAuth(k);   // state·PKCE 생성
+     res.redirect(302, url);
+ }
```
````

- **바뀌지 않는 부분은 주석으로 명시**해 안심 포인트를 남깁니다.
  ```diff
  + await this.tokenStore.save(identity.memberId, tokens.access_token);
    // ↓ 이하 127-147줄 로직 100% 동일 (sessionToken 발급 → completed 저장)
  ```
- 규모 변화가 있으면 숫자로 적습니다. (예: `138줄 → 약 60줄`)
- diff는 **읽히는 수준의 발췌**면 충분합니다. 완전한 구현 코드를 옮기지 마세요.
  - After 쪽은 설계 문서에서 복사하는 것이 아닙니다. **설계 문서에는 함수 본문이 없는 것이 정상**이며(계약까지만 담습니다), After는 §4·§5 계약이 Before 코드에 적용되면 어떤 모습이 되는지를 **Preview 작성자가 최소한으로 그려 보이는 것**입니다. 계약만으로 After를 특정할 수 없는 부분은 억지로 지어내지 말고 `(구현 재량)`으로 표기하거나 이 절에서 뺍니다.

### 5. 추가 / 삭제되는 것

파일·모듈뿐 아니라 **설정·환경변수·스키마·의존성**까지 포함합니다.

**신규 항목은 코드가 아니라 역할로 적습니다.** 아직 존재하지 않는 파일이라 대조할 Before가 없고, 설계 문서의 구현 내용을 옮기면 재서술이 됩니다. 읽는 사람이 알아야 할 것은 "무엇이 생기는가"가 아니라 **"무엇을 하는 것이 생기는가"** 입니다.

| | 항목 |
| --- | --- |
| 신설 | `src/modules/oauth-client/` (5파일) — 외부 SP와 인가코드 교환·토큰 갱신을 담당<br>`token.util.ts` — PKCE `code_verifier`·`state` 생성 |
| 삭제 | `src/modules/hp-auth-client/` (4파일), `LoginDto` |
| Redis | `OAUTH_STATE:{state}` 1종 추가 (TTL 300s) — 기존 3종 무변경 |
| 환경변수 | `OAUTH_CLIENT_ID` 1개 추가 (신규 패키지 0개) |

- 신설 항목은 `경로 (파일 수) — 역할 한 줄` 형식으로 적습니다. 파일 하나하나를 나열하지 않습니다.
- **삭제 대상은 반드시 참조처를 `Grep`으로 확인**하고, 그 결과를 표 아래에 한 줄로 적습니다.
  > 삭제 대상의 사용처를 확인한 결과 문서의 주장이 맞습니다 — `XAuthClient`는 `auth-session.service.ts:45` 한 곳뿐이라 삭제해도 다른 곳이 깨지지 않습니다.
- 확인 결과가 문서와 **다르면** 그 사실을 그대로 적습니다.

### 6. 그대로인 것

변하지 않는 것을 명시하는 것이 변경 목록만큼 중요합니다. 사용자의 불안(“이것도 건드리나?”)을 없애는 절입니다.

- 클라이언트 코드 (계약 무변경)
- `SiteAccessTokenResolver`, `SiteBoundTokenService`, 3개 스토어
- DB 스키마 (마이그레이션 없음)

### 7. 주의 지점 *(코드 대조에서 문제를 발견한 경우에만)*

P-2A에서 **설계 문서의 계약(§4·§5)과 실제 코드가 충돌하는 것**을 발견했다면 여기에 적습니다. 착수 전에 사용자가 알아야 가장 싸게 고칠 수 있는 항목입니다.

| 항목 | 문서 | 실제 코드 | 영향 |
| --- | --- | --- | --- |
| `POST /x/y` | 신설로 기재 | `x.controller.ts:31`에 이미 존재 | 라우트 충돌 — 경로 재확정 필요 |

- 문서 오류를 발견해도 **설계 문서를 수정하지 마십시오.** 보고만 하고 판단은 사용자에게 맡깁니다.
- Part B(§11) 파일 목록이 코드와 어긋나는 것은 **여기에 적지 않습니다.** 갱신 의무가 없는 스냅샷이므로 오류가 아닙니다.
- 발견한 문제가 없으면 이 절을 통째로 생략합니다.
