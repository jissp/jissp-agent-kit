# 1-7. 주석 정리·보강

> 카테고리: **허용되는 변경** (읽는 사람의 인지 부하를 줄이는 변경만 수행한다)

주석은 "줄 수"가 아니라 **읽는 사람이 얻는 정보량** 기준으로 판단한다.
정보가 없는 주석은 덜어내고(7-1), 코드만으로 의도가 안 잡히는 지점에만 채운다(7-2·7-3).

## 7-1. 불필요·장황한 주석 정리

**삭제** — 코드를 읽으면 이미 아는 내용만 담긴 주석
- 코드를 그대로 옮긴 주석 (`// 주문 조회` 위의 `getOrder(orderId)`)
- 시그니처를 반복할 뿐인 JSDoc (`@param userId 유저 아이디`만 있는 블록)
- 장식·구분선 주석(`// =====`), 작성자·날짜 낙서, 이미 처리된 TODO 잔재
- 주석 처리된 죽은 코드 (동작 보존이 100% 확실할 때만 — `rules/06` 기준을 함께 적용)
- **PRD·설계 문서용으로 작성되어 코드에 그대로 옮겨진 주석** — 아래 7-1-1 참조

### 7-1-1. 문서용 주석 제거

PRD·설계 문서 안에서만 뜻이 통하는 주석은 코드에서 지운다. 코드를 읽는 사람에게 정보를 주지 않으면서, 문서가 개정되면 번호·서술부터 어긋나 거짓 정보가 된다.

**대상**
- 요구사항·태스크 식별자 — `(R5)`, `FR-3`, `AC-2`, `§7`, `TASK-12` 등 문서 대조용 기호
- 기획·PRD 맥락 서술 — "체크박스를 추가로 고를 수 없게 된다", "업종 마스터는 23종 규모"
- 설계 결정의 트레이드오프 서술 — "A 를 택하면 판정이 코어로 새어 들어온다"
- 화면·기획 영향 설명 — "400 은 화면 자체를 깨뜨린다", "URL·북마크가 깨진다"

**판단 절차** — 문서 라벨과 설명이 한 주석에 섞여 있으면, 라벨을 지운 뒤 남는 문장이 7-2·7-3 기준(복잡한 로직의 역할 설명, WHY·함정)에 해당하는지로 판단한다. 해당하면 라벨만 떼고 남기고, 아니면 주석째 지운다.

```ts
// 전: 앞은 문서 라벨, 뒤는 JSX 구조를 보면 드러나는 배치 설명 → 통째로 삭제
/** 패널 하단 컨트롤 (R5). 스크롤 영역 밖에 두어 항상 보이게 한다 */
```

**단, 이슈·티켓 링크(`// JIRA-123 우회`)는 지우지 않는다.** 이는 코드 밖에서 여전히 조회 가능한 추적 정보이므로 "손대지 않는다" 항목에 해당한다.

**간소화** — 정보는 있으나 서술이 늘어진 주석
- 여러 줄 서술 → 핵심 한 줄로 압축. 배경 설명·중복 문장·자연어 코드 낭독을 걷어내고 결론만 남긴다
- 나열형 장문 JSDoc → 실제로 비자명한 항목만 남기고 나머지 태그 제거

**손대지 않는다**
- WHY(왜 이 방식인지), 함정·주의사항, 우회 이유, 이슈·티켓 링크
- 외부 계약 정보(API 스펙, 응답 코드 의미, 벤더 제약)
- 아직 유효한 TODO/FIXME
- **코드와 어긋나 보이는 주석** — 어느 쪽이 맞는지 판단하려면 로직 검증이 필요하므로 임의로 고치거나 지우지 말고 "범위 외 관찰"로 보고한다

## 7-2. 복잡한 로직에 역할 설명 추가

코드만으로 "무슨 일을 하는 블록인지" 한 번에 안 잡히는 지점에 **짧은 설명 주석**을 단다.

대상 판단 기준 (하나라도 해당할 때)
- 비자명한 조건 조합 — 논리 연산자 3개 이상이 얽혀 진입 조건의 의미가 안 드러남
- 다단 변환·집계 — 체이닝/중첩 반복으로 최종 산출물이 뭔지 끝까지 읽어야 알 수 있음
- 재귀, 비트 연산, 정규식, 순서 의존 부수효과 등 읽는 속도가 눈에 띄게 떨어지는 구간
- 계산식에 도메인 규칙이 녹아 있어 "무엇을 구하는 값인지" 코드에 안 드러남

작성 방식
- 블록 **상단 한 줄**로, **목적·결과**를 쓴다. 코드를 한국어로 다시 읽어주는 문장은 금지
  - 나쁨: `// items를 순회하며 status가 PAID인 것만 필터링해서 amount를 더한다`
  - 좋음: `// 결제 완료 건만 합산한 정산 대상 금액`
- 기존 주석 언어(한국어/영어)를 따른다
- 라인마다 촘촘히 달지 않는다 (`rules/08`의 "무의미한 주석 대량 추가" 금지와 직결)
- **한 함수에 3개를 넘기면 주석이 아니라 코드가 문제다.** 그 경우 주석 대신 네이밍(`rules/01`)·흐름 평탄화(`rules/02`)·매직값 의미화(`rules/04`)에서 후보를 다시 찾는다

## 7-3. WHY/컨텍스트 주석 (신중하게)

설명이 아닌 **배경**을 남기는 주석. 다음에 한해 한 줄 또는 한 블록이 가독성에 기여한다.

- 비즈니스 룰의 의미 요약
- 함정/주의사항 설명 (예: `// amount / 1.1은 부동 소수점 오차가 발생할 수 있어 * 10 / 11로 처리`)
- JSDoc로 계산식 노출
- TODO에 컨텍스트(이유·관련 링크) 포함
- 메서드의 도메인 절차 요약 — 아래 7-3-1

### 7-3-1. 메서드 절차 요약 JSDoc

여러 단계를 순서대로 밟는 메서드는 상단 JSDoc에 **도메인 절차를 번호로 요약**해, 본문을 따라 읽기 전에 전체 흐름을 잡게 한다.

**대상** (모두 충족)
- 순서에 의존하는 처리 단계가 3개 이상이다
- 호출 이름만으로는 도메인상 의미(무엇을 확정하는지, 왜 이 순서인지)가 드러나지 않는다
- 기존 JSDoc이 없거나 시그니처 반복뿐이다 (있으면 새로 달지 않고 그 JSDoc을 대체·보강한다)

```ts
/**
 * 시트 업로드를 완료 처리한다.
 * 1. 중단되어 남아 있는 행을 실패로 확정한다
 * 2. 확정된 결과로 성공·실패 건수를 집계한다
 * 3. 집계 결과와 함께 업로드를 완료 상태로 전환한다
 */
async process(job: Job<CompleteUploadJobData>) { ... }
```

**작성 방식**
- 첫 줄은 메서드의 목적 한 줄, 이어서 번호 목록
- 각 항목은 호출명의 번역이 아니라 **그 단계가 만드는 도메인 결과**를 쓴다
  - 나쁨: `1. failPending 을 호출한다`
  - 좋음: `1. 중단되어 남아 있는 행을 실패로 확정한다`
- 로깅처럼 도메인 의미가 없는 부수 단계는 생략한다
- 변수명·라인 번호 등 코드가 바뀌면 곧바로 어긋나는 세부는 넣지 않는다

**중복 금지**
- 절차 요약은 이 JSDoc 한 곳에만 둔다. 본문에 같은 단계를 다시 설명하는 단계 주석·박스 주석을 달지 않는다
- 단계 이름만으로 절차가 읽히면(대상 조건 미충족) 달지 않는다. 그 JSDoc은 7-1의 "코드를 그대로 옮긴 주석"이 된다

## 우선순위

주석 변경은 **네이밍·흐름 평탄화로 해결되지 않는 지점에만** 적용한다.
이름을 바꾸거나 조건을 평탄화해서 읽히는 코드라면, 주석을 다는 대신 그쪽을 고친다.
