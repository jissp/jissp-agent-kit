# 가독성 리팩토링 작업 계약

`jissp-readability-refactorer` 서브에이전트와 스킬 직접 수행(모드 C, Gemini) 이 **공통으로 따르는** 작업 규칙입니다.
한쪽에만 규칙을 추가하지 않습니다. 트리거·모드 판별·대상 수집은 SKILL 이 담당하며, 이 문서는 대상이 확정된 뒤의 작업만 다룹니다.

# 1. 입력

호출 측(SKILL)이 아래 항목을 전달합니다. 스킬이 직접 수행할 때는 SKILL 이 판별한 값을 그대로 사용합니다.

| 항목 | 내용 |
|---|---|
| `operation_mode` | `apply`(적용 모드) / `plan`(설계 문서 모드) / `apply+plan`(적용 후 설계 문서도 작성) |
| `input_mode` | `A`(로컬 변경 파일) / `B`(명시된 파일) / `C`(스니펫) |
| `targets` | 작업 대상 파일의 절대 경로 목록 (모드 C 는 스니펫 원문) |
| `workdir` | 대상 프로젝트(레포) 경로 |
| `user_rules` | 이번 대화에서 사용자가 준 지시 중 이번 작업에 걸리는 것 (없으면 생략) |
| `answers` | 직전 반환의 "확인 필요" 항목에 대한 사용자 답변 (재위임일 때만) |

# 2. 작업 절차

1. **rules 읽기** — `~/jissp-agent-kit/skills/jissp-readability-refactoring/rules/` 디렉토리의 모든 파일을 `Read` 로 읽습니다. 읽지 못했다면 추측으로 진행하지 않고 그 사실을 반환합니다.
   - `rules/01-*` ~ `rules/07-*` — **허용되는 변경 카테고리**. 이 카테고리에 해당하는 변경만 수행합니다.
   - `rules/08-forbidden-changes.md` — **금지되는 변경 카테고리**. 발견해도 손대지 말고 "범위 외 관찰"로만 보고합니다.
   - `rules/09-*` ~ `rules/11-*` — 추출 조건 / 동작 보존 / 인지 부하 자문 등 판단 기준.

2. **대상 정독** — 대상 코드를 처음 보는 독자 시점으로 읽고, "여기서 멈춰 다시 읽었다" 싶은 지점을 표시합니다. 그 지점이 1순위 개선 대상입니다. 파일이 여러 개면 파일 단위로 순회합니다.

3. **개선 후보 도출** — 허용 카테고리 중에서만, **인지 부하 자문(`rules/11-cognitive-load.md`)** 을 통과한 항목만 후보로 삼습니다. 금지 카테고리는 즉시 제거하고 "범위 외 관찰"로 보고합니다. 후보 0건이면 해당 파일/스니펫은 "개선 여지 없음" 판정입니다.
   - 아래 경우는 **적용하지 않고 "확인 필요"로 남깁니다.** 나머지 후보는 그대로 진행합니다.
     - 식별자 의도가 코드만으로 추정 불가능 (예: `process()` 가 무엇을 처리하는지 단서 없음)
     - 같은 개념에 서로 다른 도메인 용어가 섞여 있는데 어느 쪽이 우세한지 판단되지 않음 (도메인 용어는 기본 보존 — `rules/01`)
   - `answers` 가 전달되면 해당 "확인 필요" 항목을 답변대로 처리합니다.

4. **결과물 생성 — `operation_mode` 에 따라 분기**

   **4-1. 적용 (`apply`)**
   - **모드 A/B (파일)**: Edit 도구로 파일에 직접 변경 적용. 변경된 식별자는 **해당 파일 내부 스코프 전체**에 일관 반영. 파일 경계를 넘는 변경은 적용하지 않고 "범위 외 관찰"로 보고.
   - **모드 C (스니펫)**: 리팩토링된 코드를 결과의 코드 블록으로 냅니다.
   - 공통: 사용자 언어/스타일(들여쓰기·따옴표·세미콜론) 유지. 주석의 삭제·간소화·추가는 `rules/07-comments.md` 기준을 따릅니다.

   **4-2. 설계 문서 (`plan`)**
   - **Edit 를 수행하지 않습니다.** 대상 코드는 Read 로 읽어 분석만 합니다.
   - 3번의 개선 후보를 "4. 결과 양식 > 설계 문서" 템플릿에 맞춰 작성합니다. 각 후보는 **변경 전/후 코드와 인지 부하 감소 근거**를 포함해, 문서만 보고도 적용 여부를 판단할 수 있게 합니다.
   - **저장 위치**: 모드 A/B 는 `[Jissp 문서]/[설계 문서]/` 아래에 Write 로 생성합니다. 경로 표기는 `~/jissp-agent-kit/jissp-document.md` 의 정의를 따르므로 **저장 전 반드시 이 파일을 Read 로 읽어** 실제 경로·디렉토리명을 확인합니다 (추측 금지). 디렉터리가 없으면 생성합니다.
   - 파일명은 `{YYYYMMDD_HHmmss}_readability-plan-{대상요약}.md` (예: `20260606_143205_readability-plan-payment-handler.md`). 시각은 `date +%Y%m%d_%H%M%S` 로 확인하며, **시분초(`_HHmmss`)를 절대 생략하지 않습니다.** 대상이 여러 파일이면 한 문서에 파일별 섹션으로 묶습니다.
   - 모드 C 는 파일을 만들지 않고 설계 문서 내용을 결과에 마크다운으로 담습니다.

   **4-3. 적용 + 설계 문서 (`apply+plan`)** — 4-1 수행 후 4-2 문서를 함께 작성합니다.

5. **자체 검증** — (적용) 외부 동작이 동일한지 확인하고 인지 부하 자문(`rules/11-cognitive-load.md`)을 한 번 더 적용합니다. (설계 문서) 각 후보가 동작 보존·허용 카테고리 안에 있는지, 변경 전/후가 정확한지 재확인합니다.

6. **결과 반환** — "4. 결과 양식"을 따릅니다.

# 3. 행동/툴 사용 규칙

코드 변경 카테고리 차원이 아니라, **도구 사용·작업 행동** 차원의 규칙입니다.

## 허용

- **Read**: 작업 대상 파일, `rules/`, `jissp-document.md` 읽기
- **Bash**: `date` 조회, 설계 문서 디렉터리 생성(`mkdir -p`). git 은 *조회 전용*
- **Edit**: 적용 모드에서 작업 대상 파일에 가독성 변경 적용 (설계 문서 모드에서는 사용 금지)
- **Write**: 설계 문서 모드에서 `[Jissp 문서]/[설계 문서]/` 아래 설계 문서 파일 생성

## 금지

- **작업 대상 외 파일 탐색 금지** — 의존성·호출처 추적, 광범위 Grep/Glob, 다른 파일 영향도 분석 등은 책임 범위가 아닙니다
- **작업 대상 외 파일 변경 금지** — 가독성 변경(특히 export 된 식별자명 변경)이 다른 파일에 영향을 준다면, 그 영향이 단순 import 한 줄이라도 적용하지 않고 "범위 외 관찰"로 보고합니다
- **설계 문서 모드에서 코드 파일 변경(Edit) 금지**
- **git add/commit/push 금지**
- **새 코드 파일 생성 금지** — 설계 문서 모드의 설계 문서 파일만 예외입니다
- **다른 SKILL·에이전트 호출 금지** — 범위를 벗어나면 "범위 외 관찰"로 보고만 합니다

# 4. 결과 양식

맨 앞에 상태 줄을 둡니다. 서브에이전트는 이 양식 외의 진행 설명·인사·요약 문단을 덧붙이지 않습니다.

```
상태: 완료 | 확인 필요 | 중단
```

- `완료` — 모든 후보를 처리함
- `확인 필요` — "확인 필요" 항목을 제외한 나머지는 처리했고, 답변을 받으면 이어서 처리할 항목이 있음
- `중단` — rules 를 읽지 못함, 대상 파일이 없음 등 작업을 진행할 수 없음 (사유 한 줄)
