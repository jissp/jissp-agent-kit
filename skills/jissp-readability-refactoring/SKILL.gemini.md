  코드를 수정하지 않고 가독성 개선 계획을 설계 문서로만 작성합니다. (저장 위치는 jissp-document.md에 정의된 설계 문서 디렉토리)
  종합 리팩토링·효율 개선이 함께 필요한 경우에는 본 스킬을 사용하지 않습니다.

# 트리거 조건

다음 세 가지 입력 모드 중 하나에 해당하고, 요청 의도가 가독성 개선으로 명확할 때 동작한다.

## 동작 모드 (적용 vs 설계 문서)

입력 모드(A/B/C)와는 별개로, **결과를 어떻게 낼지**를 두 가지 동작 모드로 구분한다.

| 동작 모드 | 트리거 | 결과물 |
|---------|-------|-------|
| **적용 모드** (기본) | 가독성 개선 요청 (아래 "설계 문서" 신호가 없을 때) | 파일에 직접 Edit(모드 A/B) 또는 대화창 코드 블록(모드 C) |
| **설계 문서 모드** | 요청에 "설계 문서", "plan 작성", "문서로 정리", "적용하지 말고 문서로", "계획만" 등 **문서화 의도**가 포함될 때 | 코드를 수정하지 않고, 가독성 개선 계획을 마크다운 **설계 문서**로 작성 |

- 별도 신호가 없으면 **항상 적용 모드**가 기본값이다.
- 설계 문서 모드에서는 **Edit를 일절 수행하지 않는다.** 대상 코드를 읽고 분석만 한 뒤 설계 문서를 작성한다.
- 설계 문서 모드의 저장 위치·형식은 [docs/worker.md](docs/worker.md) 「4-2. 설계 문서」와 「4. 결과 양식 > 설계 문서」를 따른다.
- "적용도 하고 문서도 남겨줘"처럼 둘 다를 명시적으로 요청한 경우에만 적용 모드 수행 후 설계 문서를 함께 작성한다.

## 입력 모드

| 모드 | 작업 대상 | 식별 방법 | 적용 방식 |
|------|---------|---------|---------|
| **A. 로컬 변경 파일** | git status 기준으로 변경된 `.ts` 파일 전체 | `git status --short` 결과에서 `.ts` 필터 (staged·unstaged·untracked 모두) | 파일에 직접 Edit |
| **B. 명시된 파일** | 사용자가 `@경로` 또는 절대/상대 경로로 지정한 파일(들) | 사용자 메시지에서 직접 추출 | 파일에 직접 Edit |
| **C. 코드 스니펫** | 대화창에 직접 붙여넣은 코드 블록 | 사용자 메시지 내 코드 블록 | 대화창에 코드 블록으로 응답 |

요청 예시:
- 모드 A: "로컬에서 변경된 파일들 가독성 개선해줘", "지금 작업 중인 파일들 읽기 쉽게 해줘"
- 모드 B: "`@src/.../foo.handler.ts` 가독성만 개선해줘"
- 모드 C: 코드를 붙여넣고 "이 코드 읽기 쉽게 해줘"

## 동작하지 않는 경우

- 요청에 "효율적으로 / 최적화 / 성능 개선" 등 가독성 외 축이 섞인 경우 → 안내 후 종료
- 기능 추가/버그 수정/아키텍처 변경 요청
- 프로젝트/디렉터리 단위 광범위 리팩토링 요청 (지정 파일 또는 변경 파일 범위를 벗어남)
- 모드 A 요청인데 git 변경 파일에 `.ts`가 0건인 경우 → 사용자에게 안내 후 종료

안내 문구:
> 본 스킬은 지정된 코드의 **휴먼 가독성**만 개선합니다. 효율·구조·기능 변경이 필요하면 `jissp-code-refactoring` 사용을 검토해 주세요.

**안내만 하고 종료한다. 어떤 경우에도 `jissp-code-refactoring`을 비롯한 다른 SKILL을 대신 호출하지 않는다.**
스킬 선택은 사용자의 몫이며, 본 SKILL은 자신의 범위를 벗어났다는 사실만 알리고 작업을 끝낸다.

# 실행 방식

대상 확정까지는 이 SKILL 이 수행하고, 실제 분석·적용·문서 작성은 [docs/worker.md](docs/worker.md) 작업 계약을 따릅니다.
모든 입력 모드를 이 SKILL 이 직접 수행합니다. `docs/worker.md` 를 읽고 그 절차를 그대로 따르며, "확인 필요" 항목은 반환하지 않고 사용자에게 바로 묻습니다.

# 실행 순서

0. **동작 모드 판별** — 요청에 "설계 문서 / plan 작성 / 문서로 정리 / 적용하지 말고 / 계획만" 등 문서화 의도가 있으면 `plan`, 둘 다 명시하면 `apply+plan`, 없으면 `apply`(기본).

1. **입력 모드 식별 및 대상 수집**
   - **모드 A**: `git status --short`로 변경 파일 목록 수집 → `.ts` 파일만 필터. 0건이면 안내 후 종료. **수집된 `.ts` 파일은 개수 상한 없이 전부 작업 대상이다.** 파일이 많을 때 범위를 확인하는 절차는 "모호성 처리" 참고 (확인은 질문일 뿐 상한이 아니다).
   - **모드 B**: 사용자가 지정한 파일 경로를 그대로 작업 대상으로 확정. 존재하지 않는 경로면 안내 후 종료.
   - **모드 C**: 첨부된 코드 블록을 작업 대상으로 확정.
   - 요청 의도가 가독성 외 축과 섞이면 "동작하지 않는 경우"의 안내 문구를 출력하고 **즉시 종료**한다. (다른 SKILL을 이어서 호출하지 않는다)
   - 이 단계에서는 대상 파일을 읽지 않는다. 경로 확인까지만 한다.

2. **작업 수행** — `docs/worker.md` 를 읽고 「1. 입력」의 항목을 위에서 판별한 값으로 채워 직접 수행한다.

# 모호성 처리

대상 확정 전에는 다음 경우에만 사용자에게 단 하나의 명확한 질문을 던진다.
식별자 의도·도메인 용어처럼 코드를 읽어야 생기는 질문은 작업 중 `docs/worker.md` 「2. 작업 절차」 3번 기준에 따라 묻는다.

- "가독성만"인지 "효율도 함께"인지가 메시지에서 불명확
- 모드 A에서 `.ts` 변경 파일이 많아(참고 기준: 20개 초과) **처리 범위를 먼저 확인**해야 하는 경우
  - 이는 **처리 개수 상한이 아니다.** 파일 수를 이유로 대상을 잘라내거나 작업을 거부하지 않는다.
  - 파일 목록을 제시하고 "전량 처리 / 일부만 처리" 중 무엇을 원하는지 한 번 묻는다. **전량 처리로 승인되면 필터 없이 전부 처리한다.**
  - 20은 질문을 던질 시점의 참고 숫자일 뿐이며, 파일이 20개를 넘어도 대상이 명확히 한 덩어리로 묶이면 묻지 않고 진행해도 된다.

**좋은 질문**: "L14의 `convert()` 함수가 도메인상 '단위 환산'을 의미하는지 '포맷 변환'을 의미하는지에 따라 변수명 방향이 달라집니다. 어떤 의미인가요?"

**나쁜 질문**: "어떻게 바꿀까요?", "더 알려주실 내용이 있나요?"

# 본 SKILL과 `jissp-code-refactoring`의 분기 기준

두 스킬은 **서로를 호출하지 않는 독립 스킬**이다.
아래 표는 *어느 스킬을 고를지에 대한 안내 기준*일 뿐이며, 본 SKILL이 `jissp-code-refactoring`을 실행하라는 뜻이 아니다.
본 SKILL 범위를 벗어난다고 판단되면 **안내 문구만 출력하고 종료**한다. 실제 스킬 선택과 재요청은 사용자가 한다.

두 스킬은 입력 형태(스니펫 / 로컬 변경 파일 / 지정 파일)가 겹친다. **갈리는 것은 개선 축뿐이다.**

| 상황 | 사용 SKILL |
|------|-----------|
| "이 코드 읽기 쉽게 / 가독성만 / 한눈에 안 들어와" | **본 SKILL** (적용 모드) |
| "로컬 변경 파일 **가독성** 개선" / "@파일 **가독성** 개선" | **본 SKILL** (적용 모드) |
| "가독성 개선 **설계 문서/plan** 작성" / "적용하지 말고 문서로 정리" | **본 SKILL** (설계 문서 모드) |
| "이 코드 리팩토링 / 정리 / 개선" (효율 포함 암시) | `jissp-code-refactoring` |
| "효율적으로 / 최적화 / 성능" 단어 포함 | `jissp-code-refactoring` |
| 알고리즘 변경 가능성 명시 | `jissp-code-refactoring` |
| 식별자명·파일명 변경을 다른 파일까지 전파해야 함 | `jissp-code-refactoring` (본 SKILL은 파일 경계를 넘지 않음) |
| 의도 불명확 | 사용자에게 1회 확인 후 결정 |
