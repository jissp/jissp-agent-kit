# 태스크 구현 위임 (run 구현 단계)

> 선행: [execute.md](execute.md) 2장의 태스크 컨텍스트 확보까지 마친 뒤 적용합니다.

`architecture.md` 가 있는 태스크의 구현은 **설계는 Opus, 구현은 Sonnet** 으로 나누기 위해 아래 구현 방식 중 하나로 진행합니다.

| 구현 방식 | 실행 주체 | 비고 |
|---|---|---|
| `agent` | `jissp-task-implementer` 서브에이전트 (Sonnet) | 별도 컨텍스트에서 구현하고 결과만 반환 |
| `skill` | `jissp-task-implement` 스킬 (Sonnet) | run 세션 안에서 모델만 바꿔 구현 |
| `inline` | run 메인 세션 | 기존 방식. `~/jissp-agent-kit/skills/planner-execute/guideline.md` 를 `Read` 로 읽고 직접 구현 |

- 지정: `run [feature] [task] --impl agent|skill|inline`
- 생략 시 [../config.md](../config.md) frontmatter 의 `default_impl` 을 따릅니다. (값이 없거나 파일이 없으면 `agent`)
- **Gemini(agy) 환경**: `agent` 는 `invoke_subagent` 로 `TypeName: "jissp-task-implementer"` 를 띄웁니다. 호출 시 모델을 고를 수 없어 Opus/Sonnet 분리는 적용되지 않고, 컨텍스트 분리 효과만 얻습니다. `skill` 은 `jissp-task-implement` 스킬을 같은 계약으로 실행하되, 모델 전환 없이 run 세션의 모델로 구현합니다.
- 그 밖에 서브에이전트를 지원하지 않는 환경은 `inline` 으로 진행합니다.
- `agent` 와 `skill` 은 **같은 구현 계약(아래 2장)** 을 따릅니다. 두 방식을 비교한 뒤 한쪽을 폐기할 예정이므로, 한쪽에만 규칙을 추가하지 않습니다.
- `architecture.md` 가 **없는** 태스크(README·`prd.md`·`module-structure.md` 만 있음)는 아래 4장 「설계 없는 태스크 위임」 을 따릅니다.

# 1. 호출 측 절차 (run 메인 세션)

## 위임 단위

- 설계 문서 §12 작업 순서의 **단계 단위**로 위임합니다. 사용자가 범위를 지정하면(예: "1~3단계") 그 범위를 한 번에 위임합니다.
- 단계 결과를 요약 보고한 뒤 다음 단계로 진행할지 사용자에게 확인합니다.
- `agent` 방식에서 같은 run 안의 다음 위임(다음 단계·보완)은 **직전 구현 서브에이전트에 이어서 맡기는 것**(`SendMessage`, Gemini(agy) 는 직전 서브에이전트의 `conversationId` 로 `send_message`)을 우선합니다. 새로 띄울 때마다 시스템 프롬프트·문서·코드를 다시 읽는 고정비가 들기 때문입니다.

## 병렬 그룹

§12에 `2-A`, `2-B` 처럼 숫자가 같고 접미사만 다른 단계가 있으면 병렬 그룹입니다. 그룹 단위로 착수·보고합니다.

- **`agent` 방식 (Claude)**: 그룹 단계 수만큼 `jissp-task-implementer` 를 **한 메시지에서 동시에 새로** 띄웁니다. 병렬 단계에는 위 이어서 맡기기 규칙을 적용하지 않습니다.
  - 착수 전, 그룹 구성(단계·담당 파일 수·실행 모델)을 보여주고 한 번만 확인받습니다. 그룹 안의 단계마다 따로 묻지 않습니다.
  - §11 에 `단계` 컬럼이 없거나 그룹 단계의 파일이 비어 있으면 `owned_files` 를 정할 수 없으므로 동시에 실행하지 않고 순차로 진행합니다. 메인 세션이 파일 소유를 추측해 나누지 않습니다.
  - §12 에서 `Opus`/`opus-required` 로 지정된 그룹 단계는 동시 실행에서 빼고, 나머지 단계의 반환이 모인 뒤 `inline` 으로 진행합니다. (사용자가 Sonnet 진행을 지시하면 함께 띄웁니다)
  - 그룹이 끝난 뒤의 다음 단계(조립 등)는 그룹 중 한 서브에이전트에 이어서 맡깁니다.
- **`skill`·`inline` 방식, Gemini(agy)**: 동시에 실행하지 않고 그룹 단계를 `2-A → 2-B` 순서로 하나씩 진행합니다. `skill`·`inline` 은 run 세션 안에서 실행되어 동시 실행이 불가능하기 때문이며, 구현 측 계약(2장)은 `agent` 와 같습니다.
- 사용자가 범위를 지정하면(예: "2그룹만") 그 범위를 따릅니다. 그룹 일부 단계만 지정되면 지정된 단계만 띄웁니다.
- 지정 범위가 그룹을 포함하면(예: "1~3단계") 한 번에 위임하지 않고 그룹 앞 단계 → 그룹 동시 실행 → 그룹 뒤 단계로 나눠 위임합니다. 각 구간이 끝날 때마다 보고하되, 범위 안이므로 다음 구간 진행 여부는 다시 묻지 않습니다.

## 전달 항목

문서 내용을 붙여 넣지 말고 **경로만** 전달합니다. 구현 측이 직접 읽습니다.

| 항목 | 내용 |
|---|---|
| `task_dir` | 태스크 디렉토리 경로 |
| `architecture` | 태스크 `architecture.md` 경로 |
| `task_docs` | 존재하는 태스크 문서 경로 (`README.md`·`prd.md`·`module-structure.md`·`docs/*`) |
| `context_docs` | 태스크 컨텍스트에서 이번 범위와 관련 있다고 판단한 선행 태스크·feature 문서 경로 |
| `stage` | 이번에 구현할 §12 단계 (번호·이름) |
| `parallel_with` | 병렬 그룹으로 동시에 진행 중인 다른 단계 (번호·이름). 동시 실행할 때만 전달합니다 |
| `owned_files` | `parallel_with` 와 함께만 전달. §11 `단계` 컬럼이 이번 `stage` 인 파일 경로 |
| `others_files` | `parallel_with` 와 함께만 전달. §11 `단계` 컬럼이 `parallel_with` 단계인 파일 경로 |
| `workdir` | 코드를 작성할 레포(워크트리) 경로 |
| `user_rules` | 이번 대화에서 사용자가 준 지시 중 이번 구현에 걸리는 것. 메모리 인덱스·`CLAUDE.md` 는 구현 측에도 자동으로 들어가므로 다시 옮기지 않습니다 |
| `notes` | 이전 단계 반환에서 이어받을 결정·사용자 추가 지시 |
| `fixes` | 보완 위임일 때만. 사용자가 승인한 보완 항목 목록과 출처(갭 리포트·리뷰 결과 경로와 항목 번호) |

## 반환 처리

- `상태: 완료` → 결과를 요약 보고하고, README.md "작업 이력"에 **구현 방식**(`agent`/`skill`)·단계·결정 사항을 기록합니다.
- `상태: 중단` → 중단 사유를 사용자에게 그대로 알리고 결정을 받습니다. 결정을 `notes` 에 담아 같은 단계를 다시 위임합니다.
  - `opus-required` 로 중단된 단계는 사용자가 Sonnet 진행을 지시하지 않는 한 `inline` 으로 진행합니다.
- `계약 일탈` 항목이 있으면 모아 두었다가 [execute.md](execute.md) "완료 전·후 안내"의 `architecture.md` 갱신 여부 확인에서 처리합니다.
- 모든 단계가 끝나면 [execute.md](execute.md) 3장 완료 처리(검토 선택지)로 이어갑니다. 구현 측이 종료했다고 run 을 끝내지 않습니다.

## 그룹 합류 (병렬 그룹을 동시에 실행한 경우)

- 그룹의 반환이 **모두 모인 뒤** 처리합니다. 한 단계가 `중단` 이어도 나머지 반환을 기다렸다가 한 번에 보고합니다.
- 메인 세션에서 전체 타입 체크·빌드와 기존 테스트를 한 번 실행합니다. 각 반환에서 "합류 후 실행 필요" 로 미룬 테스트도 여기서 실행합니다. 검증을 다른 서브에이전트에 맡기지 않습니다.
  - 실패가 나면 실패한 파일이 속한 단계(`owned_files`)의 서브에이전트에 `SendMessage` 로 수정을 맡깁니다. 여러 단계에 동시에 맡기면 `parallel_with`·`owned_files` 를 그대로 유지합니다. 어느 단계에도 속하지 않는 파일이면 사용자에게 알리고 결정을 받습니다.
- 각 반환의 `소유 범위 밖` 중단은 모아서 보고하고, 해당 파일 작업을 조립 단계로 넘길지 사용자에게 확인합니다.
- 작업 이력에는 `그룹 2 (2-A, 2-B / agent 병렬)` 처럼 그룹과 실행 방식을 함께 기록합니다.

## 보완 위임 (검토 루프)

[execute.md](execute.md) 3장 검토 선택지에서 나온 코드 보완도 구현과 같은 방식으로 위임합니다. `inline` 이면 메인 세션이 직접 고칩니다.

- **위임 대상**: 갭 리포트(선택지 1)·코드 리뷰(선택지 2)에서 사용자가 승인한 항목, 추가 명령(선택지 4) 중 이번 태스크 범위의 코드 수정
- **위임하지 않는 것**: 가독성 리팩토링(선택지 3, 스킬이 직접 수행), 설계 문서·태스크 문서 갱신, 태스크 범위 밖 작업, 조사·질의응답처럼 코드를 고치지 않는 요청
- 승인된 항목만 `fixes` 에 담습니다. 승인 전 항목이나 메인이 판단해 덧붙인 항목을 넣지 않습니다.
- 반환은 구현과 같이 처리하고, 작업 이력에는 `보완 [N]차 (agent/skill)` 로 기록합니다.

# 2. 구현 측 계약 (`jissp-task-implementer`·`jissp-task-implement` 공통)

## 착수 전

1. `~/jissp-agent-kit/skills/planner-execute/guideline.md` 를 `Read` 로 읽습니다.
2. 전달받은 `architecture` → `task_docs` → `context_docs` 순으로 읽습니다.
3. `workdir` 의 `CLAUDE.md` 와 코드 컨벤션을 확인합니다.

## 적용할 규칙

- guideline 「설계 문서 해석」·「실행 모델 가드레일 (opus-required)」·「구현 단위 규약」·「구현 순서 규약」·「테스트 코드 작성 정책」·「주석 원칙」 을 따릅니다.
- guideline 「설계 문서 갱신 정책」 은 적용하지 않습니다. **설계 문서·태스크 문서를 수정하지 않으며**, `/jissp-planner` 도 호출하지 않습니다. 계약을 바꿔야 하면 중단하고 반환합니다.
- 태스크 문서끼리 어긋나면 `architecture.md` > `module-structure.md` > `prd.md` 순으로 따르고, 어긋난 지점을 반환에 적습니다.
- `user_rules` 는 guideline 보다 우선합니다.
- 구현 범위는 전달받은 `stage` 까지입니다. 다음 단계를 미리 작성하지 않습니다.
- `parallel_with` 가 전달되면 다른 구현자가 같은 레포에서 동시에 작업 중입니다. §11은 설계 시점 스냅샷이지만, 동시 실행 중에는 충돌을 막기 위해 `owned_files` 소유권을 지킵니다.
  - `owned_files` 의 파일과, §11에 없는 **신규 파일**(반환 `변경 파일` 에 적음)만 생성·수정·삭제합니다.
  - 신규 파일은 `owned_files` 가 속한 모듈 디렉토리 안에만 만듭니다. 공용 위치(배럴(index)·공용 타입·상수·DI 등록 등)에 새 파일이 필요하면 다른 구현자와 겹칠 수 있으므로 중단하고 반환합니다.
  - 그 밖의 기존 파일이나 `others_files` 를 고쳐야 하면 중단하고 반환합니다.
- `parallel_with` 가 전달되면 검증 범위를 아래처럼 좁힙니다. 같은 `workdir` 에서 다른 구현자의 검증과 동시에 돌기 때문입니다.
  - 타입 체크는 산출물을 남기지 않는 방식(예: `tsc --noEmit`)으로만 실행합니다. 빌드 출력(`dist`·`tsbuildinfo` 등)을 쓰는 빌드는 실행하지 않습니다.
  - 타입 체크 에러 중 소유 범위(`owned_files`·직접 만든 신규 파일) 밖에서 난 것은 고치지 않고 건수만 반환에 적습니다.
  - 테스트는 소유 범위의 단위에 걸린 기존 테스트 중 공유 자원(DB·외부 서비스·고정 포트·공용 파일)을 쓰지 않는 것만 실행합니다. 공유 자원을 쓰는 테스트는 실행하지 않고 반환 `검증` 에 "합류 후 실행 필요" 로 적습니다.
  - 빌드와 전체 검증은 호출 측이 합류 후 수행합니다.
- `fixes` 가 전달되면 보완 위임입니다. 범위는 `fixes` 항목뿐이며, 출처 리포트에서 해당 항목만 읽고 고칩니다. 승인되지 않은 다른 항목은 고치지 않습니다.
- `git add`·`commit` 을 하지 않습니다. 작업 이력도 기록하지 않습니다. (호출 측 담당)

## 중단하고 반환할 조건

사용자에게 직접 묻지 않고, 아래에 해당하면 **그 지점에서 멈추고 반환**합니다. 이미 작성한 코드는 되돌리지 않고 반환에 적습니다.

| 분류 | 조건 |
|---|---|
| `opus-required` | 이번 단계가 §12 에서 `Opus`/`opus-required` 로 지정됨 (착수 전 확인) |
| `계약 불일치` | §4·§5 계약을 그대로 지킬 수 없음 |
| `미결정` | §9 미결정 항목이 이번 범위에 걸림 |
| `선행 결과물 수정` | 선행 태스크 결과물(공통 모듈 등)을 고쳐야 함 |
| `소유 범위 밖` | 동시 실행 중 `owned_files` 밖 기존 파일이나 `others_files` 를 고치거나, 공용 위치에 신규 파일을 만들어야 함 (파일 경로와 이유를 적음) |
| `지시 불일치` | 지시문서와 실제 코드 상황이 어긋남 |
| `중요 결정` | guideline Mission 2 의 중요한 결정(인증 방식·DB 종류 등)이 필요함 |

## 반환 양식

아래 양식만 반환합니다. 코드 전문이나 문서 원문을 담지 않습니다.

```markdown
상태: 완료 | 중단
단계: [§12 단계 번호·이름 / 보완이면 "보완: 출처 항목 번호"]

- `경로` — 한 줄 요지

- 합류 후 실행 필요: `테스트 경로` — 쓰는 공유 자원 (`parallel_with` 가 있을 때만, 없으면 생략)
```

# 3. 설계 없는 구현 계약 (`jissp-implementer`)

`architecture.md` 가 없어 §4·§5 계약과 §12 단계가 없는 구현에 적용합니다. 태스크 run 의 설계 없는 태스크와, 태스크 없이 메인 세션이 위임한 일반 코딩 요청이 대상입니다.

변경 파일 스테이징은 호출 측이 맡습니다. 태스크 run 은 [execute.md](execute.md) 「변경 파일 스테이징」 을 따르고, 일반 요청은 메인 세션이 상태 `완료` 반환을 받은 뒤 「변경 파일」 을 같은 규칙(개별 경로, `0-jissp-docs` 하위 제외, 커밋 없음)으로 스테이징합니다.

## 입력 (호출 측이 전달)

문서 내용을 붙여 넣지 말고 **경로만** 전달합니다. 태스크가 없는 일반 요청만 `request` 에 원문을 담습니다.

| 항목 | 내용 |
|---|---|
| `workdir` | 코드를 작성할 레포(워크트리) 경로 |
| `task_dir` | 태스크 디렉토리 경로. 일반 요청이면 생략 |
| `task_docs` | 존재하는 태스크 문서 경로 (`README.md`·`prd.md`·`module-structure.md`·`docs/*`). 일반 요청이면 생략 |
| `context_docs` | 선행 태스크·feature 문서 중 이번 범위와 관련 있는 것의 경로 |
| `request` | 일반 요청일 때 사용자 요청 원문과 메인 세션이 확인한 범위·결정. 태스크면 이번 회차에 구현할 범위(요구사항 일부만 진행할 때) |
| `user_rules` | 이번 대화에서 사용자가 준 지시 중 이번 구현에 걸리는 것 (메모리·`CLAUDE.md` 는 자동으로 들어가므로 옮기지 않음) |
| `notes` | 이전 반환에서 이어받을 결정·사용자 추가 지시 |
| `fixes` | 보완 위임일 때만. 승인된 보완 항목 목록과 출처(갭 리포트·리뷰 결과 경로와 항목 번호) |

## 착수 전

1. `~/jissp-agent-kit/skills/planner-execute/guideline.md` 를 `Read` 로 읽습니다.
2. `task_docs` → `context_docs` 순으로 읽습니다. 태스크 문서끼리 어긋나면 `module-structure.md` > `prd.md` > `README.md` 순으로 따르고, 어긋난 지점을 반환에 적습니다.
3. `workdir` 의 `CLAUDE.md` 와 코드 컨벤션을 확인합니다.

## 적용할 규칙

- guideline 「구현 단위 규약」·「테스트 코드 작성 정책」·「주석 원칙」 을 따릅니다. `module-structure.md` 가 있으면 그 결정이 「구현 단위 규약」 보다 우선합니다.
- 「구현 순서 규약」 은 신규 모듈을 여럿 만들 때만 적용합니다. 기존 코드 수정이면 변경 단위를 하나씩 고치며 검증합니다.
- 요구사항에 없는 기능·리팩토링을 덧붙이지 않습니다. 범위는 `task_docs` 의 요구사항(또는 `request`)까지입니다.
- `user_rules` 는 guideline 보다 우선합니다.
- 태스크 문서를 수정하지 않고 작업 이력도 기록하지 않습니다. (호출 측 담당) `git add`·`commit`·`stash`·`merge`·브랜치 전환을 하지 않습니다.
- `fixes` 가 전달되면 그 항목만 고칩니다.

## 중단하고 반환할 조건

사용자에게 직접 묻지 않고, 아래에 해당하면 **그 지점에서 멈추고 반환**합니다. 이미 작성한 코드는 되돌리지 않고 반환에 적습니다.

| 분류 | 조건 |
|---|---|
| `요구사항 모호` | 요구사항만으로 구현 방향을 하나로 정할 수 없음 (선택지를 적어 반환) |
| `중요 결정` | guideline Mission 2 의 중요한 결정(인증 방식·DB 종류·공개 API·스키마 변경 등)이 필요함 |
| `선행 결과물 수정` | 선행 태스크 결과물(공통 모듈 등)을 고쳐야 함 |
| `지시 불일치` | 요구사항과 실제 코드 상황이 어긋남 |
| `범위 초과` | 요구사항을 채우려면 범위 밖 모듈·다수 파일의 대규모 변경이 필요해 설계 문서(`/jissp-planner architecture`)가 먼저 필요해 보임 |

## 반환 양식

2장 「반환 양식」 과 같습니다. 다만 `단계` 는 `범위: [이번에 구현한 요구사항 요지 / 보완이면 "보완: 출처 항목 번호"]` 로, `계약 일탈` 은 `요구사항과 다르게 처리한 점` 으로 바꿔 씁니다.

# 4. 설계 없는 태스크 위임 (run 메인 세션)

`architecture.md` 가 없는 태스크를 실행할 때의 호출 측 절차입니다.

| 구현 방식 | 실행 주체 |
|---|---|
| `agent` | `jissp-implementer` 서브에이전트 (3장 계약) |
| `skill`·`inline` | run 메인 세션이 3장 「착수 전」·「적용할 규칙」 을 따라 직접 구현 (`jissp-task-implement` 는 설계 문서 전용이므로 쓰지 않음) |

- 위임 단위: 태스크 요구사항 전체를 한 번에 맡깁니다. 사용자가 범위를 나누면 그 범위를 `request` 에 담습니다.
- 이어서 맡기기·반환 처리·보완 위임은 1장과 같습니다. (`계약 일탈` 대신 `요구사항과 다르게 처리한 점` 을 모아 보고)
- `범위 초과` 로 중단되면 `/jissp-planner architecture --task [feature]/[task]` 로 설계 문서 작성을 제안합니다.
- Gemini(agy) 의 `agent` 는 `invoke_subagent` 로 `TypeName: "jissp-implementer"` 를 띄웁니다.
