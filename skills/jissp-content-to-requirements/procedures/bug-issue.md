# [처리 절차] 버그/이슈 제보 — 분석 요구사항 정리

버그/이슈 제보로 분류된 건은 아래 절차를 순서대로 진행합니다.
이 절차는 **무엇을 확인해야 하는지(분석 요구사항)를 확정하는 데까지**입니다. 코드 분석·재현 검증·판정은 수행하지 않으며, 확정된 요구사항으로 분석하는 것은 `jissp-code-analyzer`의 몫입니다.

## 1. 문의 유형 판별
| 유형 | 설명 | 정리 방향 |
|------|------|-----------|
| **버그 제보** | "안 돼요", "에러 나요", "값이 이상해요" | **재현 가능성 검증 요구사항**: 어떤 조건에서 어떤 문제가 코드상 실제 발생하는가 |
| **확인 요청** | "이게 정상 동작인가요?", "왜 이렇게 나오나요?" | **사실 확인 요구사항**: 코드상 의도된 동작인지, 어떤 규칙/조건으로 그 결과가 나오는지 |
| **데이터/이력 조회** | "이 건 왜 이 상태인가요?" | **경로 추적 요구사항**: 어떤 로직이 그 데이터 상태를 만들 수 있는지 |
| **개선/기능 요청** | "이렇게 되면 좋겠어요" | **현행 동작 파악 요구사항**: 현재 코드가 어떻게 동작하며 요청과 어떤 차이가 있는지 |

## 2. 요구사항 정리 + 사용자 확인 [필수 게이트]
분류에 맞춰 **핵심 질문 1~3개**로 압축합니다. 각 질문에는 아래를 명시합니다.
- **관련 기능/화면/API**
- **입력·환경 조건**
- **기대 vs 실제** (해당되는 경우)
- **확인해야 할 것** (한 문장으로, 코드 분석의 목표가 되도록 구체적으로)

정리한 요구사항을 아래 형식으로 채팅에 출력합니다.

```
## 📋 문의 요약 및 분석 요구사항

**유형**: [버그 제보 / 확인 요청 / 데이터 조회 / 개선 요청]
**출처**: (슬랙 링크 / 회의록 / 메모 등)

### 원문에서 파악한 내용
- **증상/요청**: ...
- **맥락**: ...
- **기대 vs 실제**: ...
- **내부 코멘트**: ...

### 분석 요구사항
1. (핵심 질문 1) — 관련 기능: ..., 조건: ...
2. (핵심 질문 2) — ...

### 불명확한 부분 (있는 경우)
- (원문만으로는 알 수 없어 가정한 내용, 또는 추가 정보가 필요한 항목)
```

출력 후 **반드시 사용자에게 검토를 요청하고 응답을 기다립니다.** 이때 승인 여부만 묻지 말고,
**"추가로 확인하거나 요청하고 싶은 내용이 있는지"를 함께 질문합니다.**

```
위 요구사항으로 확정할까요?
추가로 확인하고 싶은 내용이나 요청하고 싶은 부분이 있으면 알려주세요. (없으면 이대로 확정합니다)
```

### 확인 루프 — 추가 요청이 없을 때까지 반복
사용자 응답을 아래로 판단하고, **추가 요청이 없다는 응답이 나올 때까지 이 루프를 반복합니다.** (반복 횟수에 제한을 두지 않습니다)

| 사용자 응답 | 처리 |
|-------------|------|
| **추가 요청 없음** (예: "없어", "없습니다", "그대로 진행", "이대로 ㄱㄱ", "괜찮아", "진행해") | 승인으로 간주하고 **즉시 3. 요구사항 문서 본문 가공으로 진행**합니다. 같은 질문을 다시 하지 않습니다. |
| **추가 요청·수정 사항 있음** | 요구사항에 반영 → **갱신된 요구사항 전문을 다시 출력** → **다시 같은 질문(승인 + 추가 요청 여부)을 반복**합니다. |
| **판단이 모호한 응답** | 임의로 승인·거부로 해석하지 말고 무엇을 반영할지 되묻습니다. |

- 반영 시에는 **어떤 요청을 어디에 반영했는지 한 줄로 밝힙니다.** (예: `추가 반영: 모바일 환경 조건을 분석 요구사항 2에 추가`)
- 사용자의 추가 요청이 이 스킬의 범위를 벗어나면(예: 코드 수정 요청) 반영하지 않고 그 사실을 알린 뒤, 요구사항에 담을 수 있는 형태로 조정합니다.
- **승인 없이 요구사항을 확정하지 않습니다. 가장 중요한 규칙입니다.**

## 3. 요구사항 문서 본문 가공
확정된 요구사항을 이 스킬 디렉토리의 `templates/cs-issue-request.md` 양식으로 가공합니다. (SKILL.md의 [반환 규칙] 참고)
- **확정된 요구사항**(사용자 피드백 반영본)을 그대로 남깁니다.
- 판정·원인·개선 방향은 쓰지 않습니다. 이 절차는 코드 분석을 하지 않았으므로 근거가 없습니다.
- **파일로 저장하지 않습니다.** 저장은 호출자의 몫입니다.

## 4. 요약 작성
- 본문과 함께 반환할 요약에는 문의 유형 / 분석 요구사항 개수와 핵심 질문 / 불명확한 부분만 간결히 담습니다.

## 5. 절차 종료 후
[반환 규칙]의 4개 항목(문서 유형·핵심 키워드·문서 본문·요약)을 갖춘 뒤 SKILL.md [종료 처리]에 따라 분기합니다.
- 다른 스킬이 호출한 경우: 여기서 응답을 끝내지 말고 **호출한 스킬의 다음 단계로 복귀**합니다.
- 사용자가 직접 호출한 경우: 본문 전문과 요약을 채팅에 출력하고 종료합니다.
