# 분류 기준 및 제안 양식

분류의 목적은 **작업자가 단계별로 한 가지에 집중할 수 있게** 나누는 것입니다. 많이 쪼개는 것이 목표가 아닙니다.

## feature 분리 기준

feature는 **혼자서도 완료를 판단할 수 있는 기능 영역**입니다.

| 판단 | 기준 | 예시 |
|---|---|---|
| 하나로 둔다 | 목적이 하나이고, 일부만 끝나서는 완료라고 할 수 없음 | PG 리팩토링 → feature 1개 |
| 나눈다 | 기능 영역마다 따로 완료·검증할 수 있음 | 상품 추가 → 상품 / 장바구니 / 주문 |
| 나눈다 | 같은 도메인이어도 동작(Action)이 독립적임 | 상품 옵션 → 단독형 옵션 / 조합형 옵션 / 추가 옵션 |

- 한 feature의 태스크가 10개를 넘을 것 같으면 나눌 수 있는지 다시 봅니다.
- 나눈 feature 사이의 **순서·의존은 정하지 않습니다.** (feature 간 순서는 현재 범위 밖)

### feature slug

- **동작(Action) 단위** kebab-case로 짓습니다. 같은 도메인을 여러 feature로 나눠도 이름이 겹치지 않게 하기 위함입니다.
  - 형식: `[동작]-[대상]-in-[도메인]` 또는 `[동작]-[대상]`
  - 예: `add-single-option-in-product`, `add-additional-option-in-product`, `refactor-pg`
- structure.md "이름 규칙"의 예약어(`maintenance`, `_` 시작, `backlog`·`holding`·`completed`·`all`)는 쓰지 않습니다.

## 태스크 분리 기준

태스크는 **feature 안에서 모듈 단위로 범위를 정한 작업 1건**입니다.

- **크기**: PRD·설계 문서 하나로 다루고 `run` 한 번에 끝낼 수 있는 크기
- **결과**: 끝났을 때 동작·테스트로 검증할 수 있는 결과물이 있음
- **너무 잘게 쪼개지 않음**: DTO·상수 하나, 엔티티/서비스/컨트롤러 같은 레이어만으로 자른 태스크는 만들지 않습니다. 동작하는 단위로 묶습니다.
- **개수**: 보통 feature당 2~8개. 작업이 하나뿐이면 태스크 1개로 둡니다.
- **순서**: 의존 순서대로 나열합니다. 여러 태스크가 쓰는 공통 모듈이 있으면 앞에 둡니다.
- **선행 태스크**: 앞 태스크의 결과물(모듈·API 등)을 쓰는 태스크는 선행 태스크와 사용하는 결과물을 적습니다.
- **task-slug**: 태스크 내용을 요약한 kebab-case (예: `s3-upload-module`)

## 공통

- 원문에 없는 범위를 추측해 feature·태스크로 만들지 않습니다.
- 원문이 모호해 나누기 어려운 지점은 임의로 정하지 않고 제안에 "확인 필요"로 표시합니다.

## 제안 양식

```markdown
## 분류 결과

[나눈 이유 1~2문장]

### feature: [slug] — [제목]

[이 feature가 맡는 목적·범위 1~2문장]

| # | 태스크 (slug) | 개요 | 선행 |
|---|---|---|---|
| 01 | s3-upload-module | S3 업로드 공통 모듈 | - |
| 02 | excel-sheet-module | 엑셀 sheet 공통 모듈 | 01 |

### 확인 필요

- [모호한 지점과 질문] (없으면 절 생략)
```

- task 모드에서는 대상 feature 하나만 적고, 번호는 그 feature에서 다음에 쓰일 번호부터 예상치로 적습니다. (실제 번호는 `tm.sh` 가 매김)
- maintenance는 번호 대신 `-` 로 적고, 선행 관계는 태스크 slug로 적습니다.
