# Mission

이 문서는 설계 문서를 기반으로 코드를 구현할 때 지켜야 하는 **정책과 룰**입니다.
구현에 착수하기 전에 먼저 읽고, 아래 기준으로 설계 문서를 해석하십시오.

1. 플랜 모드는 절대! 사용하지 않습니다.
2. 사용자가 "알아서 해줘"라고 하더라도, 중요한 결정 사항(예: 인증 방식, DB 종류 등)은 반드시 추천안을 제시하고 동의를 구하세요.

## 절 번호 표기 규칙

`§` 는 **설계 문서의 절 번호**를 가리킵니다. 다른 문서의 절을 가리킬 때는 `구조 문서 §4` 처럼 **문서명을 앞에 붙입니다.**
이 문서 자체의 절은 번호를 쓰지 않고 「설계 문서 해석」 처럼 **이름으로** 부릅니다.

# 설계 문서 해석

설계 문서는 **Part A(§1~§10, 확정된 설계 결정)** 와 **Part B(§11~§12, 실행 참고)** 로 나뉩니다. 이 둘은 구속력이 다릅니다.

## 반드시 지켜야 하는 것 — Part A의 계약

**§4 데이터 모델**(스키마·DDL·불변식)과 **§5 인터페이스 계약**(API 엔드포인트·공개 시그니처·타입/DTO·큐 페이로드·설정 키)이 구현의 고정점입니다.

- 이 계약에서 벗어나면 설계 위반입니다. 구현 중 벗어나야 할 이유를 발견하더라도 **임의로 바꾸지 말고 사용자에게 보고**합니다.
- ⚠️ **계약 일탈 및 임의 타협 절대 금지**: 실제 코드베이스의 제약이나 구현 난관을 이유로 §4·§5의 계약(타입, 시그니처, DDL 등)을 임의로 축소·우회·단순화하여 코드를 끼워 맞추지 마십시오. 계약을 그대로 준수할 수 없다면 작업을 즉시 중단하고 사용자 보고 후 `/jissp-planner architecture revise` 를 통해 설계를 먼저 보정받아야 합니다.
- §3(아키텍처 결정·의존 방향)과 §7(영향 범위)도 준수 대상입니다. 특히 의존 방향 위반은 컴파일이 통과해도 설계 실패입니다.
- §9에 미결정 항목이 남아 있고 그것이 이번 구현 범위에 걸리면, 추측으로 진행하지 말고 사용자에게 확인합니다.

## 참고 자료일 뿐인 것 — Part B의 파일 목록·작업 순서

§11(변경 대상 파일)·§12(작업 순서)는 **설계 시점의 스냅샷**입니다.

- 실제 코드를 읽어보니 파일 구성이 문서와 다르거나 더 나은 배치가 있다면, **Part B를 따르지 말고 실제 코드에 맞게 구현**합니다. 이때도 §4·§5 계약은 그대로 지킵니다.
- §11의 파일이 실재하지 않거나 경로가 어긋나는 것은 오류가 아닙니다. 문서를 고치려 하지 말고 코드를 기준으로 진행합니다.
- 어떤 행의 `변경 요지` 앞에 **`[재작성 필요]`** 표기가 있으면, 그 행은 계약이 바뀐 뒤 갱신되지 않은 것입니다. **표기된 내용을 무시하고 §4·§5 계약을 기준으로** 구현합니다.
- §11 표의 `준수할 계약` 컬럼은 그 파일이 어느 계약에 묶여 있는지를 가리킵니다. 구현 전 해당 절을 확인하십시오.
- §12의 단계 구성은 참고하되, **진행 방향은 「구현 순서 규약」 을 따릅니다.** 둘이 다르면 규약이 우선합니다.

## 실행 모델 가드레일 (opus-required)

이 스킬(planner-execute)은 확정된 설계를 바탕으로 **Sonnet 모델(high)** 을 통해 고속·정밀 구현을 수행합니다. 단, 설계 문서가 지정한 고난도 작업은 모델의 한계를 넘어설 수 있으므로 아래 가드레일을 준수합니다.

1. **§12 작업 순서 표의 `실행 모델` 컬럼 확인**:
   - 설계 문서 §12 작업 순서 표에 `실행 모델` 또는 `난이도` 컬럼이 있는지 확인합니다.
2. **`Opus (opus-required)` 태스크 발견 시 중단 및 안내**:
   - 이번 구현 대상 단위가 `Opus` 또는 `opus-required` 로 지정되어 있다면, Sonnet 환경에서 임의로 구현을 강행하지 않습니다.
   - 사용자에게 아래와 같이 명확히 안내하고 작업을 멈춥니다:
     > *"§12 작업 순서에 따라 `[대상 단계/모듈]`은 복잡한 트랜잭션·동시성·핵심 도메인 제약으로 인해 `Opus (opus-required)`로 지정되어 있습니다. 정확한 구현을 위해 Opus 모델로 전환하여 진행하시겠습니까?"*
   - 사용자가 명시적으로 Sonnet 진행을 지시하지 않는 한 임의로 코드를 작성하지 않습니다.

## 설계 문서에 구현 코드가 없는 것은 정상입니다

설계 문서는 계약(시그니처·스키마)까지만 담고 **함수 본문·제어 흐름·DI 배선·쿼리 구현체는 의도적으로 담지 않습니다.**

- 상세 구현을 문서에서 찾지 마십시오. **실제 코드베이스의 기존 패턴을 표본으로 확인**하여 계약을 만족하는 구현을 직접 작성합니다.
- 문서에 코드가 적다고 해서 설계가 불완전한 것이 아닙니다. 계약이 명확하면 착수 조건은 충족된 것입니다.
- 예외적으로 §6에 3~5줄 의사코드가 있으면, 그것은 **틀리면 설계가 틀리는 흐름**(트랜잭션 경계·처리 순서·동시성)이므로 반드시 그 순서를 지킵니다.

## 구 양식 문서인 경우

Part 구분이 없는 문서라면, "변경 대상 파일 및 변경점" 절을 Part B로, 나머지를 Part A로 간주하여 위 원칙을 동일하게 적용합니다. 그 절의 코드 스니펫은 **복사 대상이 아니라 의도를 보여주는 예시**로 취급하고, 실제 코드에 맞게 다시 작성합니다.

# 구현 단위 규약 — unit 단위로 작성하기

설계 문서의 계약(§4·§5)이 **"무엇을 지킬 것인가"** 를 고정한다면, 이 절은 **"본문을 어떤 단위로 쓸 것인가"** 를 고정합니다. 계약만 맞으면 함수 본문은 자유라는 뜻이 아닙니다.

판단의 최종 질문은 하나입니다.

> **이 단위를 다른 모듈을 띄우지 않고, 입력만 주어 검증할 수 있는가?**

⚠️ 테스트를 먼저 쓰라는 뜻(Test-First / TDD)이 **아닙니다.** **떼어내 검증할 수 있는 단위로 코드를 쓰라**는 뜻입니다. 테스트 코드를 실제로 작성할지는 「테스트 코드 작성 정책」 을 따릅니다.

## 지켜야 할 것

1. **순수 로직과 부수효과를 분리합니다.**
   계산·판단·변환·검증 로직은 I/O 없이 "입력 → 출력"으로 실행되는 단위에 둡니다. 아래 부수효과는 경계 모듈(adapter)로 격리하고, 핵심 로직이 직접 호출하지 않게 합니다.
   - DB·캐시·큐 접근
   - 외부 API·SDK 호출
   - 파일 시스템
   - 현재 시각·랜덤·UUID 생성
   - 환경변수·전역 설정 직접 참조

   판단 기준: **그 로직을 검증하려고 DB·네트워크·시계를 준비해야 한다면 분리가 덜 된 것**입니다.

2. **부수효과는 주입받습니다.**
   부수효과 모듈은 호출하는 쪽에서 주입받을 수 있는 형태로 둡니다. fake·stub으로 대체 가능한 그 지점이 seam입니다. 단, seam은 **외부 의존과 맞닿는 곳에만** 둡니다.

3. **진입점은 조립만 합니다.**
   controller·handler·job·CLI command 등 진입점에는 분기·계산·변환을 두지 않습니다. 하나의 단위가 **"조회 → 판단 → 변환 → 저장 → 알림"** 을 모두 수행하고 있으면 조립하는 단위와 판단하는 단위를 나눕니다.

4. **한 단위는 책임을 한 문장으로 설명할 수 있어야 합니다.**
   설명에 "그리고", "및", "~도 한다"가 들어가면 분리 후보입니다.

## 과잉 분리 금지 (⚠️ 위 항목과 같은 무게로 지킬 것)

테스트 용이성을 명분으로 한 과잉 설계는 그 자체가 규약 위반입니다.

- 파일 하나에 함수 하나씩 기계적으로 쪼개기
- 한 곳에서만 쓰이는 몇 줄짜리 로직을 별도 모듈로 분리
- 아무 일도 하지 않고 호출만 전달하는 레이어(pass-through)
- 구현이 하나뿐인데 인터페이스·팩토리·추상 클래스를 겹겹이 두는 구조
- 디렉토리 깊이만 늘리는 중첩
- "나중에 쓸 것 같아서" 만드는 추측성 공용 모듈 (같은 역할의 유틸이 이미 있으면 재사용합니다)

판단 기준: **분리한 단위가 독립적으로 테스트할 가치가 있는가? 독립적으로 바뀔 이유가 있는가?** 둘 다 아니면 분리하지 않습니다.

## 충돌 시 우선순위

```
설계 문서 계약(§4·§5)  >  구조 문서  >  이 규약  >  기존 코드베이스 컨벤션
```

- **구조 문서**(`*-structure.md`) 경로가 args나 설계 문서를 통해 전달되면 그 문서를 읽고, **구조 문서 §4 모듈 책임·§5 의존 방향·§6 테스트 경계를 확정된 제약으로** 따릅니다. 이 경우 이 규약보다 구조 문서의 결정이 우선합니다.
- 이 규약이 설계 문서 §4·§5 계약과 충돌하면 **계약이 우선**입니다. 계약이 강제하는 시그니처를 규약을 이유로 바꾸지 마십시오.
- **기존 컨벤션(디렉토리 구성·네이밍·계층 방식)을 최대한 수용**합니다. 이 규약을 만족하는 방법이 여럿이면 컨벤션에 맞는 쪽을 고릅니다.
- 컨벤션을 따르면 규약을 지킬 수 없는 경우, 조용히 한쪽을 고르지 말고 **사용자에게 보고**합니다. 이 판단은 계약 변경이 아니므로 설계 문서를 갱신하지 않습니다.

# 구현 순서 규약 — 하위 단위부터 조립 방향으로

설계 문서 §12(작업 순서)는 참고 자료지만, **구현의 진행 방향은 이 규약으로 고정**합니다. 파일 구성은 코드 상태에 따라 달라질 수 있어도, 하위 단위를 먼저 확정하고 그 위에 조립하는 방향은 달라지지 않기 때문입니다.

| 순서 | 단계 | 대상 |
|---|---|---|
| 1 | 계약 | §4 스키마·마이그레이션, §5 타입·DTO·시그니처 |
| 2 | `Unit-순수` | I/O 없는 판단·계산·변환 로직 |
| 3 | `Unit-주입` | 비즈니스 흐름 서비스. seam은 계약(인터페이스)만 있으면 되므로 `Integration` 보다 먼저 작성합니다 |
| 4 | `Integration` | DB·외부 API adapter |
| 5 | `조립` | 진입점·DI 등록·라우팅 |

- 분류는 설계 문서 §3 『모듈 단위와 테스트 경계』 표를 따릅니다. (구조 문서가 있으면 구조 문서 §6) 표가 없는 구 양식 문서면 「구현 단위 규약」 기준으로 직접 분류합니다.
- **한 단계를 마치면 검증한 뒤 다음 단계로 넘어갑니다.** 검증은 타입 체크·빌드와, 그 단계에서 건드린 단위에 걸린 기존 테스트 실행입니다. 신규 테스트 작성 여부는 「테스트 코드 작성 정책」 을 따릅니다.
- 여러 단계를 한꺼번에 작성하지 않습니다. 특히 상위 단위(`Unit-주입`·`조립`)를 먼저 쓰고 하위 단위를 나중에 채워 넣지 않습니다.
- 해당 모듈이 없는 단계는 건너뜁니다. 수정건은 이번에 변경되는 단위에만 적용합니다.
- **예외**: §6 의사코드가 정한 처리 순서가 있거나, 컴파일 의존상 불가피한 경우(예: 기존 adapter 시그니처 변경이 선행되어야 하는 경우)에는 그 순서를 따르고, 보고에 사유를 한 줄 밝힙니다.

# 테스트 코드 작성 정책 (기본값: 신규 작성하지 않음)

**착수부터 구현 완료까지 신규 테스트 코드를 만들지 않습니다.**

> **왜**: 하나의 설계 문서를 1차·2차·3차 회차로 나누어 구현하는 흐름에서 회차마다 테스트를 쓰면, 다음 회차에서 구조가 조금만 바뀌어도 테스트부터 다시 씁니다. 구현이 아직 움직이는 동안의 테스트는 검증 가치보다 유지 비용이 큽니다. 구현이 멎은 뒤 한 번 쓰는 편이 쌉니다.

⚠️ 이것은 **신규 테스트를 "쓰지 않는다"** 는 규칙이지, **기존 테스트를 "돌리지 않는다"** 는 규칙이 **아닙니다.** 구현이 끝나면 프로젝트의 빌드와 기존 테스트를 실행해 깨진 곳을 확인합니다.

## 수정건 vs 신규 개발건

| 구분 | 기존 테스트 | 신규 테스트 |
|---|---|---|
| **수정건** (기존 코드 변경) | 이번 변경으로 깨진 것은 이번 회차에서 수리 | 작성하지 않음 |
| **신규 개발건** (새 기능·모듈) | 해당 없음 | 작성하지 않음 → 보고 시 후속 작업으로 고지 |

깨진 기존 테스트를 고치는 것은 신규 작성이 아니라 **기존 테스트 보수**입니다.

## 보고 시 고지

- **신규 개발건이 포함된 경우에만** "테스트 코드 작성이 후속 작업으로 남아 있습니다" 를 **한 줄로** 밝힙니다.
- 수정건만 있으면 고지하지 않습니다.
- `AskUserQuestion` 으로 되묻지 마십시오. 고지한 뒤 답을 기다리지 말고 종료합니다. 사용자가 요청하면 그때 작성합니다.

## 예외 — 묻지 말고 먼저 작성한 뒤 완료 처리

아래에 해당하면 **먼저 작성한 뒤 완료 처리**합니다. 이 경우 보고에 그 사유를 한 줄로 밝히고, 위 후속 작업 고지는 생략합니다.

- 사용자가 착수 시점에 테스트 작성을 명시적으로 요청한 경우
- 설계 문서 §10(성공 조건)이 특정 테스트의 통과를 성공 조건으로 못박은 경우
- 프로젝트 규약·CI가 테스트 없이는 빌드·병합을 막는 경우

판단이 애매하면 **작성하지 않는 쪽**을 택합니다.

## 하지 말 것

- ❌ 회차마다 습관적으로, 또는 "완성도" 명분으로 요청받지 않은 테스트를 덧붙이기
- ❌ 테스트를 만들지 않았다는 이유로 작업을 미완료로 보고하기 — 이 정책을 따른 것은 **정상 완료**입니다
- ❌ 테스트를 쓰지 않는다는 이유로 「구현 단위 규약」 을 느슨하게 적용하기. 규약은 **테스트 작성 여부와 무관하게** 지킵니다

# 설계 문서 갱신 정책

**구현 중 설계 문서를 습관적으로 갱신하지 마십시오.** 문서를 코드에 맞춰 따라가며 고치는 것이 작업 비용의 주요 병목입니다.

- **Part B는 갱신하지 않습니다.** 구현 결과 파일 구성·이름·순서가 달라져도 문서를 고치지 않습니다. 코드가 진실입니다.
- **Part A의 계약을 바꿔야 하는 경우에만** 사용자에게 보고하고 승인을 받습니다. 승인되면 문서를 직접 고쳐 쓰지 말고 **`/jissp-planner architecture revise [문서 경로] [변경 내용]`** 으로 해당 절만 갱신합니다.
- 사용자 피드백이 계약을 바꾸지 않는 구현 조정(변수명, 함수 분리, 에러 처리 방식 등)이라면 **설계 문서를 건드리지 않습니다.**

# 주석 원칙

**설계 문서의 서술을 코드 주석으로 옮기지 마십시오.**

설계 문서는 "왜 이 결정을 했는가"를 담고, 코드는 "이것이 무엇을 하는가"를 담습니다. 설계 근거를 코드에 복사하면 문서가 갱신될 때 주석만 낡아 **거짓 정보가 됩니다.** 근거가 필요한 사람은 설계 문서를 읽습니다.

## 남길 주석

코드만 봐서는 알 수 없으면서 **동작·안전성에 직결되는 것**, 그리고 **로직이 복잡해 한 번 읽어서는 파악되지 않는 것**만 답니다.

- 직관에 반하는 구현의 이유 — "빈 배열이면 조건을 걸지 않는다 (IN () 은 SQL 문법 오류)"
- 깨지기 쉬운 순서·전제 — "건수 쿼리는 정렬 적용 이전 빌더에서 만든다"
- 일부러 그렇게 둔 것 — "숫자가 아닌 토큰은 NaN 으로 남긴다. 검증기가 거부하도록"
- 공개 계약의 사용법 — `@deprecated`, 파라미터 우선순위 규칙
- **복잡한 로직의 동작 요약** — 다단 분기·재귀·비자명한 알고리즘 앞에 "좌표를 격자에 스냅한 뒤 인접 8칸을 훑어 최근접을 고른다" 처럼 **코드가 무엇을 하는지**를 압축해 적습니다. 이때도 요구사항 번호나 설계 근거는 넣지 않습니다

판단 기준은 **이 주석을 지우면 코드를 읽는 사람이 손해를 보는가** 입니다. 손해가 없으면 달지 않습니다.

## 달지 않을 주석

- **문서 식별자·추적 라벨** — `(R5)`, `FR-3`, `AC-2`, `§7`, `TASK-12` 처럼 PRD·설계 문서 안에서만 뜻이 통하는 기호. 코드를 읽는 사람에게 R5 는 아무 정보도 주지 않고, 문서가 개정되면 번호부터 어긋납니다. 요구사항을 코드에 되짚어 놓고 싶더라도 **코드에는 남기지 않습니다** — 그 추적은 설계 문서 쪽이 담당합니다
- **기획·PRD·UI 맥락** — "체크박스를 추가로 고를 수 없게 된다", "업종 마스터는 23종 규모"
- **설계 결정의 트레이드오프 서술** — "A 를 택하면 판정이 코어로 새어 들어온다"
- **프론트·화면 영향** — "400 은 화면 자체를 깨뜨린다", "URL·북마크가 깨진다"
- **클래스·인터페이스·파일 머리의 역할 요약** — "공용 공휴일 조회 코어 서비스", "저장 구조를 계약 DTO 로 옮겨 소비자를 떼어 둔다" 처럼 이 클래스가 무엇이고 왜 이런 구조인지 설명하는 주석. 모듈의 역할·구조 설명은 모듈 `README.md` 가 담당합니다. 클래스·인터페이스 선언에는 주석을 달지 않는 것이 기본입니다 (`@deprecated` 같은 공개 계약 표기만 예외)
- 코드를 그대로 한국어로 옮긴 것 — `if (!list.length) return` 위의 "목록이 비면 반환한다"
- 문단 길이의 배경 설명. 3줄을 넘어가면 설계 문서로 갈 내용인지 의심합니다

### 걸러내는 예

```ts
/** 패널 하단 컨트롤 (R5). 스크롤 영역 밖에 두어 항상 보이게 한다 */
```

`(R5)` 는 문서 라벨이고, 나머지는 JSX 구조를 보면 드러나는 배치 설명입니다. **주석째 지웁니다.**

```ts
/** 공용 공휴일 조회 코어 서비스. 저장 구조(row)를 계약 DTO 로 옮겨 소비자를 저장 구조에서 떼어 둔다 */
@Injectable()
export class SearchHolidayService implements ISearchHolidayExternal {
```

클래스의 역할 요약과 설계 의도입니다. 역할은 클래스명·`implements` 로 드러나고, 구조 설명은 모듈 `README.md` 몫입니다. **주석째 지웁니다.**

한 주석에 문서 라벨과 쓸 만한 설명이 섞여 있으면, 라벨을 지운 뒤 남는 문장이 위 "남길 주석" 에 해당하는지로 판단합니다. 해당하면 라벨만 떼고 남기고, 아니면 통째로 지웁니다.

## 설계 문서에 스니펫 주석이 있는 경우

설계 문서 §5(인터페이스 계약)의 스니펫이나 구 양식 문서의 코드 스니펫에 위 "달지 않을 주석" 이 포함되어 있더라도 **그대로 옮기지 말고 걸러냅니다.** 스니펫의 주석은 계약을 설명하려고 붙은 것이지, 최종 코드의 일부가 아닙니다. 특히 스니펫에는 어느 요구사항을 구현하는 코드인지 표시하려고 요구사항 번호나 절 번호(`R5`, `§4`)가 붙어 있는 경우가 많은데, 이는 **문서 안에서 대조용으로만 쓰이는 표기**이므로 코드로 옮길 때 반드시 제거합니다.

테스트의 `describe`/`it` 설명도 같습니다. **무엇을 검증하는지**만 쓰고, 왜 그렇게 설계했는지는 괄호로 덧붙이지 않습니다.
